# Figma 제작 플레이북 (이 하네스 전용 보충 규칙)

`use_figma`의 전체 API 규칙은 figma-use/figma-generate-design 스킬(MCP 리소스)이 이미 다룬다. 여기서는 **이 하네스 특유의 규칙**만 적는다. `use_figma`를 호출하기 전에 반드시 `figma-use`(및 화면 조립이면 `figma-generate-design`)를 리소스로 로드할 것.

> **이번 프로젝트의 화면 목록·프레임 규격은 여기 없다.** `projects/<슬러그>/build-plan.md`에 있다.

## Greenfield(기존 디자인시스템 없음) 처리

`figma-generate-design`의 기본 전제는 "발행된 디자인시스템에서 컴포넌트를 가져와 조립"이다. 기존 자산이 없는 프로젝트에서는 이 전제가 성립하지 않는다.

1. `search_design_system` / `get_libraries`로 연결된 라이브러리가 있는지 **1회만** 확인한다 — 빈 결과면 즉시 로컬 제작으로 전환하고 반복 검색하지 않는다.
2. 로컬 미니 디자인시스템을 직접 만든다: `brief.md`의 토큰 값으로 색상/타이포 변수·텍스트 스타일을 **먼저** 등록 → 반복 요소를 로컬 컴포넌트로 제작 → 화면은 그 인스턴스로 조립.
3. 새 파일이 필요하면 `create_new_file`로 만들고 반환된 `fileKey`를 이후 모든 호출에서 재사용한다.

## 분해 원칙

한 번의 `use_figma` 호출에 화면 하나를 통째로 넣지 않는다. 호출이 커질수록 실패 지점을 특정할 수 없고, 부분 실패 시 되돌리기도 어렵다.

순서 원칙 — **토큰 → 컴포넌트 → 화면 → 엣지케이스**. 앞 단계가 끝나기 전에 뒤 단계로 가면 나중에 하드코딩을 되돌리는 비용이 커진다.

각 단계 후 `get_screenshot` 또는 `node.screenshot()`으로 즉시 확인하고, 문제가 있으면 다음 단계로 넘어가기 전에 고친다.

프로젝트별 실제 분해 목록(화면 몇 개를 어떤 순서로)은 `build-plan.md`에 미리 적고 시작한다 — 만들면서 즉흥적으로 정하지 않는다.

## 반환값 규약

모든 쓰기 스크립트는 `{ createdNodeIds, frameId, notes }` 형태로 반환해, 다음 호출과 A/C단계 검증이 이 ID들을 바로 참조할 수 있게 한다.
