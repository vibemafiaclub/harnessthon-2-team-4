# Figma 제작 플레이북 (이 하네스 전용 보충 규칙)

`use_figma`의 전체 API 규칙은 figma-use/figma-generate-design 스킬(MCP 리소스)이 이미 다룬다. 여기서는 **이 하네스 특유의 규칙**만 적는다. `use_figma`를 호출하기 전에 반드시 `figma-use`(및 화면 조립이면 `figma-generate-design`)를 리소스로 로드할 것.

> **이번 프로젝트의 화면 목록·프레임 규격은 여기 없다.** `projects/<슬러그>/build-plan.md`에 있다.

## Greenfield(기존 디자인시스템 없음) 처리

`figma-generate-design`의 기본 전제는 "발행된 디자인시스템에서 컴포넌트를 가져와 조립"이다. 기존 자산이 없는 프로젝트에서는 이 전제가 성립하지 않는다.

1. `search_design_system` / `get_libraries`로 연결된 라이브러리가 있는지 **1회만** 확인한다 — 빈 결과면 즉시 로컬 제작으로 전환하고 반복 검색하지 않는다.
2. 로컬 미니 디자인시스템을 직접 만든다: `brief.md`의 토큰 값으로 색상/타이포 변수·텍스트 스타일을 **먼저** 등록 → 반복 요소를 로컬 컴포넌트로 제작 → 화면은 그 인스턴스로 조립.
3. 새 파일이 필요하면 `create_new_file`로 만들고 반환된 `fileKey`를 이후 모든 호출에서 재사용한다.

## 분해 원칙

한 번의 `use_figma` 호출에 화면 하나를 통째로 넣지 않는다. 호출이 커질수록 실패 지점을 특정할 수 없고, 부분 실패 시 되돌리기도 어렵다.

순서 원칙 — **토큰 → 컴포넌트 → 화면 → 엣지케이스**. 앞 단계가 끝나기 전에 뒤 단계로 가면 나중에 하드코딩을 되돌리는 비용이 커진다.

각 단계 후 `get_screenshot` 또는 `node.screenshot()`으로 즉시 확인하고, 문제가 있으면 다음 단계로 넘어가기 전에 고친다.

프로젝트별 실제 분해 목록(화면 몇 개를 어떤 순서로)은 `build-plan.md`에 미리 적고 시작한다 — 만들면서 즉흥적으로 정하지 않는다.

## 반환값 규약

모든 쓰기 스크립트는 `{ createdNodeIds, frameId, notes }` 형태로 반환해, 다음 호출과 A/C단계 검증이 이 ID들을 바로 참조할 수 있게 한다.

## 알려진 함정

### `setBoundVariableForPaint`는 color 외 paint 속성을 떨어뜨린다

`figma.variables.setBoundVariableForPaint(paint, 'color', variable)`로 컬러 변수를 바인딩하면, base paint의 `opacity` 같은 color 이외 속성이 반환 paint에 실려오지 않는 경우가 있다. **에러가 나지 않는다.** 알파를 준 fill(예: 상태 배지 배경 = 액센트 컬러 14% 틴트)에 이걸 쓰면 opacity가 조용히 1로 리셋되어, 배지가 화면을 가득 채운 원색 덩어리로 렌더된다.

- **증상**: 스크립트는 성공 반환, 노드 속성 조회도 정상처럼 보임 → **스크린샷으로만 발견된다.**
- **해결 (유일하게 재현 가능)**: 알파 블렌딩을 쓰지 말고, 미리 계산한 solid pastel 컬러를 토큰으로 등록해 그걸 바인딩한다. 틴트 단계가 필요하면 토큰 자체를 단계별로 만든다. 현장 트레이스에서 적용한 전 케이스(배지 4변형 + 인스턴스 다수, 아바타)에서 예외 없이 즉시 성공.
- **하지 말 것 — opacity 되씌우기(`node.fills = [{ ...bound, opacity: base.opacity }]`)**: **비결정적으로 실패한다.** 현장 트레이스 4회 시도 중 2회 성공(배지 메인 컴포넌트, 데모 카드 내 인스턴스) / 2회 실패(아바타 메인 컴포넌트, `swapComponent` 직후의 배지 인스턴스). 재현 조건 불명. 몇 번 성공하는 걸 보고 채택하면 나중에 조용히 깨진다.

이 함정이 **분해 원칙의 "각 단계 후 즉시 스크린샷"이 선택이 아닌 이유**다. 토큰·컴포넌트 단계에서 눈으로 확인하지 않고 화면 조립까지 진행하면, 5개 화면을 다 만든 뒤에야 배지가 깨진 걸 발견하게 된다.

### 스크린샷과 노드 속성이 어긋날 수 있다

위 되씌우기 실패 케이스에서, `node.fills` 조회는 `opacity: 0.16`을 정확히 돌려주는데 **바로 다음 스크린샷은 여전히 불투명하게 렌더**됐다. 문서 데이터는 맞고 그림만 틀린 상태다.

원인은 확인되지 않았다. 현장 가설은 "Figma 문서 버그가 아니라 렌더 서비스가 아주 최근 mutation을 못 따라가는 sync/캐시 지연"이지만 **검증되지 않은 추정**이다.

실무 규칙:

- 속성 조회가 통과했다고 C단계를 건너뛰지 않는다 — 이 케이스가 정확히 "데이터는 맞는데 화면이 깨진" 경우다.
- 반대로 스크린샷 한 장이 예상과 다르다고 곧장 국소결함으로 단정하지 않는다. 재렌더로 한 번 더 확인한다.
- 재렌더해도 속성과 그림이 계속 어긋나면, 그 구현 방식 자체를 버리고 **결정적으로 동작하는 방식**(위의 solid 토큰)으로 바꾼다. 어긋남의 원인을 추적하는 데 시간을 쓰지 않는다.
