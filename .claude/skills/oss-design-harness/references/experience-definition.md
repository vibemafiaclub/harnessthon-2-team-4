# 핵심경험 정의 — 페르소나 · `CE-n` · 인접 경험

> **이식 노트(2026-09-05)**: iceberg-1234 하네스 `steps/P-persona-experience.md`를 이 하네스의 4막·원장·요구 계약 구조로 옮긴 것이다. 원문의 독립 P단계는 이 하네스에 대응하는 막이 없다 — **0단계에서 초안, I막에서 승격**으로 분해했다(아래 「어느 막에서 하는가」). 프로젝트 값(페르소나 이름·화면명·실제 `CE` 문장)은 여기 없다 — `design/<project-id>/brief.md`와 `contracts/requirements.json`에 있다.

## 이 파일이 있는 이유

`stage-a-structural.md`의 **A-T(CE1~CE7)** 와 `stage-c-aesthetic.md`의 **C-X(CX1~CX5)** 는 `CE-n`을 기준으로 판정한다. 그런데 이 하네스에는 **`CE-n`을 만들어 내는 절차가 없었다.** 그 결과 축 ③은 언제나 `검증 불가`로 떨어지고, `design-principle.md`의 규칙("추적 근거가 없으면 `Pass`가 아니라 `검증 불가`")에 따라 최종 판정이 FAIL이 된다 — **하네스가 구조적으로 통과할 수 없는 상태**였다. 이 파일이 그 입력을 생산한다.

| 축 | 이 절차의 역할 |
|---|---|
| **③ 핵심경험** | **정의 전담.** W막·A·C가 전부 여기서 나온 `CE-n`을 기준으로 계획하고 판정한다 |

🔴 **여기서 정의되지 않은 경험은 파이프라인 어디에서도 검증되지 않는다.**

## 어느 막에서 하는가 — 초안과 승격을 분리한다

`design-principle.md`는 `CE-n` 정의를 I막에, 추적성 계획을 W막에 둔다. 그런데 라우터 순서는 `M → 0 → B → W → I → U`이므로 **W막이 아직 존재하지 않는 `CE-n`을 참조**하게 된다. 이 순환은 이 하네스의 후보→승격 기계장치로 푼다.

| 시점 | 무엇을 하나 | `CE-n`의 상태 | 소스 |
|---|---|---|---|
| **M막** | 핵심경험의 **관습적 해법**만 관찰 (`reference-research.md`) | 아직 없음 | — |
| **0단계** | 이 파일의 §1~§9로 **초안**을 만들어 원장에 올린다 | **후보** | `사람-원문`에서 온 것만 확정 가능, 나머지는 `사람-해석` |
| **B단계** | 핵심경험 **강화 수단** 결정 — 시그니처 피처 | 후보 (변경 금지, 인용만) | — |
| **W막** | 화면 ↔ `CE-n` **추적성 계획** (`screen-specification.md`) | 후보 기준으로 계획 | — |
| **I막** | 실사용자·시뮬레이션 체험으로 **정정·승격** → `LOCK-I` | **확정** | 승격 원문 |
| **U막 이후** | A-T / C-X가 확정된 `CE-n`으로 판정 | 확정 (UNLOCK 없이 변경 금지) | — |

★ **W막을 후보 상태의 `CE-n`으로 진행하는 것은 정상이다.** 막는 것은 그 반대다 — `CE-n` 없이 W막에 들어가면 화면 목록의 근거가 PRD 목록뿐이 되어, I막에서 갭이 쏟아져도 `LOCK-W`와 충돌해 UNLOCK 비용을 문다.

★ **I막에서 `CE-n`이 바뀌면 그것은 W막 재작업 신호다.** 조용히 U막으로 가지 않는다 — 바뀐 `CE-n`이 W의 화면 목록·CTA와 충돌하면 `UNLOCK 요청`(`process-acts.md`)을 낸다.

## 근거 라벨 — 이 하네스의 소스 어휘를 쓴다

원문(iceberg)은 `[PRD]` / `[관찰]` / `[가설]` 세 라벨을 쓴다. 이 하네스는 `stage-0-alignment.md`의 **다섯 소스**가 이미 원장 어휘이므로 그것을 쓴다. 라벨 체계를 두 벌 두지 않는다.

| iceberg 라벨 | 이 하네스의 소스 | 확정 가능? |
|---|---|---|
| `[PRD]` | `사람-원문` — PRD·디자이너 발화 원문 | 예 |
| `[관찰]` | `실측` — 레퍼런스 화면에서 직접 관찰 (증거 경로 필수, `reference-research.md`) | 예 |
| `[가설]` | `사람-해석` — 에이전트가 도출한 추론 | **아니오 — 후보.** 사람이 승격해야 확정 |
| — | `가정(위임)` | 사람이 명시적으로 위임한 항목만 |
| — | `차단` | 사람 권한 필요, 미답 |

🔴 **Primary `CE-n`은 `사람-원문` 또는 `실측` 근거를 최소 하나 갖는다.** `사람-해석`만으로 만든 Primary는 PRD와 무관한 제품을 낳는다. 이는 「소스 어휘를 더 쪼갠다」의 규칙("`사람-해석`은 확정 불가")이 축 ③에 적용된 것일 뿐, 새 규칙이 아니다.
🔴 **`사람-해석`을 `사람-원문`으로 위장하지 않는다.** 라벨을 섞는 것이 이 절차의 가장 심각한 실패다 — `docs/harness-lessons.md` L13이 정확히 이 사고다.

## 실행 절차

기능이나 아이디어부터 시작하지 않는다. **근본 욕구 → 대상의 구조 → 시장의 구조적 한계 → 새로운 관점 → 핵심 경험** 순으로 간다. PRD는 대개 "무엇을 만들지"만 적고 "유저가 왜 그것을 필요로 하는지"는 비운다. 그 공백을 메우는 절차다.

### 1. 페르소나 정의

PRD의 유저 스토리·사용자 상황과 M막 레퍼런스 관찰에서 도출한다.

| 항목 | 내용 |
|---|---|
| 라벨 | 역할 기반 (예: "주 3회 방문하는 재방문자") |
| 상황 | 언제·어디서·어떤 상태로 쓰는가 (이동 중 / 한 손 / 짧은 세션 / 불안정한 네트워크) |
| 근본 욕구 | 표면 요구 아래의 진짜 욕구 |
| 제약 | 시간·주의력·환경·숙련도의 한계 |
| 실패 시나리오 | 목적을 달성하지 못하면 무슨 일이 생기는가 |

각 항목에 소스를 붙인다.

🔴 **원본(iceberg)의 "Primary 페르소나 1명 강제"는 이 하네스로 옮기지 않는다** (`docs/PLAN-design-process-import.md` §3). 여러 역할이 함께 쓰는 제품에서는 역할 하나를 Primary로 접는 순간 나머지 역할의 PRD 요구가 **중요도 라벨 때문에** 누락된다. 대신:

- **화면별 주 사용 역할**은 정한다 (`screens[].blocks[]`의 위계 근거). 제품 전체의 Primary를 하나로 접지는 않는다.
- **어느 역할의 PRD 요구도 우선순위 라벨을 이유로 누락하지 않는다.** 역할이 여럿이면 `personas[]`에 여럿을 두고, 각각의 요구가 최소 하나의 `CE-n`에 연결되는지 확인한다.
- 역할 간 화면 요구가 **충돌**하면 임의로 한쪽을 접지 않는다 — 충돌 상태로 표시해 사람에게 보여준다(`stage-0-alignment.md` 충돌 처리).
- `project.json`의 `interview.audiences`가 여럿이면 I막에서 **각각** 인터뷰한다.
- 페르소나의 **상황·제약은 `foundation-derivation.md`의 토큰 하한 도출 입력**이다. 여기가 비면 거기서 대비·최소 크기 하한을 근거 없이 고르게 된다.

#### 핵심 행동 + 빈도

**각 역할**이 이 제품에서 하는 행동과 **빈도**를 함께 적는다. 역할이 여럿이면 역할별로 표를 나눈다.

| # | 핵심 행동 | 빈도 | 소스 |
|---|---|---|---|
| 1 | | 매일 / 매 세션 | |
| 2 | | 주 1회 | |
| 3 | | 최초 1회 | |

🔴 **이 빈도가 W막의 블록 위계(P0/P1/P2)를 결정한다.** CE 우선순위만으로는 부족하다 — 같은 Primary CE 안에서도 매일 하는 행동과 최초 1회 설정은 배치가 달라야 한다.

### 2. Find the Core — 근본 문제 규명

- 사용자는 **왜** 이것을 쓰는가? / 실제로 얻으려는 **변화**는? / 이 대상만의 **고유한 작동 원리**는?

기능 목록으로 답하지 않는다. **"무엇이 달라지는가"**로 답한다.

### 3. Model the System — 구조와 관계로 해석

대상을 개별 요소가 아니라 구조와 관계로 본다: `고정 요소 / 변화 요소 / 관계 / 시간 / 결과`.
이 모델이 W막 IA(정보 구조)의 근거가 된다 — 여기가 비면 IA 그룹핑 근거가 "카테고리가 달라서"로 떨어진다.

### 4. 인접 경험 매핑 — PRD 밖에서 가져오기

각 역할의 **상황**을 놓고, PRD에 없지만 그 상황에 실제로 동반되는 경험을 나열한다.

| # | 도출 질문 |
|---|---|
| 1 | **직전** — 이 화면에 오기 전에 유저는 무엇을 하고 있었나? (앱 밖 포함) |
| 2 | **직후** — 목적을 달성한 후 무엇을 하려 하나? |
| 3 | **동반** — 이 일을 하는 동안 같이 신경 쓰는 것은? (시간·비용·타인·불안) |
| 4 | **대체** — 이 제품이 없으면 어떻게 해결하나? (엑셀·메모·전화·타 앱) |
| 5 | **연결** — 인접 도메인에서 이미 익숙해진 해결 방식은? |

| 인접 경험 | 유형 | 유저 흐름과의 연결 관계 | 디자인 시사점 | 소스 |
|---|---|---|---|---|
| | 직전/직후/동반/대체/연결 | | | |

🔴 **"유저 흐름과의 연결 관계"를 반드시 적는다.** 연결 관계를 못 쓰면 그것은 이 제품의 관심사가 아니다 — 지우고 넘어간다. 이 열이 비면 인접 경험 매핑이 배경 서술이 되어 W막이 쓸 수 없다.

### 5. Find the Structural Gap — 구조적 공백

> 중요한 사용자 욕구 또는 도메인 특성 중, 시장이 아직 충분히 제품화하지 못한 것은 무엇인가?

경쟁사의 기능 유무보다 **문제 정의·구조·경험의 Gap**을 우선한다. M막에서 관찰한 카테고리 관습을 근거로 쓴다 — 3개 이상 앱에서 공통 관찰된 것이 관습이고, **관습이 다루지 않는 영역**이 Gap 후보다.

### 6. Reframe — 질문 바꾸기

```
기존 질문: "어떻게 더 빠르게 ___할 수 있게 할까?"
재구성:    "애초에 ___를 해야 하는 이유를 없앨 수 있을까?"
```

### 7. Define the Concept — 하나의 중심 원리로 압축

| 항목 | 정의 |
|---|---|
| **Core Truth** | 발견한 핵심 사실 |
| **Worldview** | 서비스가 그 사실을 바라보는 관점 |
| **Core Experience** | 사용자가 반드시 경험해야 할 **변화** |
| **Core Mechanism** | 그 경험을 만드는 **최소 구조** |

발산에서는 충분히 탐색하되 **수렴에서는 중심 원리 하나만 남긴다.** 이 Concept이 B단계 방향 선택의 상위 제약이다.

### 8. 핵심경험 `CE-n` 확정

위 과정을 **판정 가능한 `CE-n` 목록**으로 변환한다. 이것이 최종 산출물이다.

| 항목 | 내용 | 계약 필드 |
|---|---|---|
| ID | `CE-01`, `CE-02` … | `id` |
| 우선순위 | Primary / Secondary | `priority` |
| 유저의 목적 | "유저는 ___하고 싶다" | `statement` |
| 성공 조건 | "___했을 때 ___를 확인할 수 있으면 성공" | `success_condition_observable` |
| 근거 | 소스 + 원문 위치 | `evidence_labels` |
| 페르소나 | 어떤 페르소나의 경험인가 | (statement에 포함) |
| 변화 | "___에서 ___로 바뀐다" (Core Experience와 연결) | (statement에 포함) |

#### 성공 조건 작성 규칙

A-T의 CE4~CE6과 C-X의 CX1~CX4가 **이 문장 하나를 기준으로** 판정한다. 따라서:

- ✅ **관찰 가능한 화면 상태**로 쓴다: "저장 후 목록에 항목이 나타나고 성공 토스트가 보이면 성공"
- ❌ 내면 상태로 쓰지 않는다: "유저가 만족감을 느끼면 성공" → 판정 불가 → 축 ③ `검증 불가` → FAIL

🔴 이 문장이 애매하면 **A·C 두 단계가 동시에 무력해진다.** 판정자가 두 명인데 자가 하나뿐인 구조이므로, 여기의 모호함은 뒤에서 복구되지 않는다.

### 9. Translate to Product — 경험 흐름

각 Primary `CE-n`에 대해 아래 흐름을 쓴다. 이것이 W막 Userflow의 골격이다.

```
Pain → Entry → Core Interaction → Understanding/Decision → Outcome
```

| 단계 | 내용 |
|---|---|
| **Pain** | 유저가 느끼는 문제 상태 |
| **Entry** | 🔴 이 흐름에 **들어오는 지점** — 어디서·어떤 상태로 진입하는가 |
| **Core Interaction** | 제품이 제공하는 핵심 체험 |
| **Understanding/Decision** | 그 체험으로 유저가 이해하거나 결정하게 되는 것 |
| **Outcome** | 최종적으로 달라진 상태 |

🔴 **`Entry`는 §4의 "직전 경험"과 직결된다.** 유저가 앱 밖에서 무엇을 하다 왔는지가 진입 화면의 요건을 정한다. Entry를 비우면 W막이 진입 화면을 누락하고, C-X의 CX5가 실패한다.

### 10. 추론 체인 검증 — 끝내기 전에

앞 절의 결과가 뒷 절의 근거로 **실제로 연결되는지** 확인한다.

```
근거(사람-원문/실측) → 근본 문제(§2) → Structural Gap(§5) → 재구성 질문(§6)
  → Concept(§7) → CE-n(§8) → UX Flow(§9)
```

| 연결 | 확인 질문 |
|---|---|
| 근거 → 근본 문제 | 근본 문제가 인용된 근거에서 도출되는가, 별개의 직감인가 |
| 근본 문제 → Gap | Gap이 그 문제의 미해결 부분인가 |
| Gap → 재구성 질문 | 재구성 질문이 Gap을 겨냥하는가 |
| 재구성 질문 → Concept | Concept이 그 질문에 답하는가 |
| Concept → `CE-n` | 각 `CE-n`이 Core Experience를 분해한 것인가 |
| `CE-n` → UX Flow | 흐름이 성공 조건에 도달하는가 |

🔴 **끊어진 연결이 하나라도 있으면 그 지점부터 다시 본다.** "근거 없이 등장한 결론"은 W·U에서 추적 불가능해지고 결국 축 ③이 `검증 불가`가 된다. 끊어진 채로 진행하면 그 사실을 **미해결 결정의 이름**(절대 규칙 5)으로 남긴다 — 예: "CE-02의 Gap→Concept 연결 미확립".

| 무엇 | 어디에 |

| 인접 경험 | 같은 파일 → `adjacent_experiences[]` |
| `CE-n` 목록 (ID·우선순위·statement·성공 조건·근거·참조) | 같은 파일 → `core_experiences[]` |
| Concept · 추론 체인 · Structural Gap · Reframe | `design/<project-id>/brief.md` 핵심경험 섹션 |
| 미확정·차단 항목 | `brief.md` 가정 로그 + 미해결 결정의 이름 |

🔴 **CE 본문을 두 곳에서 관리하지 않는다** (`PLAN-design-process-import.md` §5). `CE-n`의 **정본은 `core_experiences[]`** 이고, 대응하는 요구는 `requirement_refs`로 **REQ ID만 참조**한다. `requirements[]`에 `kind: "core_experience"`로 본문을 복제하지 않는다 — 두 곳이 갈라지면 어느 쪽이 승격된 것인지 알 수 없게 된다. 기존 데이터가 두 위치에 있으면 대조표를 만든 뒤 충돌을 해결한다.

`core_experiences[]`의 `screens` / `evidence_nodes` / `flow_depth_taps`는 **여기서 채우지 않는다** — W막(화면)과 U막(nodeId)이 채운다.

## 완료 조건

0단계에서 이 목록이 **후보로** 채워지면 W막으로 간다. I막 승격 후 `LOCK-I`가 붙으면 확정이다.

- [ ] PRD가 요구하는 **모든 역할**이 `personas[]`에 있음 (상황·근본 욕구·제약·실패 시나리오 + 소스)
- [ ] 각 역할의 요구가 최소 하나의 `CE-n`에 연결됨 — 우선순위 라벨 때문에 누락된 역할 0건
- [ ] 핵심 행동 + **빈도** (매일 / 주 1회 / 최초 1회) — W막 블록 위계의 근거
- [ ] Find the Core — 기능 목록이 아닌 **변화**로 서술
- [ ] Model the System — 구조/관계 모델 (W막 IA 근거)
- [ ] 인접 경험 5개 질문별 결과 + **유저 흐름 연결 관계** 열이 전부 채워짐
- [ ] Structural Gap — 카테고리 관습이 다루지 않는 영역
- [ ] Reframe — 기존 질문 → 재구성 질문
- [ ] Concept — Core Truth / Worldview / Core Experience / Core Mechanism **각 1개**
- [ ] `CE-n` 목록이 `contracts/requirements.json`에 기입됨
- [ ] Primary `CE-n` **최소 1개**, 각각 `사람-원문` 또는 `실측` 근거 보유
- [ ] 모든 성공 조건이 **관찰 가능한 화면 상태**로 작성됨
- [ ] Primary `CE-n`별 `Pain → Entry → … → Outcome` 흐름
- [ ] `Entry`가 §4의 "직전 경험"과 연결됨
- [ ] 추론 체인 6개 연결 전부 확인 (끊어진 것은 이름으로 기록)
- [ ] 모든 서술에 소스 표기

## 금지 사항

- ❌ **아이디어·기능부터 시작.** 근본 욕구와 구조 이해가 먼저다.
- ❌ 경쟁사 기능 **단순 조합**. 차별점을 **기능 수**에서 찾기.
- ❌ 도메인의 고유성을 **범용 기능·기술로 대체**.
- ❌ `사람-해석`을 `사람-원문`으로 **위장**하기.
- ❌ `사람-해석`만으로 **Primary `CE-n`** 만들기.
- ❌ 성공 조건을 **내면 상태**로 쓰기.
- ❌ 🔴 역할 하나를 Primary로 접어 **다른 역할의 PRD 요구를 누락**하기.
- ❌ 수렴에서 **중심 원리를 여러 개** 남기기.
- ❌ 🔴 **에이전트가 `CE-n`을 스스로 확정 선언하기.** 승격은 I막에서 사람이 한다(절대 규칙 2). 0단계 산출물은 언제나 **후보**다.
- ❌ 🔴 I막 이후에 `CE-n`을 **조용히 수정**하기. `LOCK-I` 이후 변경은 `UNLOCK 요청`뿐이다.
