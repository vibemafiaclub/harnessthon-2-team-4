# 레퍼런스 리서치 절차 (0단계 보조)

목적: 요구사항만 주어졌을 때, **레퍼런스를 스스로 찾아 추리고 조합하는** 절차. 도메인이 바뀌어도 이 절차 자체는 바뀌지 않는다.

> 찾아낸 레퍼런스 목록과 반응은 `design/<project-id>/reference-review.md (양식 `templates/reference-review.md`)`에 쓴다. 이 파일에는 **찾는 방법**만 있다.

## 0. 목적이 둘이다 — 하나가 없어도 나머지는 남는다

| 목적 | 무엇에 쓰나 | 클라이언트가 없으면 |
|---|---|---|
| A. 자극물 | 사람에게 보여주고 반응을 뽑는다 | **소멸** |
| B. 에이전트의 시각 입력 | 이 도메인·과업의 실제 화면이 어떤 밀도·톤·구조인지 눈으로 확인한다 | **그대로 남는다** |

A가 없다고 이 절차 전체를 건너뛰지 않는다. B는 산출물의 품질을 직접 결정한다 — 실물을 보지 않고 정한 값은 텍스트 추론의 산물이고, 그게 화면에서 "본 적 없는 사람이 만든 것" 으로 드러난다.

## 0-1. 먼저 인정할 한계

에이전트는 검색은 하지만 **이미지를 실제로 봐야 미적 판단이 된다.** 이미지에 접근하지 못한 레퍼런스는:

- 정보구조·플로우 서술의 근거로만 쓴다.
- **톤·색·타이포 판단의 근거로는 쓰지 않는다.** 본 적 없는 것을 봤다고 하지 않는다.
- 그 상태로 판단이 필요하면 사람에게 그 레퍼런스를 확인해달라고 요청한다.

## 1. 검색어 생성 — 도메인 직역 금지

요구사항의 도메인명을 그대로 검색하면 대개 빈손이거나 마케팅 페이지만 나온다. 직접 경쟁 서비스가 없는 도메인일수록 그렇다. **세 축으로 쿼리를 나눠 만든다.**

| 축 | 무엇을 찾는가 | 쿼리 형태 |
|---|---|---|
| **과업 구조** | 도메인이 달라도 *같은 문제*를 푸는 화면 | "여러 명 일정 맞추기 앱", "다중 선택 후 그룹 만들기 UI" |
| **도메인** | 같은 맥락의 실제 서비스 | 도메인명 + "앱", 영문 도메인명 + "app" |
| **정서/톤** | 과업 정서에 맞는 시각 언어 | "차분한 일정 앱 UI", "calm scheduling app" |

- **한국어·영어를 모두 돌린다.** 국내 서비스는 한국어로만 잡히고, 시각 레퍼런스는 영어로만 잡힌다.
- 과업 구조 축이 가장 중요하다. **도메인이 달라도 과업이 같으면 훨씬 쓸모 있다.**

## 2. 소스별 성격 — 무엇을 어디서 가져오는가

| 소스 | 성격 | 무엇에 쓰나 |
|---|---|---|
| 앱스토어/플레이 스토어 스크린샷 | 실제 출시된 서비스, 접근 쉬움 | **정보구조·플로우** |
| 실제 앱을 직접 써보기 | 가장 신뢰도 높음 | 정보구조·플로우·상태 처리 |
| UI 패턴 아카이브(Mobbin 등) | 실서비스 화면 모음 | 정보구조·플로우 |
| Dribbble·Behance | 컨셉샷. **실사용 검증 안 됨** | **톤·타이포·마감**만 |

**철칙: 정보구조는 실서비스에서, 미적 마감은 컨셉샷에서 가져온다.** 반대로 하면 예쁘지만 작동하지 않는 화면이 나온다 — 컨셉샷은 빈 상태·에러·긴 목록을 그리지 않기 때문에 그 구조를 베끼면 현실 데이터에서 무너진다.

## 3. 추리는 기준

**인기 지표(조회수·좋아요)는 1차 필터로만 쓴다.** 그건 "많은 사람이 봤다"이지 "우리 과업에 맞다"가 아니다. 인기순으로 15~20개를 훑은 뒤, 아래 3기준으로 **4~6개**까지 좁힌다.

1. **과업 유사도** (가장 중요) — 그 화면이 해결하는 문제가 우리 요구사항의 문제와 같은가. **도메인이 달라도 된다.**
2. **제약 유사도** — 데이터 규모·상태 개수·역할 수가 비슷한가. 항목 5개를 다루는 화면과 100개를 다루는 화면은 다른 문제다. 규모가 다르면 그 해법은 우리에게 안 통한다.
3. **최신성** — 오래된 것은 플랫폼 관례가 달라 그대로 쓰면 어색하다. 다만 과업 유사도가 높으면 오래됐어도 취한다(구조는 유행을 덜 탄다).

**의도적으로 1~2개는 "안 좋다고 판단한 것"을 남긴다.** 좋은 것만 모으면 "왜 좋은지"가 안 나온다. 반례가 있어야 기준이 선명해지고, 그 대비가 그대로 판단기준이 된다.

## 4. 조합 판단 순서 — 무엇을 취하고 무엇을 버리나

**레퍼런스를 통째로 가져오지 않는다.** 한 레퍼런스의 무드를 전부 가져오면 그건 그 서비스의 클론이 되고, 우리 요구사항에서 나온 결정이 하나도 없게 된다.

순서:

1. **각 레퍼런스에서 "이 화면이 잘 푸는 문제" 하나를 한 줄로 적는다.** 두 개 이상 적히면 아직 덜 분해한 것이다.
2. **그 문제를 우리 요구사항의 항목·난제에 매핑한다.** 대응하는 게 없으면 **버린다** — 좋아 보여도 우리 문제가 아니다.
3. **축별로 후보를 모은다.** (정보밀도 축에는 A의 방식, 상태 표현 축에는 C의 방식) 이 축은 B단계에서 쓸 축과 같은 것이다.
4. **충돌 검사** — 서로 다른 레퍼런스에서 가져온 결정들이 한 화면에서 양립하는가. 예: A의 고밀도 목록과 C의 넉넉한 여백은 같이 못 간다. 충돌하면 어느 쪽이 우리 요구사항에 더 맞는지로 판정한다.
5. 살아남은 것을 `decisions.md`의 축 후보로 넘긴다.

## 5. 기록 형식 — `design/<project-id>/reference-review.md (양식 `templates/reference-review.md`)`

| 항목 | 내용 |
|---|---|
| 출처 | URL 또는 앱 이름 + 화면 |
| 봤는가 | 이미지를 실제로 봤는지 예/아니오 (0장 참고) |
| 잘 푸는 문제 | 한 줄 |
| 우리 요구사항 대응 | §번호 또는 난제 이름. 없으면 버린 이유 |
| 취할 것 | 어느 축에 무엇을 |
| 버릴 것 | 무엇을 왜 |
| 사람 반응 | 있으면 **원문 그대로**. 요약하지 않는다 |

사람이 레퍼런스에 반응을 남겼다면 그게 이 절차 전체보다 중요하다 — `stage-0-alignment.md` §3의 역추출로 넘긴다.

## 6. dev 추가 규칙 — 제시 매체와 되묻기

- 레퍼런스는 HTML 갤러리(스크래치 디렉터리 또는 Artifact)로 **한 번에 하나**만 보여 준다. 여러 개를 동시에 주면 비교 모드로 들어가 개별 반응이 흐려진다.
- 첫 반응은 라벨이다. 반응에서 나온 단어를 **같은 축 유사 변형 2~3개**(probe-2/3)로 다시 시험한다 — `process-acts.md` 되묻기 규칙. probe 기록이 없는 후보는 승격 질문 금지.
- ooo interview 어댑터(`docs/integrations/ooo-interview.md`)를 쓰면 `references` cue 하나당 5축 대비 질문이 자동 생성된다.
- 이미지를 못 본 레퍼런스(`봤는가=아니오`)는 구조 근거로만 쓴다. yj1 §0-1과 동일.
