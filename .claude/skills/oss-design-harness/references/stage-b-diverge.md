# B단계 — 발산·수렴 방법론

> **합병 노트(2026-09-05)**: 이 파일은 `dev`(운영 뼈대)와 `feat/yj1`(판정 디테일), iceberg-1234 하네스(3축 원칙·추적성·정량 미학)를 합친 것이다. 출처를 각 절 머리에 적었다. 프로젝트 값(색·화면명·인명)은 여기 없다 — `docs/projects/<id>/`와 `design/<id>/`에 있다.

## B단계 — 발산·수렴

어떻게 만들지에 정답이 하나가 아닐 때.

**스킵 경로 — 축 분기가 불필요한 경우**: 사람이 이미 명확한 스펙을 줬거나 정답이 하나라면, `decisions.md` 라운드 1에 **"축 분기 불필요 — 사유: …"**를 적고 선택 완료로 간주해 제작단계로 간다. 이 경로가 없으면 라우터가 B단계를 벗어날 방법이 없어 순환한다(후보를 만들려면 B를 실행해야 하고, B를 벗어나려면 후보가 있어야 한다).

### B-1.5 운영 메모 — 대표 시안 N개 + 외부 평가 하네스 (2026-09-05 사용자 요청, 기준 대기)

사용자가 "대표 시안 3개씩 빠르게 만들고 평가·검수 하네스로 좋은 방향을 선택"하기를 원한다. B-2/B-3의 배선은 그대로 쓰되 다음을 적용한다.
- 후보 수 기본값 **3**(축마다). 후보는 여전히 텍스트 스펙이며, 사람이 "시각 비교가 필요하다"고 하면 **W막 그레이박스 수준**으로만 Figma에 그린다(하이파이 3벌 금지 — 비용과 앵커링).
- **평가·검수 하네스 기준은 사용자가 추후 제공한다.** 받기 전까지 B-3 비평 페르소나는 기존 기본(UX 관점 / 개발 호환성 관점)으로 두고, 받은 기준은 `brief.md` 판단기준 원장에 `사람-원문` 소스로 넣은 뒤 B-3 비평 프롬프트와 C/V 판정에 동시에 투입한다.
- 선택은 여전히 사람이 한다. 평가 하네스의 점수는 "제시 재료"다.

**★ 베이스라인 고정 — 눈가림만으로는 축이 갈리지 않는다.**

# 보조 방법론 (출처: feat/yj1 stage-b-diverge.md)


목적: 무엇을 만들지는 정해졌으나 어떻게 만들지에 정답이 하나가 아닐 때, 축을 분리해 병렬로 발산하고 근거 있게 수렴한다.

> **이번 프로젝트에서 실제로 무슨 축을 골랐고 무엇을 선택했는지는 여기 없다.** 전부 `design/<project-id>/decisions.md`에 있다 — 방법론 파일에 결정 결과를 쓰면 다음 프로젝트가 그 답을 그대로 베낀다.

## 1. 독립 축 식별

축을 먼저 나누지 않고 화면 전체(풀스크린 시안 A vs B)를 통째로 비교하면, 무엇 때문에 선택했는지 뒤섞인다(confound) — "A가 좋다"고 했을 때 그게 색 때문인지 정보밀도 때문인지 알 수 없다. 반드시 서로 독립적인 축으로 쪼갠 뒤 축마다 후보를 만든다.

**축이 독립인지 확인하는 법**: 축 X의 선택을 바꿨을 때 축 Y의 선택도 따라 바뀌어야 한다면, 둘은 독립이 아니다 — 하나로 합치거나 다시 쪼갠다.

자주 나오는 축의 종류(그대로 쓰라는 목록이 아니라, 쪼갤 지점을 찾는 힌트):

- 진입 화면의 1차 프레임 — 어떤 정보 축을 먼저 보여줄 것인가
- 정보 밀도 — 한 번에 펼칠 것인가, 요약하고 탭해서 확장할 것인가
- 표현 방식 — 텍스트로 나열할 것인가, 시각 기호로 압축할 것인가

## 2. 후보 생성

축마다 최소 2개 후보를 **병렬로** 스케치(로우파이 설명 또는 실제 프레임 2개)한다. 사람의 순차적 스케치를 흉내내지 않고, 후보들을 동시에 만들어 비교 기준을 고정한 채 본다.

## 3. 비교·수렴 — 최소 2개 페르소나 교차 비평

- **UX 관점**: 실제 사용자(요구사항의 유저스토리)의 목표 달성 속도로 평가. "목표 행동까지 탭 수가 몇 번인가?"
- **개발호환성 관점**: Figma 산출물이 "AI 에이전트가 읽고 이어서 작업할 수 있는 데이터"인지로 평가. 컴포넌트화 가능한 구조인가, 상태(빈 상태/로딩/에러)를 변형으로 감당할 수 있는가.

두 관점이 충돌하면 어느 쪽을 왜 우선했는지까지 `decisions.md`에 남긴다.

## 4. 기록

축별 후보·비교근거·선택·남은 트레이드오프는 전부 `design/<project-id>/decisions.md`에 쓴다. 탈락한 후보를 지우지 않는다 — C단계에서 "방향 자체가 틀림"으로 회귀했을 때 되돌아올 지점이 된다.
