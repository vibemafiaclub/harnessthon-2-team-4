- 프로젝트 `brief.md` 「판단기준 원장」 행은 **합격선**(이 프로젝트에서 어디부터 실패인가 — 숫자·구체 조건)만 담는다. 이것만 사람이 승격한다. 행 형식: `[C-n] <렌즈 항목명> — 실패선: <조건>`.

- iceberg AS/CX는 `사람-해석`(설계자 정의) — 마찬가지로 후보.
- **`OBSERVE` 판정 상태**: 렌즈에는 걸렸지만 이 프로젝트에 확정 합격선이 없는 항목은 `SKIP`이 아니라 `OBSERVE + 무엇이 어떻게 보이는지 + 위치`로 기록한다. OBSERVE는 FAIL이 아니므로 라운드 카운터를 쓰지 않고, 사람 승격 질문의 원석(피드백 원문 로그 → 원장 후보)이 된다. 이렇게 하면 원문 없는 렌즈도 관찰력을 유지한다.
- **A단계로 내려보내는 렌즈**(이진·구조적으로 셀 수 있음 → 소스 `실측`, 사람은 "이 규칙을 켤 것인가"만 답): 메인 컬러 사용 범위(Accent 바인딩 노드 수 − 주요 행동 노드 수 = 0), 압축 표기(`^\+\d+$` 텍스트 0), 기본 상태 라벨(목록 항목 라벨 부착 비율 < 100%), 이진 선택(형제 버튼 2개가 가능/불가 쌍이면 실패), 색 범례(색 점을 쓰는 프레임에 범례 노드 존재), 어포던스(리액션 있는 텍스트에 stroke/fill/underline 중 하나). 나머지는 C에 남는다.

## C단계 — 미적·게슈탈트 판단

A단계 통과 후, **반드시 스크린샷을 렌더해서** 판단한다. 개별 수치가 다 맞아도 전체가 어색할 수 있고, 그게 이 단계가 따로 있는 이유다.

**스크린샷 전달 배선** — Agent 프롬프트는 텍스트만 담으므로 이미지를 직접 넣을 수 없다.
→ 스크린샷을 `<산출물루트>/renders/r<라운드>.png`로 **저장하고, Agent에는 절대경로만 준다**(Agent가 Read로 읽는다).
→ 렌더 툴이 없으면 사람에게 수동 export를 요청한다. **C단계는 자동 실행이 원리적으로 보장되지 않는 유일한 단계다** — 그래도 스크린샷 없이는 성립하지 않으므로 이 경로는 반드시 확보한다.

### 검증자 격리 — 이 단계의 핵심 장치

「검증 Agent 배선」 ①~④를 전부 적용한다. 그 위에 입력을 제한한다.

| 주는 것 | 주지 않는 것 |
|---|---|
| 스크린샷 절대경로 | `decisions.md` — 어떤 후보를 왜 골랐는지 |
| `brief.md` 「판단기준 원장」의 **확정 상태 행만** (후보 제외) | 제작 과정·설계 의도·대화 이력 |
| 렌즈 전부(이 파일 하단 판단 항목·AS·CX·대립 리뷰 절차) + 원장의 확정 합격선 행 | 파일 탐색 권한 (스스로 찾아 읽는다) |
| A단계 판정 결과 **요약만** — 어느 항목이 PASS/SKIP인지 | A단계가 본 노드 트리·기준값 원본 |

왜: 제작 의도를 아는 검증자는 탈락 항목에서 **"의도가 이랬으니 괜찮다"로 자기변호**한다. 검증자의 무지가 검증력이다. 실제 사용자도 의도를 모르고 화면을 보므로, 검증 조건이 실사용 조건과 같아진다.

A단계 결과 요약만 주는 이유: C-3은 "수치는 A-3이 봤다"를, C-6은 "존재 여부는 A-6이 봤다"를 전제한다. A-6이 SKIP된 줄 모르면 검증자는 빈 상태가 있는지도 모른 채 C-6을 판정하거나 A-6과 중복 탈락시킨다. 항목별 PASS/SKIP만 주면 **설계 의도는 섞이지 않으므로 격리는 유지된다.**

### 판정 규칙

각 항목을 `PASS` / `FAIL + 무엇이 어떻게 보이는지 + 스크린샷 상 위치` / `OBSERVE(합격선 미승격 — 관찰만)` / `SKIP(렌즈에도 없음)`으로 답한다.

- **합격선이 `brief.md`에 없는 항목은 PASS/FAIL을 내지 않는다.** 렌즈에 걸리면 OBSERVE로 관찰만 적는다. 기준 없이 PASS/FAIL을 내면 그게 곧 추측이다.
- "개선 여지가 있다" 같은 중립 표현을 쓰지 않는다 — 판정이 아니라 회피다.
- **전 항목 SKIP은 통과가 아니라 판정 불가.** 정지하고 사람에게 기준을 요청한다 — 요청 사유에 기준이 없는 항목의 이름(C-n)을 나열한다(절대 규칙 5).

**「판단기준 원장」 ↔ 렌즈 매핑**: 원장의 합격선 행에 `C-1`~`C-7`·`C-X`·`C-S` 태그를 붙인다(상단 항목 지도). 태그가 없으면 어느 항목에 걸리는지 알 수 없고, "여기 없는 기준으로 탈락시킬 수 없다"는 규칙과 결합하면 그 항목은 영구히 PASS가 된다.

### 체크 항목

렌즈 정의는 이 파일 하단 「판단 항목 상세」(yj1)·「정량 미학 AS」·「핵심경험 CX」에 있다. 태그별 묶음은 상단 「항목 지도」. 여기서는 중복 기술하지 않는다.

### 사람 판정과 오버라이드 재유입 — 우로보로스 고리

C 검증 Agent의 판정은 제안이다. 최종 판정은 사람이 내린다(절대 규칙 2). **사람이 Agent 판정을 뒤집는 사건(오버라이드)은 버리는 게 아니라 다음 라운드의 판단기준 원석이다.**

1. **기록**: `decisions.md`의 「오버라이드 로그」에 남긴다 — 항목 / Agent 판정 / 사람 판정 / 사람이 말한 이유 **원문**.
2. **증류**: 그 이유에서 "판정을 가른 기준"을 뽑아 `brief.md` 「판단기준 원장」에 **후보**로 기입한다 — 0-2의 확인 경로와 동일하게 태생이 확인 대기다.
3. **확인·승격**: 디자이너가 승격하면 다음 C 재검과 다음 라운드부터 검증 Agent에게 그 기준이 전달된다 — 승격된 기준은 원장의 확정 행이 되므로 기존 배선 그대로 흘러간다.
4. ★ **완화 방향 자동 증류 금지.** "사람이 PASS로 뒤집었으니 이 항목은 앞으로 덜 엄격하게 보자"를 에이전트가 스스로 쓰지 않는다 — 통과가 목적이 되는 순간 검증이 무너진다. 완화든 강화든 승격은 사람만 한다.

이 고리가 있어야 라운드가 반복될수록 검증 Agent의 판정이 그 디자이너의 안목에 수렴한다 — **평가의 출력이 차세대 기준의 입력이 된다.**

# 판단 항목 상세 (출처: feat/yj1 stage-c-aesthetic — 라벨 금지, 합격선 필수)


각 항목은 **"무엇을 보면 그렇게 판단하는가"까지** 적혀야 한다. "위계가 좋아야 한다" 같은 라벨만 있으면 에이전트가 판단할 수 없고, 매번 다른 답이 나온다.

좋은 예 — 여백 리듬 항목의 서술:
> 카드 내부 패딩과 카드 사이 간격이 같으면 카드 경계가 뭉개져 보인다(게슈탈트 근접성). 카드 사이 간격이 내부 패딩보다 **눈에 띄게 커야** 카드 단위가 분리돼 보인다 → 프로젝트 합격선: 내부 16 vs 사이 12는 실패, 내부 16 vs 사이 24는 통과.

나쁜 예:
> 여백이 일관되어야 한다.


## 판단 항목

- [ ] **섹션 간 색온도·조명 일관성** — 같은 화면 안에서 배경/표면의 명도 단계가 임의로 튀지 않는가. 특히 상태색 여러 개를 나란히 놓았을 때 하나만 채도가 튀면 팔레트를 벗어난 것이다.
- [ ] **시각적 위계가 한눈에 읽히는가** — 스크린샷을 2초만 보고 눈이 가는 곳이, 요구사항이 정한 **"지금 사용자가 처리해야 할 것"**과 일치하는가.
  - **실패: 상시 요소가 1순위를 가져간 경우.** FAB·헤더 버튼처럼 **항상 같은 자리에 있는 것은 그 자체로 정보가 없다.** 화면에서 가장 채도 높은 요소가 그것이면, 정작 급한 항목이 뒤로 밀린다.
  - **실패: 그룹 헤더가 항목보다 약한 경우.** 목록이 상태별로 묶여 있는데 섹션 이름이 보조 텍스트 크기·색이면, 사용자는 묶임 자체를 못 읽고 평평한 목록으로 본다.
  - 통과 조건: ① 가장 급한 그룹의 **헤더가 본문만큼 진하다** ② 그 그룹의 상태 표시가 화면에서 **가장 대비가 높다** ③ 상시 버튼은 그보다 약하다(채움 → 테두리로 낮추는 것으로 대개 해결된다).
- [ ] **여백 리듬의 체감 일관성** — 수치상 그리드를 지켜도 시각적으로 리듬이 느껴지는가. 위 근접성 원리 참고.
- [ ] **정보 밀도 번잡함 여부** — 한 단위(카드/행/섹션)에서 시선이 멈추는 지점이 몇 개인가. 상한은 B단계에서 고른 밀도 축과 정합해야 한다.
- [ ] **메인 컬러의 사용 범위** — 브랜드 메인 컬러가 반복 요소(아바타, 리스트 마커, 칩, 카드 배경)까지 칠해져 있으면 **강조가 강조로 읽히지 않는다.** 판단법: 스크린샷에서 메인 컬러가 칠해진 요소를 센다. 그 화면의 주요 행동(대개 1~2개) 외의 것에 쓰였으면 실패.
  - 통과: 메인 컬러가 FAB·주요 버튼에만. 반복 요소는 중립색.
  - 실패: 아바타 18개가 전부 메인 컬러 → 화면이 한 색으로 덮여 어디를 눌러야 할지 사라짐.
- [ ] **반복 요소의 색이 정보인가 장식인가** — 아바타·태그·리스트 마커처럼 여러 번 반복되는 요소의 색은 **무언가를 식별해야** 한다. 두 가지 실패가 대칭으로 존재한다:
  - **장식 실패**: 반복 요소를 전부 브랜드색으로 칠함 → 화면이 한 색으로 덮이고 강조가 사라진다.
  - **회피 실패**: 그게 싫어서 전부 무채색으로 바꿈 → 정보가 사라지고 화면이 죽는다. **무채색은 안전한 답이 아니라 정보를 포기한 답이다.**
  - 통과 조건: 그 색이 **무엇을 구분하는지 한 문장으로 말할 수 있다.** (사람별 고정색 / 분류별 색 / 상태별 색)
  - 여러 색을 쓸 때는 **채도와 명도를 같은 대역으로 묶는다.** 색상(hue)만 다르고 채도·명도가 통일되면 구분은 되면서 산만해지지 않는다. 하나만 채도가 높으면 그게 강조로 오인된다.
  - 색에 매핑할 정보가 정말 없다면 그때는 무채색이 맞다 — 다만 "없다"를 먼저 확인해야지, 색을 피하려고 무채색을 고르면 안 된다.
- [ ] **상태 구분이 대비 강도로도 벌어져 있는가** — 진행 단계를 나타내는 상태들이 **색상(hue)만 다르고 대비 강도가 같으면** 어느 것이 급한지 읽히지 않는다. 색맹 사용자에게는 아예 구분이 사라진다.
  - 판단법: 상태 배지들을 나란히 놓고 봤을 때 **시선이 가는 순서가 실제 긴급도 순서와 일치하는가.**
  - 끝난 상태(완료·보관·지난 것)는 눈에 띄게 약해야 하고, **배지만이 아니라 그 항목 전체가 물러나야 한다** — 배지 하나만 흐리게 하고 카드는 그대로면 목록에서 여전히 같은 무게로 보인다.
  - 실패 예: 대기중·확정됨·완료가 모두 같은 명도의 옅은 배경 + 같은 진하기 텍스트.
- [ ] **압축 표기의 자립성** — `+2`, `외 3` 같은 줄인 표기는 **그 자체로 "무엇이 몇 개인지"가 읽혀야 한다.** 판단법: 주변 맥락을 가리고 그 라벨만 봤을 때 의미를 말할 수 있는가.
  - 실패: `+1` (무엇이 1인지 없음)
  - 통과: `외 1곳`, `그룹 2개 더`
- [ ] **기본 상태를 표시하고 있지 않은가** — 목록의 **모든** 항목에 상태 라벨이 붙어 있으면 그건 정보가 아니라 노이즈다. 정상·기본에 해당하는 상태는 **표시하지 않고**, 주의가 필요한 예외만 표시한다.
  - 판단법: 라벨을 다 지웠다고 상상했을 때 사용자가 잃는 정보가 있는가. 없으면 그 라벨은 지워야 한다.
  - 실패: 5명 중 3명에 "회신완료", 2명에 "대기중" → 5줄 전부 라벨이라 정작 급한 2명이 안 튄다.
  - 통과: 응답한 사람은 무표시, 미응답만 표시 + 총계는 섹션 헤더에 한 줄("5명 · 3명 회신").
- [ ] **상태 라벨이 사용자 언어인가** — 상태 이름을 시스템 관점의 조어로 만들지 않는다. 가능하면 **"지금 누구 차례인지"**가 읽히게 쓴다.
  - 실패: "확정앞둠"(조어 예) — 한국어로 어색한 조어이고, 누가 무엇을 해야 하는지 안 보인다.
  - 통과: "내 차례" / "상대 차례" / "끝남" 처럼 지금 누가 무엇을 해야 하는지가 드러나는 말.
- [ ] **파괴적 행동이 구분되어 있는가** — 되돌릴 수 없는 행동(삭제·취소·탈퇴)은 ① **전용 색**(경고색과도 구분한다 — 경고는 "서두르세요", 파괴는 "되돌릴 수 없다") ② **확인 단계**를 갖는다.
  - 실패: 삭제가 다른 보조 링크와 같은 색이고, 누르면 바로 지워진다.
  - 확인 단계의 문구는 **무엇이 사라지는지 명시**한다. "삭제하시겠습니까?"보다 "이 날짜 후보를 삭제할까요?"가 낫다.
- [ ] **이진 선택에 버튼을 두 개 두지 않았는가** — 하나를 고르면 나머지가 자동으로 결정되는 선택은 **컨트롤 하나**로 표현한다. 버튼 2개는 선택지가 3개 이상일 때의 형태다.
  - 실패: 날짜마다 `[가능][불가]` 두 버튼 → 항목 수만큼 버튼이 두 배로 늘고 화면이 기계적으로 보인다.
  - 통과: 체크 하나. 체크=가능, 미체크=불가.
  - 부수 효과: 응답 마찰이 줄어 응답률이 오른다. 선택지를 늘릴수록 미응답이 는다.
- [ ] **색으로 부호화했으면 범례가 있는가** — 색·점·배지로 분류를 표현했다면, 그 색이 무슨 뜻인지 **같은 화면 안에서** 알 수 있어야 한다. 눌러야만 알 수 있으면 조망 화면인데 조망이 안 되는 것이다.
  - 실패: 캘린더에 색 점만 찍혀 있고 무슨 색이 무슨 분류인지 어디에도 없음.
  - 통과: 부호를 쓰는 영역 근처에 범례가 있고, 범례의 표시가 실제 표시와 **똑같은 형태**다(점이면 점, 배지면 배지).
- [ ] **같은 행동으로 가는 입구가 둘 이상인가** — 한 화면에 같은 곳으로 가는 버튼이 둘이면 사용자는 "뭐가 다르지?"를 먼저 묻는다. 그 순간 둘 다 못 누른다.
  - 판단법: 각 버튼이 **서로 다른 결과**로 이어지는지 말할 수 있는가. 못 하면 하나를 지운다.
  - 특히 **빈 상태**에서 흔하다 — 할 일이 하나뿐인데 상시 FAB와 본문 CTA가 같이 있는 경우. 빈 상태에서는 상시 버튼을 지우는 쪽이 맞다.
- [ ] **누를 수 있는 것이 눌러 보이는가** — 보조 행동을 맨 텍스트로 두면 안내 문구와 구분되지 않는다.
  - 실패: 본문 설명과 같은 크기·색의 텍스트인데 실제로는 링크.
  - 통과: 테두리·배경·밑줄 중 하나 이상으로 눌리는 것임이 표시된다. 색만 다르게 하는 것으로는 부족하다(색맹).
- [ ] **더미 데이터가 현실 분포를 따르는가** — 목업 데이터가 반복적이면 실제보다 나빠 보이고, 그 화면의 진짜 문제를 가린다.
  - 실패: 아바타 이니셜이 `김·김·김`처럼 같은 값 반복, 모든 항목이 같은 길이.
  - 통과: 이름·길이·개수가 실제 데이터처럼 흩어져 있다. **긴 이름과 짧은 이름을 섞어 레이아웃이 견디는지도 함께 확인된다.**
- [ ] **클리셰/AI슬롭 여부** — 과도한 그라디언트, 근거 없는 그림자 남발, 의미 없는 장식용 블롭/추상 도형, 이유 없는 이모지. 도메인 맥락상 추가로 금지할 클리셰는 `brief.md` 판단기준 원장.
- [ ] **엣지케이스의 실제 완성도** — 빈 상태/로딩/에러가 텍스트 한 줄로 방치돼 있으면 실패. 무엇을 하면 채워지는지 안내 + 그 행동으로 이어지는 경로가 있어야 한다.

# 정량 미학 AS1~AS6 (출처: iceberg-1234)


> 참조: `rules/design-principle.md`

"안정적으로 보인다"를 **측정 가능한 항목**으로 분해한다. "눈으로 본다"만으로는 재현성이 없다.

| ID | 검증 | 측정 방법 | 실패 기준 |
|---|---|---|---|
| AS1 | **정렬 축 수** | 화면 내 서로 다른 x 시작점의 개수를 센다 | 4개 초과 → 산만함 (Major) |
| AS2 | **위계 대비** | 인접 타이포 단계 간 크기 비율 | 1.15배 미만 → 위계 불명확 (Major) |
| AS3 | **리듬 일관성** | 블록 간 간격의 종류 수 | 4종 초과 → 리듬 붕괴 (Major) |
| AS4 | **시각 무게 균형** | 상/하, 좌/우 영역의 잉크 밀도(비배경 픽셀 비중) 비교 | 한쪽이 3배 초과 → 기울어짐 (Minor, 의도적이면 허용) |
| AS5 | **여백 방향성** | 요소 주변 여백이 소속을 명확히 하는가 (근접성 원리) | 그룹 내 간격 ≥ 그룹 간 간격 → 소속 모호 (Major) |
| AS6 | **강조 요소 수** | 화면당 시선을 강하게 끄는 요소(고채도/대형/고대비) 개수 | 3개 초과 → 초점 분산 (Major) |

### 측정 절차

1. `get_screenshot`으로 화면을 렌더한다.
2. AS1·AS3·AS5는 `use_figma`로 노드 좌표·간격을 조회해 **수치로** 확인한다.
3. AS2는 `_system/brief.md`의 T 타이포 스케일에서 인접 단계 비율을 계산한다.
4. AS4·AS6은 스크린샷을 관찰하되, **어떤 요소가 근거인지 지목**한다.

🔴 **AS 위반이 A단계 IC 위반과 중복되면 IC 쪽을 우선한다** (IC가 더 정밀한 측정이다). 중복 카운트하지 않는다.

# 핵심경험 경험 검증 CX1~CX5 (출처: iceberg-1234)


> A단계 CE1~CE7이 **구조**를 봤다면, 여기서는 **실제 경험**을 본다.

| ID | 검증 | 방법 | 실패 기준 |
|---|---|---|---|
| CX1 | **3초 테스트** | 핵심 화면 스크린샷을 보고, 3초 안에 "이 화면에서 무엇을 할 수 있는지" 파악되는가 | 파악 불가 → Blocker |
| CX2 | **추적성 실물 확인** | 요구 계약 추적성 매트릭스의 "근거 요소" nodeId가 스크린샷에 **실제로 보이는가** | 표에는 있는데 화면에 없음 → Blocker (허위 기록) |
| CX3 | **플로우 완결성** | 요구 계약 screens의 Userflow대로 스크린샷을 따라가면 요구 계약 핵심경험의 성공 조건에 도달하는가 | 중간에 끊김 → Blocker |
| CX4 | **성공 피드백** | CE 성공 조건 달성 시 유저가 "됐다"를 확인할 수 있는 시각적 신호가 있는가 | 없음 → Major |
| CX5 | **인접 경험 반영** | 요구 계약 핵심경험의 인접 경험(직전/직후/대체)이 요구한 진입점·이탈점이 화면에 있는가 | 없음 → Minor (Primary CE에 필수면 Major) |

🔴 **CX2는 이 하네스의 핵심 안전장치다.** 추적성 매트릭스에 기록만 하고 실제로 구현하지 않은 경우를 잡는다. **nodeId와 스크린샷을 반드시 대조**한다.

🔴 **A단계 보고의 CE1이 실패(추적성 부재)면 CX1~CX5는 `검증 불가`다.** 축 ③ 전체가 `검증 불가`가 되고 최종 판정은 FAIL이다.

**성공 조건이 판정 불가인 경우**: 요구 계약 핵심경험의 성공 조건이 내면 상태로 쓰여 있으면(예: "만족감을 느끼면") CX3·CX4를 판정할 수 없다. 이 경우 **요구 계약(핵심경험 정의)으로 반환**하여 관찰 가능한 조건으로 재작성한다.

# 대립적 리뷰 — Critic ⇄ Advocate → PM (출처: iceberg-1234)

> dev 검증자 격리(신규 컨텍스트 Agent)와 결합한다: Critic·Advocate는 **각각 별도 신규 컨텍스트 Agent**, PM 판결은 사람 또는 master. 세 역할을 한 세션이 순서대로 연기하는 것은 격리가 아니다.


> 참조: iceberg-1234/harness의 stage-7-judge-design 패턴

단일 체크리스트로 자기 작업을 검토하면, 결함을 무의식적으로 용납한다. 이 단계는 **세 역할을 순서대로 수행**한다:

### 역할 1: Critic (비평가)

스크린샷과 노드 데이터를 보고 **문제만** 찾는다. 이 역할은 칭찬하지 않는다.

각 finding은:
- **evidence**: 스크린샷에서 보이는 구체적 현상 또는 노드 속성 값
- **invariant**: 위반한 규칙 ID (CS1~CS8, IC1~IC6, 체크리스트 1~10, HIG-*)
- **severity**: Blocker / Major / Minor
- **target**: 어떤 화면의 어떤 요소

### 역할 2: Advocate (변호인)

Critic의 각 finding에 대해:
- **rebut**: 새로운 증거(다른 스크린샷, 노드 속성)로 반박. 또는
- **concede**: 반박할 증거가 없으면 인정.

"의도된 디자인이다"는 증거 없는 반박이다. **새로운 측정값**이 필요하다.

### 역할 3: PM (제품 책임자 판결)

Critic과 Advocate의 주장을 읽고 각 항목을 판결한다:
- **verdict**: fix / accept / defer
- **action**: fix일 때 구체적 수정 내용
- **escalate**: 규칙 자체가 문제면 `brief.md` 기준값의 해당 항목 재검토 요청

# Source-Fidelity 비교 (출처: iceberg-1234)


> 참조: iceberg-1234/harness의 stage-7-judge-design source-fidelity 패턴

생성된 화면이 **같은 제품의 확장처럼 보이는지** 검증한다. 비교 기준은 아래 우선순위로 정한다:

| 우선순위 | 비교 기준 | 판정 의미 |
|---|---|---|
| 1 | 기존 Figma 소스 화면 | "같은 앱의 다른 화면"으로 읽히는가 |
| 2 | `reference-review.md`의 레퍼런스 관찰 결과 | 카테고리 관습에서 벗어나지 않는가 |
| 3 | 없음 | `해당 없음 — 비교 기준 없음` |

`get_screenshot`으로 소스 화면(또는 M막 레퍼런스)과 생성 화면을 나란히 렌더하고, 아래 5개 축으로 비교한다:

| 축 | 확인 기준 | 허용 범위 |
|---|---|---|
| 색상·조명 언어 | 소스와 같은 색온도/채도 범위에 있는가 | 같은 팔레트의 확장이면 Pass |
| 밀도·리듬 | 블록 간 간격, 행 높이, 여백 비율이 비슷한가 | 같은 그리드/스케일이면 Pass |
| 형태·컴포넌트 언어 | 코너 반경, 카드 스타일, 아이콘 언어가 일치하는가 | 같은 디자인 시스템이면 Pass |
| 탐색·플랫폼 관습 | 네비게이션 패턴이 소스와 동일한가 | 같은 패턴이면 Pass |
| 전체 인상 | 스크린샷만 봤을 때 "같은 앱의 다른 화면"으로 읽히는가 | 직관적으로 Yes면 Pass |

**비교 기준이 전혀 없으면 `해당 없음 — 비교 기준 없음`으로 기록한다.** 날조하지 않는다.
