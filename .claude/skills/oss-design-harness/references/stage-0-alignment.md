# 0단계 — 요구사항 정렬 방법론 (원장 인터뷰)

> **합병 노트(2026-09-05)**: 이 파일은 `dev`(운영 뼈대)와 `feat/yj1`(판정 디테일), iceberg-1234 하네스(3축 원칙·추적성·정량 미학)를 합친 것이다. 출처를 각 절 머리에 적었다. 프로젝트 값(색·화면명·인명)은 여기 없다 — `docs/projects/<id>/`와 `design/<id>/`에 있다.

## 0단계 — 요구사항 정렬 (원장 인터뷰)

무엇을 만들지 자체가 불확실할 때. 이 단계의 산출물은 "느낌"이 아니라 **원장**이다 — `brief.md`의 필수 섹션이 전부 감사 가능한 상태로 해소되어야 끝난다.

**수행 주체: 메인 세션이 직접 한다.** 서브에이전트에 위임하지 않는다 — 0단계는 사람과 여러 턴 왕복해야 하고, 서브에이전트는 사람과 대화할 수 없다. 위임하면 조용히 실패한다.

**원칙: 자극은 표상이 아니라 체험이어야 한다.**
라벨형 질문("모던한 게 좋으세요, 클래시컬한 게 좋으세요?")은 상대와 어휘 이해가 다를 수 있어 무의미하다. 구체 레퍼런스를 보여주고 반응을 받는다. IA·플로우도 다이어그램으로 보여주지 않는다 — 다이어그램도 또 하나의 전문 표기법이라 같은 함정이다.

**제시 매체** — 터미널에는 이미지를 띄울 수 없다.
- **TODO**: 무엇으로 보여줄지 (Artifact 발행 / 로컬 HTML 작성 후 열게 하기 / URL 목록 제시)
- "클릭 가능한 로우파이"는 화면을 만들 수 있어야 만들 수 있다. Figma 미인증이거나 제작 전이면 **시나리오 내러티브**로 대체한다.

### 0-1. 원장과 수렴 판정 — 우연에 의한 수렴 금지

`brief.md` 맨 위의 「수렴 판정표」가 원장이다. 필수 섹션 9개(target / 화면 목적·사용자 / 화면 요소 목록 / 시각 언어 / 구조·워크플로 / 인터랙션 품질 / 거부할 가정 / A단계 기준값 / C단계 판단기준) 각각이 다음 넷 중 하나로 해소되어야 0단계가 끝난다.

| 해소 클래스 | 뜻 | 요건 |
|---|---|---|
| **사람** | 디자이너·클라이언트가 직접 말했다 | 반응 원문이 근거로 연결되어야 한다 |
| **실측** | 기존 Figma 라이브러리·파일에서 읽었다 | 증거 경로(변수·스타일 이름)를 남긴다. 무제한 탐색 금지 — 대상 파일 안에서만 |
| **가정** | 안전한 기본값으로 닫았다 | 근거 서술 필수. **사람이 명시적으로 생략·위임을 선택한 경우에만** — 에이전트가 스스로 기본값으로 닫는 것은 금지다. 전문가의 미답을 기본값으로 닫으면 안목 추출이 무효화된다 |
| **차단** | 사람 권한이 필요한데 아직 답이 없다 | 미해결 결정의 이름을 명시하고 **멈춘다** |

- **완료 = 차단·충돌·미기입이 0이고 나머지가 전부 사람/실측/가정.** "반응을 몇 개 받았는가"는 완료 조건이 아니다 — 열린 갭이 소진됐는가가 조건이다.
- **충돌 처리**: 같은 키에 값이 둘이면 소스 우선순위(사람 > 실측 > 가정)로 푼다. 같은 급끼리 충돌하면 지어내서 고르지 않고 충돌 상태로 표시해 사람에게 보여준다.
- 갭의 우선순위 = 판정표의 행 순서. 항상 첫 번째 열린 갭부터 조준한다.

### 0-R. 레퍼런스 조사·검수·추출 — 인터뷰 앞의 필수 절차

레퍼런스는 앱 이름이 아니라 **출처가 확인된 화면·상태·흐름** 단위로 다룬다. 인기·설치 수는 배경 정보이며 디자인 채택 근거가 아니다. 이 절차의 계약은 `templates/reference-review.md`다. 기존 0-2의 사람 인터뷰와 승격 권한은 그대로 유지한다.

**하네스 유지보수·레퍼런스 조사만 요청한 경우**: Figma 제작 세션을 시작하지 않는다. 조사 보고서와 절차·템플릿을 작성하며 G-3/G-4, B 후보 생성, A/C 제작 검증은 실행하지 않는다. 프로젝트 디자인의 승인·완료로 보고하지 않는다. 실제 디자인 세션에서는 모드에 해당하는 게이트를 그대로 적용한다.

1. **조사 질문 고정**: 열린 갭과 사용자가 수행할 과업을 적는다. 같은 과업의 화면끼리 비교한다. 다른 과업의 레퍼런스는 비교 순위에 섞지 않고 보조 자료로 표시한다.
2. **소싱·동일성 확인**: 공식 사이트·앱스토어에서 제품명, 개발사, 패키지/앱 ID, URL, 열람일, 확인 가능한 버전·플랫폼을 기록한다. 블로그는 발견 경로 또는 보조 관찰로 표시한다. 접근 실패·동명이인·오래된 버전은 사실대로 남긴다.
3. **증거 확보**: 원본 전체 화면과 추출 영역을 연결한다. 공식 소개문, 스토어 홍보 화면, 직접 실행 화면, 직접 실행 흐름을 구별한다. 이미지가 없으면 시각 품질은 미검증, 클릭하지 않았으면 인터랙션은 미검증이다. 스크린샷으로 토큰·폰트·간격·컴포넌트 구조를 실측했다고 주장하지 않는다.
4. **독립 증거 검수**: 수집자와 다른 신규 컨텍스트 검수자가 출처·화면·주장의 일치를 확인한다. 「검증 Agent 배선」의 탐색 제한·수정 금지·격리 수준 기록을 적용한다. 지정된 증거와 조사 질문만 주고 수집자의 추천·사람 선호·decisions.md는 주지 않는다. 출력은 주장별 `SUPPORTED / CONTRADICTED / UNVERIFIED`와 근거 위치다. 검수자를 사용할 수 없으면 `미실시`로 남기며 스스로 검수 완료를 선언하지 않는다.
5. **사람에게 한 개씩 제시**: 0-2의 원문 반응·5축 질문을 실행한다. 에이전트는 채택/보류/제외를 **추천**할 수 있지만, 최종 선택은 사람이 한다. 제품 전체 채택과 개별 요소 채택을 혼동하지 않는다. 이유와 적용 범위를 원문으로 남긴다.
6. **요소 추출**: 채택한 범위에서 관찰 → 작동 원리 가설 → 우리 과업에 적용할 방식 → 가져오지 않을 것 → 필요한 상태 → 검증 방법을 적는다. 산출물은 B 후보가 아닌 패턴·기준 후보다. 신규 판단기준은 0-2에서 사람이 별도로 승격해야 한다.
7. **추적 연결**: `REF → 증거 → 사람 반응 → 선택 → PATTERN → CRITERION → 화면/컴포넌트 → A/C/흐름 검증`의 ID를 기록한다. 제외 항목도 보존하고 재검토 조건을 남긴다. 변경은 이력 추가 방식으로 기록한다.

**두 종류의 상태를 분리한다.** 증거 검수 통과는 디자인 채택이 아니다. 사람의 취향상 채택도 미확인 기능을 사실로 만들지 않는다. 증거 부족 항목을 제외로 자동 변환하지 말고 보류 사유를 남긴다. 자동 총점·가중치·채택 커트라인은 만들지 않는다.

**0-R 인수인계 조건**: 다음 단계가 사용하는 항목마다 증거 범위, 독립 검수 결과, 사람의 선택과 이유, 적용 범위, 패턴 ID가 있어야 한다. 정성 기준은 별도 승격 기록까지 필요하다. 부족하면 해당 의존 항목만 `BLOCKED`로 기록한다. 관계없는 조사·문서화는 계속할 수 있다. 미답·검수 미실시를 승인으로 간주하지 않는다. 참조가 없는 사람 직접 요구는 그 원문을 별도 근거로 사용할 수 있다.

**이후 단계 연결**: B에는 승인된 추출 패턴과 확정 기준만 전달한다. 제작 기록에는 적용된 패턴 ID와 실제 노드 ID를 매핑한다. A는 실제 노드 속성을 검사하고, C는 확정 기준과 제작 렌더만 받는다. C에 경쟁 앱 추천 사유를 넘기지 않는다. 실제 흐름의 유효성은 클릭·상태 전환 증거로 별도 확인한다.

### 0-2. 레퍼런스 인터뷰 루프 — 5축 대비 질문과 승격

1. **열린 갭 확인** — 판정표에서 첫 번째 미해소 섹션을 본다.
2. **그 갭을 줄일 레퍼런스 1개**를 0-R의 증거·검수 기록과 함께 제시한다. 한 번에 하나씩 — 여러 개를 한꺼번에 주면 상대가 비교 모드로 들어가 개별 반응이 흐려진다. 증거 범위와 미검증 사항을 함께 보여 준다.
3. 자유서술 반응("좋다/싫다 + 왜")을 받고 **원문 그대로** 기록한다. 요약 금지 — "산만하다"와 "정보가 많아 부담된다"는 다른 기준을 가리킨다.
3-b. **되묻기**(「디자인 프로세스」의 되묻기 규칙): 반응에서 나온 단어를 같은 축의 유사 레퍼런스 2~3개로 다시 시험한다. 되묻기 기록이 없는 후보는 6의 승격 질문으로 가지 않는다.
4. **5축 대비 질문**으로 심화한다 — "이 레퍼런스에서 우리가 **무엇을 복사하고 무엇을 피해야** 하나요?"를 다섯 축으로 나눠 묻는다: ① 표면 룩앤랭귀지 ② 워크플로·구조 ③ 인터랙션 품질 ④ 원하는 결과 ⑤ 거부할 가정. 라벨을 묻는 게 아니라 눈앞의 구체물에 대한 대비를 묻는 것이므로 표상 금지 원칙과 충돌하지 않는다. 다섯 축의 답이 원장 필수 섹션 2·4·5·6·7에 그대로 꽂힌다.
5. **증류**: 반응에서 판단기준 후보를 뽑아 「판단기준 원장」에 **후보 상태로** 기입한다. 후보는 태생이 확인 대기다.
6. **확인·승격**: 후보를 디자이너에게 보여 승격/기각을 받는다. **승격된 것만 판단기준(확정)이 된다.** 기각돼도 반응 원문은 보존한다. 증류는 에이전트가 하되 승격 권한은 사람에게만 있다 — 이것이 "에이전트가 판단기준을 채우면 오염"의 기계적 구현이다.
7. 판정표를 갱신하고 1로 돌아간다. 수렴하면 종료.

### 0-3. 스톨 감지 — 개수가 아니라 갭을 조준한다

다음 신호가 보이면 루프가 헛돌고 있는 것이다.
- 디자이너의 반응이 같은 뜻의 generic 답 반복("글쎄요, 그냥 좋아요")
- 인터뷰어의 질문이 광범위 질문으로 흐름("또 뭐 있나요?", "더 보여드릴까요?")
- 새 레퍼런스를 보여줘도 열린 갭이 줄지 않음

대응: 다음 레퍼런스를 무작위로 고르지 말고 **최우선 열린 갭을 정면으로 줄이는 레퍼런스**를 고른다(예: 인터랙션 품질이 비었으면 인터랙션이 대비되는 레퍼런스). 두 번 연속 갭이 줄지 않으면 그 갭의 이름을 명시하고 사람에게 직접 묻는다.

### 소스 어휘를 더 쪼갠다 — "PRD 원문"과 "PRD에서 도출한 해석"은 다른 소스다

원장의 소스 열에 `사람`이라고만 쓰면 PRD가 실제로 요구한 것과 에이전트가 PRD를 읽고 만들어낸 디자인 해석이 섞인다(실제 사례: PRD가 "두 사용자 집단을 따로 관리한다"고만 했는데 "두 집단을 항상 **색으로** 구분"이 `사람` 소스로 확정 처리됨 — `docs/harness-lessons.md` L13). 그래서 소스는 다섯 가지다.

| 소스 | 뜻 | 확정 가능? |
|---|---|---|
| `사람-원문` | PRD·디자이너 발화의 원문 그대로 | 예 |
| `사람-해석` | 원문에서 에이전트가 도출한 디자인 결정 | **아니오** — 후보. 사람이 승격해야 확정 |
| `실측` | Figma 파일·라이브러리에서 읽은 값 | 예 (증거 경로 필수) |
| `가정(위임)` | 사람이 명시적으로 생략·위임한 항목의 기본값 | 예(가정 상태) |
| `차단` | 사람 권한 필요, 미답 | 아니오 |

에이전트가 만든 토큰을 Figma에 넣고 다시 읽었다고 `실측`으로 바꾸지 않는다 — 그 값의 **선정 소스**는 `가정(위임)`이고 **측정 소스**만 `실측`이다. `brief.md` 토큰 표에 두 열을 따로 둔다.

### 기준값 공급원 분리 — 증류로 만들 수 없는 것이 있다

- **기존 디자인 시스템이 있으면 증류하지 않는다.** "우리 서비스"처럼 기존 파일·라이브러리가 있는 경우, 팔레트·타이포·네이밍은 **Figma의 변수·스타일·컴포넌트 라이브러리를 실측해** 채운다(소스=실측, 증거 경로 필수).
- **5축 증류는 정성 기준에만 쓴다**(밀도 선호, 무드, 회피할 클리셰 등).
- **정량 임계값**(그리드 단위, 재사용률 하한)은 **실측 또는 사람 입력**이다. 자유서술에서 임계값을 만들면 그게 곧 추측이고 절대규칙 1 위반이다.

### 탈출구 — 사람이 생략을 선택할 때

"그냥 만들어줘"라고 하면 교착하지 않는다. **사람의 명시적 선택으로** 미해소 섹션들을 가정("요구사항 정렬 생략 — 판단기준 미수집")으로 닫고 B단계로 간다. 그 결과 A·C단계 대부분이 SKIP이 되고, 검증이 거의 없었다는 사실이 원장과 최종 보고에 남는다. 에이전트가 생략을 먼저 제안할 수는 있으나 선택은 사람이 한다.

**산출물**: `brief.md` (원장)

# 보조 방법론 (출처: feat/yj1 stage-0-alignment.md)


목적: 무엇을 만들지 자체가 불확실할 때, 라벨형 질문 없이 암묵적 판단기준을 뽑아낸다.

> **이번 프로젝트에서 실제로 뽑아낸 기준·가정·토큰은 여기 없다.** `design/<project-id>/brief.md`에 있다.

## 1. 레퍼런스/시나리오 소싱

**레퍼런스를 직접 찾아야 하면 [reference-research.md](reference-research.md)를 먼저 읽는다** — 검색어 생성, 소스별 성격, 추리는 기준, 조합 판단 순서가 거기 있다. 아래는 그 결과를 어떻게 쓰는지다.

- **소싱 대상**: 요구사항의 도메인과 가장 가까운 실사용 앱 2~4개를 스크린샷 단위로 모은다. 기능이 아니라 **화면의 정보 밀도와 톤**을 참고하기 위함이다.
- **레퍼런스가 없는 도메인**은 인접 카테고리 2개를 조합해 보여준다: "X 앱처럼 되지만, 이 맥락이 들어가면 이 부분은 달라질 것 같다"는 식으로 제시해 반응을 유도한다.
- **클라이언트가 실재하지 않는 세션**(솔로 구현, 데모, 하네스톤 연습)에서도 **소싱은 그대로 한다.** 사라지는 것은 반응을 받을 상대뿐이고, 실제 화면을 봐야 톤·밀도 판단이 선다는 사실은 클라이언트 유무와 무관하다. 이 경우:
  - **소싱·조합 판단**([reference-research.md](reference-research.md))은 전 과정을 수행한다. 건너뛰면 실물을 한 장도 안 본 채 값을 정하게 된다.
  - **반응 원문**만 대체한다 — 요구사항 문서에서 작성자가 자유서술로 남긴 구체적 상황 묘사를 반응 원문처럼 취급한다. 없는 인터뷰를 지어내지 않는다.
  - 레퍼런스에 대한 판단은 사람의 반응 대신 **에이전트 자신의 "취할 것/버릴 것"**(reference-research.md §4)이 대신한다. 이건 지어내기가 아니라 명시적 판단이므로 기록하면 정직하다.

## 2. 질문 형식 — 표상이 아니라 체험

금지: "모던한 게 좋으세요, 아늑한 게 좋으세요?" / "정보량이 많은 게 좋으세요?"

허용:
- 레퍼런스 스크린샷을 보여주고 "이 화면 보면 어떤 생각이 드세요? 이걸로 실제 일을 처리한다면 뭐가 편하고 뭐가 불안할 것 같으세요?"
- IA/플로우는 다이어그램(박스+화살표) 대신 **시나리오 내러티브**로. 다이어그램도 결국 또 다른 전문 표기법이라 라벨형 질문과 같은 함정에 빠진다.

## 3. 암묵적 판단기준 역추출

클라이언트의 반응 원문 한 줄마다, **그 말이 참이려면 화면이 어떠해야 하는가**를 한 줄로 적는다. 라벨("미니멀 선호")이 아니라 화면 결정("카드에 노출할 정보는 3개 이하")까지 내려가야 다음 단계에서 쓸 수 있다.

| 반응/원문 | 역추출한 기준 |
|---|---|
| "이건 좀 산만한데요" | 한 화면에 경쟁하는 시선 유도점이 너무 많다 → 1차 정보를 하나로 줄이고 나머지는 2차로 접는다 |
| "이 사람이 어느 그룹인지 애매할 때가 많아요" | 다중 소속이 예외가 아니라 기본값 → 단일 선택(라디오형) UI는 이 도메인에서 틀린 설계 |

**작성 규칙**: 원문을 요약하지 말고 그대로 옮긴다. 요약하는 순간 이미 해석이 들어가고, 나중에 재해석할 근거가 사라진다.
