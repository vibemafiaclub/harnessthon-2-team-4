# W막 화면 기획 — 화면 목록 · IA · Userflow · 블록 구조 · 추적성 계획

> **이식 노트(2026-09-05)**: iceberg-1234 하네스 `steps/S-screen-spec.md`를 이 하네스의 W막으로 옮긴 것이다. 원문의 S단계 산출물 `screen-spec.md`는 만들지 않는다 — 이 하네스는 원장(`brief.md`)과 요구 계약(`contracts/requirements.json`)에 쓴다. 프로젝트 값(화면명·상태 enum·실제 블록)은 여기 없다.

## 이 파일과 `process-acts.md` W막 규칙의 관계

둘을 섞지 않는다. 겹치면 두 곳을 고쳐야 하고, 한쪽만 고치면 어긋난다.

| 파일 | 담당 |
|---|---|
| `process-acts.md` W막 규칙 | **매체와 절차** — HTML 로우파이 먼저 → 중간 컨펌 → Figma `W Wireframes`, 회색 1~3단계, `WF/*` 토큰 바인딩 금지, notes 항목, `LOCK-W` 조건 |
| **이 파일** | **무엇을 기획하나** — 화면 목록을 어떻게 도출하고, IA를 어떻게 고르고, 블록 위계를 무엇으로 정하고, 무엇을 추적하나 |

**순서**: 이 파일로 기획을 끝낸 뒤 `process-acts.md`의 매체 절차로 보여 준다. 반대로 하면 HTML을 먼저 그리고 나서 근거를 역으로 붙이게 된다.

## 이 막이 담당하는 대원칙 축

| 축 | 이 막의 역할 |
|---|---|
| **② 심미적 안정성** | **구조적 기반** — 정렬 축·간격 종류를 미리 정한다 (C의 AS1·AS3·AS5 사전 설계) |
| **③ 핵심경험** | **계획 전담** — Userflow·IA로 `CE-n` 완결 경로를 설계하고 **추적성 계획**을 세운다 (A-T의 CE1~CE7 근거) |

🔴 **이 막은 시각 스타일을 다루지 않는다.** 색·폰트·그림자·구체 여백값은 U막이 `foundation-derivation.md`로 정한다. 여기서는 **구조·순서·우선순위·상태**만 정한다. `process-acts.md`가 W에 토큰 바인딩을 금지하는 이유와 같다 — 색이 보이면 클라이언트가 색을 평가하기 시작하고, **기능이 맞는지를 아무도 검증하지 못한다.**

## 🔴 이 파일의 수치는 절차 기본값이지 확정 합격선이 아니다

이 파일에는 원본에서 함께 온 수치가 있다 — **IA 대안 3안**, **모든 화면 5종 상태**, **P0 600pt 이내**, **탭 수 ≤ 3**, **화면당 P0 1개**, **정렬 축 ≤ 4**, **간격 종류 ≤ 4종**, **Tab ≤ 5**.

**이것들을 이 프로젝트의 새 합격선으로 자동 승격하지 않는다** (`docs/PLAN-design-process-import.md` §3). 절대 규칙 1이 정한 대로 **기준값은 사람의 몫**이다.

| 성격 | 어떻게 다루나 |
|---|---|
| **절차 기본값** (이 파일의 수치) | 기획할 때의 출발점. 초과하면 **근거를 적는다** — 그 자체로 FAIL은 아니다 |
| **확정 합격선** | `brief.md`의 A단계 기준값 YAML. **A/C가 판정에 쓰는 것은 이것뿐이다** |

- 기존 A-T에 이미 600pt·탭 수 기준이 있다. **그 값의 승인 근거와 적용 범위를 먼저 확인**하고, 이 파일의 수치와 다르면 **이 파일 쪽을 조용히 채택하지 않는다** — 차이를 사람에게 보여 결정을 받고 `decisions.md`에 기록한다.
- `brief.md`에 해당 기준값이 `TODO`면 그 항목은 `SKIP`이다(절대 규칙 1의 ★). 이 파일의 수치로 빈칸을 메우지 않는다.
- iOS 수치(44pt 터치 영역, Safe Area 등)는 **플랫폼 적용 범위가 확인된 경우에만** 쓴다(`platform-hig-ios.md`).

★ 아래 「완료 조건」의 체크 항목은 **"확인했는가"** 이지 **"수치를 만족했는가"** 가 아니다. 초과 사실과 근거가 기록되어 있으면 그 항목은 통과다.

## 실행 절차

### 1. 화면 목록 도출 — PRD 목록은 하한이다

원장의 명시적 화면 목록은 **최소 요건**이다. `CE-n`을 완결하는 데 필요한 화면이 빠져 있으면 추가한다.

1. 각 `CE-n`의 **성공 조건**을 읽는다.
2. 그 성공 조건에 도달하려면 어떤 화면을 거쳐야 하는지 나열한다.
3. **인접 경험 매핑**을 확인한다 — 직전/직후/대체 경험이 요구하는 진입점·이탈점 화면을 추가한다.
4. 원장 목록과 대조해 **누락분을 추가**한다. 추가한 화면은 추가 근거(`CE-n` ID)를 함께 적는다.

#### 자주 누락되는 화면

| 유형 | 왜 누락되는가 |
|---|---|
| 결과/확인 화면 | 액션에 집중해 "됐다"를 확인하는 곳을 잊는다 (CX4 실패 원인) |
| 상세/도착 화면 | 목록을 만들고 탭했을 때 갈 곳을 안 만든다 |
| 필터/정렬 시트 | 목록이 길어질 때만 필요하다고 생각해 미룬다 |
| 빈 상태 | 데이터가 있는 경우만 상상한다 |
| 로딩 상태 | 즉시 렌더된다고 가정한다 |
| 에러/실패 상태 | 성공 경로만 설계한다 |
| 진입 화면 | 유저가 앱 밖에서 정보를 들고 온다는 걸 고려하지 않는다 |

🔴 **모든 화면은 최소 하나의 `CE-n`에 연결된다.** 연결되지 않는 화면은 기획하지 않는다 — A-T의 CE3가 "근거 없는 화면"으로 잡는다.

★ 화면 ID는 **W와 U가 같은 `S<nn>`**을 쓴다(`process-acts.md`: W 화면은 U 화면과 1:1). 계약에서는 `screens[].id`(`SCR-nn`)와 `name`(`S<nn>`)이 짝이다. **W에서 ID를 새로 매기고 U에서 다시 매기지 않는다** — 그 순간 추적성 매트릭스가 두 벌이 된다.

### 1-1. 관성 진단 — 기존안이 있는 경우

> `forbidden-patterns.md` §0

기존 Figma 소스·참고 화면이 있으면 **정답으로 취급하기 전에** 진단한다.

| 진단 항목 | 확인 |
|---|---|
| 네비게이션 모델 | 목적지 수만큼의 탭인가, 자리를 채운 탭인가 (SP1) |
| 컨테이너(카드) 사용 | 독립 조작 단위에만 카드를 썼는가, 모든 항목을 감쌌는가 |
| 진입 흐름 | 온보딩 캐러셀·가치 소개가 첫 작업을 지연시키는가 (SP2·SP3) |
| 부가 화면 처리 | 전부 바텀시트인가 (SP4) |
| 숨은 기능 | 햄버거 메뉴에 핵심 목적지가 있는가 (SP5) |
| 관성 FAB | FAB가 실제 핵심 행동인가 (SP6) |
| 빈 상태 | 다음 행동이 있는가 (SP7) |

**기존 화면의 배치·순서·선택은 폐기 대상**이다. 유지하는 것은 확정된 콘텐츠·기능 요구사항, **플랫폼 관습**, **디자인 시스템의 토큰·컴포넌트**뿐이다.

★ 온보딩 O-3에서 기존 산출물을 "있음/LOCK 없음"으로 등록했다면 **여기가 그것을 실제로 재검토하는 지점**이다. 등록만 하고 진단을 건너뛰면 "있으니까 맞겠지"로 관성이 그대로 통과한다.

### 2. IA — 대안 3안을 만들고 비교한다

`experience-definition.md` §3의 **Model the System**(고정/변화/관계/시간/결과)을 화면 계층으로 변환한다.

문제 정의에서 바로 하나의 IA로 뛰어들지 않는다. **정보 구조와 네비게이션 모델이 서로 다른 대안 3개**를 만든다. 예: `탭 기반` / `단일 흐름 + 진입점` / `피드형 홈 중심`.

🔴 **셋이 같은 뼈대의 변형이면 실패다.** 해결 원리가 달라야 한다. 이는 B단계의 축 분리 규칙(`stage-b-diverge.md`)과 같은 요구다 — 다만 여기서 가르는 축은 **정보 구조**다.

| 비교 항목 | 대안 A | 대안 B | 대안 C |
|---|---|---|---|
| 네비게이션 모델 | | | |
| **핵심 행동까지의 탭 수** | | | |
| **최초 사용자 vs 재방문 사용자 경로 차이** | | | |
| **실수했을 때의 복구 비용** | | | |
| **기능이 늘었을 때의 확장성** | | | |

선택 후 **탈락 이유를 명시**한다. "A가 더 나아 보여서"는 근거가 아니다.

★ **IA 선택은 사람이 한다**(절대 규칙 2, B-4와 같은 취급). 에이전트는 3안과 비교표를 만들고 추천하되 고르지 않는다. `LOCK-W`가 잠그는 "화면 목록·순서"의 상위 결정이므로, 여기서 에이전트가 고르면 사람은 이미 정해진 구조를 컨펌하게 된다.

#### 산출 항목

| 항목 | 내용 |
|---|---|
| 네비게이션 모델 | 선택안 + **근거**: M막에서 관찰한 카테고리 관습 + 위 비교 결과 |
| 화면 계층 | Depth 0(탭 루트) → Depth 1 → Depth 2 … |
| 화면 간 관계 | Push / Present(modal) / Replace / Tab switch |
| 정보 그룹핑 | 무엇이 같은 화면에 있어야 하고 무엇이 분리되는가 + 근거 |
| 진입점 | 각 화면에 도달하는 모든 경로 |

#### IA 규칙

- **Depth 3 이상은 근거를 적는다.** 깊어질수록 CE5(플로우 깊이 ≤ 3탭)를 위협한다.
- Tab은 **최대 5개**(`platform-hig-ios.md`). 넘으면 정보 그룹핑을 재검토한다.
- 🔴 **최상위 네비게이션은 사용자가 서로 오가는 목적지만** 포함한다. 한 번만 쓰는 것은 진입점 안으로 넣는다 (SP1).
- 정보 그룹핑 근거는 **페르소나의 작업 단위**여야 한다. "카테고리가 달라서"는 근거가 아니다.
- 🔴 **독립적으로 조작·이동·삭제되는 요소에만 컨테이너(카드)**를 쓴다. 반복되는 동종 항목은 구분선과 간격으로 나눈다.
- 의미적 관계는 **선·간격·타이포그래피**로 표현한다. 색상으로 표현하지 않는다 — W에는 색이 없으므로, 여기서 색에 의존한 그룹핑을 계획하면 U막에서만 성립하고 W 컨펌에서는 검증되지 않는다.

### 3. Userflow — 화면 단위

각 Primary `CE-n`에 대해 `Pain → Entry → Core Interaction → Understanding/Decision → Outcome`을 화면 시퀀스로 변환한다.

```
[진입점] 화면A
   │ (유저 액션: ___)
   ▼
화면B ──조건: X일 때──▶ 화면C
   │ (조건: Y일 때)
   ▼
화면D  ← 성공 조건 달성 지점
   │
   └─(이탈) 화면A로 복귀
```

각 전이에 기록할 것:

| 항목 | 내용 | 계약 필드 |
|---|---|---|
| 트리거 | 유저 액션 또는 시스템 이벤트 | `flow.edges[].cta` |
| 조건 분기 | 조건과 각 목적지 | `flow.edges[]` (분기마다 한 행) |
| 전이 방식 | Push / Present / Replace / Dismiss | — |
| 되돌아가기 | 이 전이를 취소하는 경로 (CE6 근거) | — |

#### 플로우 완결성 체크

- [ ] 플로우 끝에 **성공 조건 달성 지점**이 명시되어 있는가 (CX3 근거)
- [ ] 각 화면에 **이탈 경로**가 있는가 (CE6 근거 — 막다른 화면 금지)
- [ ] Primary CE 완결까지 **탭 수 ≤ 3** (CE5 근거) — 초과 시 근거 기록
- [ ] **인접 경험**의 직전/직후 연결이 반영되어 있는가 (CX5 근거)

★ 여기서 정한 전이가 U막에서 **프로토타입 `reactions`**가 된다. A-F는 "문구로만 가리키면 `표현됨`, `reactions`가 있으면 `연결됨`"으로 판정하고 **연결 0개는 FAIL**이다. 그러므로 이 표를 비워 두면 U막에서 무엇을 연결할지 알 수 없다.

### 4. 와이어프레임 블록 구조

각 화면의 블록 구성을 위→아래 순서로 정의한다. **시각 스타일은 쓰지 않는다.**

| # | 블록 | 역할 | 콘텐츠 타입 | 우선순위 | 필요 컴포넌트 |
|---|---|---|---|---|---|
| 1 | (예: Navigation Bar) | 현재 위치 + 이탈 경로 | 타이틀, Back | 고정 | (예: Organism/nav-bar) |
| 2 | | `CE-n`의 핵심 CTA | | **P0** | |

#### 우선순위 — 빈도가 위계를 결정한다

`brief.md` 핵심경험 섹션의 **핵심 행동 빈도**(매일 / 주 1회 / 최초 1회)를 1차 기준으로 쓴다. CE 우선순위(Primary/Secondary)만으로는 부족하다.

| 등급 | 기준 | 배치 제약 |
|---|---|---|
| **P0** | Primary `CE-n` × **매일/매 세션** 빈도 | 🔴 **스크롤 없는 영역**(Safe Area 상단 + 600pt 내) — CE4 근거 |
| P1 | CE 완결에 필요 × 주 1회 이상 | 첫 스크롤 내 |
| P2 | 보조 정보 / **최초 1회** 설정 | 스크롤 하단 또는 진입점 안쪽 |

🔴 **화면당 P0는 1개**를 권장한다. 2개 이상이면 C의 AS6(강조 요소 ≤ 3개)과 CX1(3초 테스트)을 위협한다.
🔴 **최초 1회만 쓰는 것을 최상위에 두지 않는다** (SP1).

#### 엄지 도달 범위 (모바일)

| 배치 | 대상 |
|---|---|
| **엄지 도달 범위** (화면 하단·중앙) | 자주 쓰는 조작 |
| **엄지 도달 범위 바깥** (상단 코너 등) | **파괴적 조작** (삭제·폐기·로그아웃) |

파괴적 조작을 엄지 범위에 두면 오조작이 발생한다. A-T가 CE4에서 P0 위치와 함께 검증한다.

#### 파괴적 행동은 되돌리기를 우선 검토한다

확인 다이얼로그는 마찰만 늘리고 오조작을 막지 못하는 경우가 많다.

| 상황 | 설계 |
|---|---|
| 되돌릴 수 있음 | **즉시 실행 + Undo 토스트** |
| 되돌릴 수 없음 + 영향 큼 | 명시적 확인 (타이핑 확인 등) |
| 되돌릴 수 없음 + 영향 작음 | 단순 확인 다이얼로그 |

#### 구조 규칙 — 심미적 안정성 사전 설계

- **정렬 축을 미리 정한다.** 화면당 서로 다른 x 시작점 **≤ 4개** (AS1 근거).
- **블록 간 간격 종류 ≤ 4종** (AS3 근거). 역할을 미리 분류한다: 블록 내 / 블록 간 / 섹션 간.
- **그룹 내 간격 < 그룹 간 간격** (AS5 근거).
- 동일 역할 블록(Nav/Tab Bar 등)은 **모든 화면에서 같은 위치**.

★ 여기서 정한 **간격 종류의 개수**만 넘기고 **값(pt)은 넘기지 않는다.** 값은 U막이 `foundation-derivation.md`로 유도한다. W에서 값을 정하면 그 값의 선정 소스가 `사람-해석`인데 U에서 `실측`으로 둔갑한다.

### 5. 화면 단위 명세

각 화면에 대해 아래를 쓴다. 이것이 U막 제작-S의 구현 명세다.

| 항목 | 계약 필드 |
|---|---|
| 화면 ID / 이름 | `screens[].id` / `screens[].name` |
| 목적 (한 문장) | `screens[].purpose` |
| 서포트하는 `CE-n` (복수 가능) | `core_experiences[].screens` (역방향) |
| 진입점 (전부) | `screens[].entry_from` |
| 이탈점 (성공 경로 + 취소 경로) | `screens[].primary_cta_to` + `flow.edges[]` |
| 필수 요소 — 없으면 목적 달성 불가한 것 | (블록 표 P0/P1) |
| 상태 — **5가지 전부** | `edge_states_planned[]` |
| 데이터 — 표시 항목과 **현실적 예시값** | fixtures |
| 인터랙션 — 유저 액션 → 결과 | `flow.edges[]` |
| 성공 조건 — 무엇이 보이면 성공인가 | `core_experiences[].success_condition_observable` |

#### 상태 5가지

**모든 화면에 대해 다섯 가지를 설계한다.** 성공 경로만 설계하면 C의 US1·US9가 실패한다.

| # | 상태 | 반드시 포함 |
|---|---|---|
| 1 | **Empty** | 다음 행동 안내 + CTA. **"데이터가 없습니다"만으로는 불충분** (SP7) |
| 2 | **Loading** | 스켈레톤 구조 (Default와 동일 골격). 400ms 이내 표시 (US1) |
| 3 | **부분 로딩 / 오프라인** | 일부만 로드된 상태 + 오프라인 배너. **어디까지 신뢰할 수 있는지** 구분 |
| 4 | **Error** | 원인 + 해결 방법 + **"재시도" vs "완전 실패" 구분** (US9) |
| 5 | **데이터 과다** | 목록이 길거나 텍스트가 길 때의 처리 (페이지네이션·말줄임·스크롤) |

★ `contracts/requirements.json`의 `edge_states_planned[].state`는 원래 `empty | loading | error` 셋이었다. **다섯으로 확장했다** — `partial_offline`, `overflow` 추가.

각 상태에서 **레이아웃이 깨지지 않는지** 함께 확인한다: 최소 터치 영역 / 동적 폰트 200% 확대 / 긴 텍스트·번역문.

★ 프로젝트의 상태 enum(`contracts/requirements.json`의 `states[]`)은 이 다섯과 **다른 것**이다. `states[]`는 도메인 상태(예: 진행/완료)이고 여기 다섯은 화면 로딩 상태다. A-F가 `states[]` 커버리지를, 여기가 `edge_states_planned[]`를 각각 본다 — 섞지 않는다.

### 6. 추적성 계획

U막이 구현하고 A-T가 검증할 계획을 세운다. **U막은 여기에 nodeId만 채운다.**

#### 정방향 — 모든 화면의 근거

| 화면 ID | 서포트하는 CE | 근거 블록 (# + 역할) |
|---|---|---|
| | | |

#### 역방향 — 모든 `CE-n`의 충족

| CE | 우선순위 | 관여 화면 | 성공 조건 달성 지점 | 판정 |
|---|---|---|---|---|
| | Primary/Secondary | | | 충족 / **미충족** |

🔴 **Primary `CE-n`이 하나라도 `미충족`이면 W막을 끝낼 수 없다.** 화면을 추가하고 재작성한다. 이 상태로 `LOCK-W`를 걸면 A-T의 CE2가 U막에서 Blocker로 잡히는데, 그때는 구조가 잠겨 있어 UNLOCK 비용을 문다.

## 산출물 — 어디에 쓰나

별도 `screen-spec.md`를 만들지 않는다.

| 무엇 | 어디에 |
|---|---|
| 화면 목록 · 목적 · 진입/이탈점 | `contracts/requirements.json` → `screens[]` |
| Userflow 전이 | 같은 파일 → `flow.edges[]` (`prototype_connected: false`로 시작) |
| 5가지 상태 계획 | 같은 파일 → `edge_states_planned[]` |
| `CE-n` ↔ 화면 역방향 | 같은 파일 → `core_experiences[].screens` |
| IA 3안 비교 · 탈락 이유 · 관성 진단 · 블록 구조표 · 정렬/간격 계획 | `design/<project-id>/brief.md` 구조·워크플로 섹션 |
| 선택 근거 원문 · 컨펌 원문 | `decisions.md` 현재 라운드 + `LOCK-W` 블록 |

`screens[].node_id`와 `core_experiences[].evidence_nodes`는 **여기서 채우지 않는다** — U막 제작-S가 채운다. `null`로 둔다.

## 완료 조건 — `LOCK-W` 전에

`process-acts.md`의 W막 종료 GATE(HTML 컨펌 원문·Figma 컨펌 원문·V-1/V-2/V-3 자체 점검) **에 더해** 아래를 확인한다.

### 화면 목록·관성
- [ ] 모든 화면이 최소 1개 `CE-n`에 연결 (CE3 근거)
- [ ] 원장 목록에 없지만 `CE-n`이 요구해 **추가한 화면**과 그 근거
- [ ] 기존안이 있으면 SP1~SP7 관성 진단 결과 + 폐기/유지 구분

### IA
- [ ] **대안 3안** — 해결 원리가 서로 다름 (같은 뼈대 변형이면 실패)

## 금지 사항

- ❌ **시각 스타일**(색·폰트·그림자·구체 여백값) 지정. U막이 정한다.
- ❌ 어떤 `CE-n`에도 연결되지 않는 화면 기획.
- ❌ Primary `CE-n`이 `미충족`인 상태로 **`LOCK-W`**.
- ❌ Empty 상태를 **"데이터가 없습니다"** 한 줄로 처리.
- ❌ 성공 경로만 설계하고 **Error/이탈 경로 생략**.
- ❌ 5가지 상태 중 **부분로딩·오프라인 또는 데이터 과다 생략**.
- ❌ IA 대안을 **1안만** 만들거나, 3안이 **같은 뼈대의 변형**.
- ❌ 🔴 **에이전트가 IA를 고르기.** 3안과 비교표까지가 에이전트의 몫이다 (절대 규칙 2).
- ❌ 탈락 이유를 **"A가 더 나아 보여서"**로 적기.
- ❌ 기존 화면의 배치·순서를 **정답으로 전제**.
- ❌ **파괴적 조작을 엄지 도달 범위**에 배치 / 되돌리기 검토 없이 확인 다이얼로그로만 처리.
- ❌ **최초 1회만 쓰는 것을 최상위 네비게이션**에 두기.
- ❌ `forbidden-patterns.md` §0의 **SP1~SP7** 사용.
- ❌ 정보 그룹핑 근거를 **"카테고리가 달라서"**로 적기.
- ❌ P0를 **스크롤 아래**에 배치.
- ❌ 예시 데이터에 **Lorem ipsum / placeholder 인명** 사용.
- ❌ 🔴 화면 ID를 W와 U에서 **다르게** 매기기. 추적성 매트릭스가 두 벌이 된다.
