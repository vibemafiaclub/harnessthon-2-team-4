## 온보딩 O단계 — 게이트보다 먼저, 프로젝트를 받아들이는 절차

새 프로젝트·새 클라이언트·새 세션 드라이버가 들어올 때 **한 번** 돈다. 산출물은 `design/<project-id>/onboarding.md`(양식 `templates/onboarding.md`)와 GATE `stage: onboarding`. 이게 없으면 G-1로 가지 않는다 — 과거에 온보딩 없이 시작해 target을 에이전트가 임의로 만들고, 3막 순서가 뒤집히고, 인터뷰 스킬 이름을 추측한 일이 있었다(`docs/harness-lessons.md` L1·L20·L25).

- 드라이버가 바뀌면(세션·사람) `onboarding.md`의 인수인계 표에 한 줄 추가하고 O-3·O-5만 다시 확인한다. 전체를 다시 돌리지 않는다.
- 온보딩에서 모은 값 중 판단기준·기준값은 **여기서 확정하지 않는다** — 원장(brief)의 몫이다. 온보딩은 "누가, 무엇으로, 어디서부터"만 잠근다.

## 디자인 프로세스 — 4막 + 단계별 확정 잠금

UI 디테일을 먼저 그리면 인터뷰가 색·폰트 얘기로 흘러 **기능이 맞는지**를 아무도 검증하지 못한다. 반대로 UX를 다 확정하고 나서 무드를 잡으면 무드가 UX를 다시 흔든다. 그래서 **무드 → 와이어프레임 → 기능 인터뷰 → UI 상세** 순서로 나누고, 막마다 클라이언트 확정을 **잠금(LOCK)**으로 기록한다. (디자이너 피드백 원문 2026-09-05: "디자인 무드부터 잡는다", "와이어프레임은 일단 html 레벨에서 먼저. 중간에 컨펌", "client가 이미 좋다고 했으면 UX 레벨에서 크게 변경하는 상황은 피하고 싶다 — divide and conquer로 단계적으로 확정", "곧이곧대로 믿지 말고 유사한 스타일로 2~3번 다시 찔러본다")

| 막 | 이름 | 매체 | 산출물 | 확정 잠금 | 사람 개입 |
|---|---|---|---|---|---|
| **M** | 디자인 무드 | 레퍼런스 이미지(HTML 갤러리 또는 URL) 1개씩 | `brief.md` 시각 언어 섹션 + 무드 보드(3~5개 채택 레퍼런스) | `LOCK-M` 무드 어휘·채택/기각 레퍼런스 | 반응 원문 + "왜" 되묻기 |
| **W** | 와이어프레임 (UX) | **① HTML 로우파이(클릭 가능)** → 중간 컨펌 → **② Figma `W Wireframes`** | HTML 파일 + Figma W 화면 + notes | `LOCK-W` 화면 목록·순서·CTA 목적지 | 컨펌 2회(HTML, Figma) |
| **I** | 기능 인터뷰 | W 화면 + 시나리오 과제 | `interview.md` | `LOCK-I` 요구 계약·해석 승격 결과 | **필수** |
| **U** | UI 상세 | Figma `03 Screens` 토큰·컴포넌트 | 하이파이 + A/C/V | `LOCK-U` 최종 승인 | 최종 판단 |

### 확정 잠금(LOCK) 규칙 — 확정된 것은 나중에 흔들지 않는다
- 막이 끝나면 `decisions.md`에 `LOCK-<막>` 블록을 append: 무엇을 확정했나(목록), 누가(역할), 언제, 근거 원문.
- **잠긴 항목은 뒤 막에서 변경 제안을 하지 않는다.** 뒤 막에서 잠긴 항목이 틀렸다는 증거가 나오면 "변경"이 아니라 **`UNLOCK 요청`**을 사람에게 낸다 — 이유·영향 범위·비용(재작업 막 수)을 적고, 사람이 승인해야 풀린다. 에이전트가 조용히 되돌리지 않는다.
- UNLOCK은 라운드 카운터를 증가시킨다(상한 3). 같은 항목을 두 번 UNLOCK하면 요구 해석 자체가 틀린 것 → 0단계 에스컬레이션.
- 잠금 전 컨펌은 **한 번에 하나의 막만** 묻는다. "무드도 괜찮고 화면도 괜찮죠?"처럼 두 막을 한 질문에 섞지 않는다.

### 되묻기 규칙 — 클라이언트 말을 곧이곧대로 믿지 않는다 (M·W·I 공통)
클라이언트의 첫 반응("따뜻해 보여요", "좋아요")은 라벨이다. 라벨을 기준으로 승격하지 않고 **같은 성질의 레퍼런스·변형 2~3개로 다시 찔러본다.**
1. 첫 반응 원문 기록 → "왜 좋으세요?" 한 번.
2. 답에서 나온 단어(예: "따뜻", "친근", "라운드")를 **같은 축의 유사 레퍼런스 2~3개**로 시험한다 — 라운드가 더 큰 것 / 라운드는 같고 색만 차가운 것 / 라운드 없고 따뜻한 색만인 것. 어느 것에서 반응이 꺾이는지가 진짜 기준이다.
3. 세 번 모두 같은 방향이면 후보 → 승격 질문. 갈리면 갈린 지점을 원문으로 기록하고 기준을 더 좁게 쓴다.
4. 되묻기 기록 열(`probe-1/2/3`)이 비어 있는 후보는 승격 질문을 하지 않는다.
- 인터뷰 진행 자체는 프로젝트 설정 `interview.skill`에 지정한 인터뷰 스킬로 한다. 기본 어댑터는 Ouroboros `ooo interview`(`docs/integrations/ooo-interview.md`) — 그 `references` 대비 질문이 0-2의 5축과 같고, `refine_answer`가 probe-1, 유사 변형 cue 추가가 probe-2/3, `restate` 승인이 LOCK 근거가 된다. ooo의 자동 기본값·`seed-ready`는 쓰지 않는다. 지정이 없으면 위 되묻기 규칙과 0-2 루프를 수동으로 쓴다. 어떤 스킬·경로를 썼는지 `interview.md` 머리에 적는다.

### M막 규칙
- 0단계 0-2 루프와 같은 진행이지만 **시각 언어(원장 섹션 4)만** 조준한다. 구조·기능 얘기가 나오면 원문만 기록하고 W막으로 넘긴다.
- 레퍼런스는 HTML 갤러리(스크래치 디렉터리 또는 Artifact)로 1개씩 보여 준다. 이미지 출처·URL·라이선스 메모를 함께 남긴다(`templates/reference-review.md`).
- 산출물: 채택 레퍼런스 3~5개 + 기각 레퍼런스와 기각 이유 원문 + 무드 어휘(예: "따뜻·친근·라운드, 딱딱한 폰트 아님") → `brief.md` 시각 언어. **토큰 값(HEX·폰트명)은 여기서 정하지 않는다** — 어휘와 레퍼런스만 잠근다. 값은 U막에서 어휘에 맞춰 고르고 실측한다.

### W막 규칙
- **① HTML 로우파이 먼저.** 프로젝트 `process.wireframe_html_dir`에 화면당 1개 HTML(회색 박스·실제 문구·CTA는 다음 화면으로 링크). 클라이언트가 클릭해 보고 **중간 컨펌**. 이 HTML은 검증 매체이며 산출물이 아니다 — 이 하네스의 "코드로 UI를 만들지 않는다" 규칙의 명시적 예외.
- 컨펌 원문을 받고 되묻기 규칙을 적용한 뒤 **② Figma `W Wireframes`**에 옮긴다. W 화면은 U 화면과 **1:1 대응**(같은 `S<nn>`). W가 흐름의 원장이다.
- W 컴포넌트(`WF/*`)는 회색 1~3단계만. `_system` 토큰 바인딩 금지 — 바인딩하면 클라이언트가 색을 평가하기 시작한다(M막에서 잠근 무드 어휘도 W에는 넣지 않는다).
- 각 W 화면 notes에 목적 / CTA 목적지 / 까다로운 경우 / 인터뷰 질문 1~3개.
- W막 종료 GATE(`stage: wireframe`)에 HTML 컨펌 원문·Figma 컨펌 원문·V-1/V-2/V-3 자체 점검이 있어야 `LOCK-W`.

### I막 규칙 — 표상이 아니라 체험
- 대상은 project.json `interview.audiences`별 최소 1명. 실제 사람이 없으면 **페르소나 시뮬레이션 Agent**(신규 컨텍스트, PRD §사용자 상황만 받음)로 대체하되 "시뮬레이션"이라고 명시 — 실제 인터뷰와 같은 급으로 승격 근거가 되지 않는다.
- W 화면을 순서대로 보여 주고 **시나리오 과제**를 준다. 라벨 질문 금지. 막힌 지점·되돌아간 지점·틀린 예상을 원문으로. 되묻기 규칙 적용.
- 기록 → 증류(`GAP-F` 기능 갭 / `GAP-X` 흐름 갭 / 해석 정정) → 승격은 사람.
- **LOCK-W와 충돌하는 갭**이 나오면 UNLOCK 요청으로 낸다. 조용히 W를 고치지 않는다.
- I막 종료 GATE(`stage: interview`) PASS + `LOCK-I` 후에만 U막.

### U막
기존 제작-L/S·A·C·V 그대로. 시작 시 `LOCK-W`의 화면 목록·CTA와 대조하고, 토큰 값은 `LOCK-M`의 무드 어휘에서 고른다(값 선정 소스=`가정(위임)`, 측정 소스=`실측`). U에서 UX 변경 제안 금지 — UNLOCK 요청만.

**라우터 추가 행**: `LOCK-M 없음 → M막` / `LOCK-W 없음 → W막(HTML → Figma)` / `interview.md 없음 또는 LOCK-I 없음 → I막` / `LOCK-I 있음 → U막(제작단계)`. `plan-only`는 M·W까지, `review`는 U 검증만.

## 인수인계 GATE — 단계 사이에 반드시 남기는 블록

각 단계가 끝날 때 `decisions.md` 현재 라운드 끝에 아래 YAML 블록을 **append**한다(양식: `templates/contracts/gate.yaml`). 다음 단계는 이 블록의 `output_refs`가 실재하는지, `target_ref`가 `brief.md` target과 같은지 확인한 뒤에만 시작한다.

```yaml
stage: build-screens            # requirements | align | diverge | build-library | build-screens | verify-A | verify-C | verify-V
mode: build
project_id: <project-id>
run_id: <세션 시작 시 고정>
revision: 1.2                   # 라운드.하위라운드
producer: <세션/에이전트 식별>
target_ref: <brief.md target의 file_key + page>
input_refs: [<경로>, ...]
output_refs: [<경로 또는 node ID>, ...]
status: PASS                    # PASS | PARTIAL | FAIL | BLOCKED
blockers: []                    # 미해결 결정의 이름
next_stage: verify-A
```

- `PASS`라는 글자만으로 통과하지 않는다. `output_refs`가 없거나 target이 다르면 `BLOCKED`로 되돌린다.
- `PARTIAL`은 진행 보고다. 의존 단계를 여는 승인이 아니다.
- `BLOCKED` = 증거·권한·결정이 없어 판정 자체를 못 한 것. `FAIL` = 검사했는데 위반. 둘을 섞지 않는다 — 검증 Agent가 한도 초과로 죽은 것은 `BLOCKED`다.
- 제작 세션과 검증 세션의 `producer`가 같으면 검증 입력으로 받지 않는다(절대 규칙 4의 기계적 검사).

## 안전한 재개 — 끊긴 뒤 다시 시작할 때

- 재개 전에 `decisions.md` 제작 기록의 노드 ID 목록과 현재 파일을 **1회 읽기로 대조**한다. 이름만 같은 노드를 내 것으로 채택하지 않는다. 응답이 끊겨 생성 여부가 불명확하면 실재 확인 → 없으면 재생성, 있으면 제자리 수정.
- 삭제·전체 재생성을 재개의 기본값으로 두지 않는다. 컴포넌트를 바꿔 끼우면 의존 인스턴스의 오버라이드가 날아간다.
- `improve` 모드는 이전 run의 라운드 번호를 이어 쓴다. 상한(3)은 run이 바뀌어도 초기화되지 않는다.
