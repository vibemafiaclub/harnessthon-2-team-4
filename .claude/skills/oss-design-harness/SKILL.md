# oss-design-harness

현업 디자이너의 판단 기준(안목)을 추출해, Figma MCP로 실제 화면을 만드는 하네스.

## 이 파일의 상태 — 무엇이 채워졌고 무엇이 비었는가

- **채워진 것 = 구조.** 게이트, 라우터, 서브에이전트 배선, 검증자 격리, 판정 규칙, 라우팅, 카운터. 손대지 않아도 실행된다.
- **빈 것 = 판단기준.** `TODO`로 표시된 곳. **이걸 채우는 것이 곧 당신의 안목을 코드화하는 작업이다.**

## 절대 규칙 — 모든 단계에 적용

### 1. `TODO`는 세 종류다. 반드시 구분한다

| 종류 | 어디에 있나 | 행동 |
|---|---|---|
| **판단기준·기준값** | SKILL.md의 A단계 기준값, C단계 6항목, 후보 개수 등 | **사람에게 묻고 멈춘다.** 추측 금지. |
| **절차** | SKILL.md에서 "어떻게 할지"가 빈 곳 (레퍼런스 소싱, 역추출 방법, 축 식별, 라우팅 판별) | **기본 절차로 진행한다.** 멈추지 않는다. 사람이 나중에 조정한다. |
| **산출물** | `brief.md`·`decisions.md` 안의 모든 TODO | **각 단계가 채운다.** 정상 작업이다. |

- **판단기준을 추측해서 채우면** 이 하네스의 목적(사람의 안목 추출)이 그 자리에서 무너지고, **무너진 것이 성공처럼 보인다** — 그럴듯한 화면과 채워진 문서가 남으므로 사람은 작동했다고 믿는다.
- **절차 TODO에서 멈추면** 하네스가 첫 실행에서 진행 불가가 된다. 절차는 하네스의 일이고, 판단기준은 사람의 일이다.
- ★ **`TODO`라는 글자는 "비어 있음"과 같다.** `tokens.color.allowed: [TODO]`를 유효한 허용 목록으로 읽지 않는다. `TODO`·`TBD`·빈 값은 전부 미기입으로 간주해 `SKIP` 처리한다. 값으로 읽으면 화면의 모든 색이 FAIL이 되고 수치 비교는 크래시한다.
- 어느 종류인지 애매하면 사람에게 묻는다.

### 2. 최종 "이 정도면 됐다" 판단은 항상 사람이 낸다
에이전트가 완료를 자체 선언하지 않는다. 축별 후보 선택도 사람이 한다(B-4 참조).

### 3. 확정 안 된 정보는 침묵하지 않고 `brief.md` 가정 로그에 명시한다
`brief.md`가 아직 없는 시점의 가정은, 파일을 만든 직후 첫 항목으로 옮겨 적는다.

### 4. 검증하는 에이전트 ≠ 만든 에이전트
문장이 아니라 배선으로 지킨다 — 아래 「검증 Agent 배선」 참조.

### 5. 멈출 때는 미해결 결정의 이름을 남긴다
정지·차단·에스컬레이션 사유를 "상한 도달"·"라운드 소진"·"기준값 없음" 같은 상태 서술로 끝내지 않는다. **무엇이 안 풀렸는지를 이름으로 쓴다** — 예: "C-1 색온도 기준 미확정 — 디자이너 확인 필요", "라운드 2·3 연속 C-4 탈락". 재개하는 사람이 보고만 읽고 무엇을 풀어야 하는지 알아야 한다.

## 프로젝트 설정 — 코어는 값을 갖지 않는다

이 스킬은 **절차만** 담는다. 도메인 값(화면 이름·상태 enum·토큰·더미 데이터·대상 파일)은 전부 프로젝트 설정에서 읽는다.

- 프로젝트 설정: `docs/projects/<project-id>/project.json` — `prd_path`, `brief_path`, `system_brief_path`, `artifact_root`, `domain_terms`(코어 누출 검사용)만 둔다. **target(파일 URL·페이지·프레임)은 여기에 복제하지 않는다** — target의 권위 있는 원장은 `brief.md`의 `target` 블록 하나다.
- 과제 전용 스킬(예 `wedding-scheduler-figma`)은 project-id를 고르는 얇은 래퍼다. 전용 스킬 안에 파일 키·노드 ID를 상수로 적지 않는다 — 원장과 어긋나는 순간 다른 파일에 쓴다.
- **도메인 누출 금지**: 이 파일과 `templates/`에는 특정 프로젝트의 화면명·상태값·색·인명이 들어가면 안 된다. `scripts/harness/check_contracts.py`가 `domain_terms`로 검사한다. 예시가 필요하면 "예: …"로 표시하고 프로젝트 문서로 옮긴다.
- 다른 도메인으로 바꿀 때는 project.json·PRD·원장·`_system`을 새로 만들고 코어는 그대로 쓴다. 이전 프로젝트의 `_system/brief.md`(색·상태 어휘)를 상속하지 않는다. 등록된 프로젝트 목록은 `docs/projects/`.

## 온보딩 O단계 — 게이트보다 먼저, 프로젝트를 받아들이는 절차

새 프로젝트·새 클라이언트·새 세션 드라이버가 들어올 때 **한 번** 돈다. 산출물은 `design/<project-id>/onboarding.md`(양식 `templates/onboarding.md`)와 GATE `stage: onboarding`. 이게 없으면 G-1로 가지 않는다 — 과거에 온보딩 없이 시작해 target을 에이전트가 임의로 만들고, 3막 순서가 뒤집히고, 인터뷰 스킬 이름을 추측한 일이 있었다(`docs/harness-lessons.md` L1·L20·L25).

| # | 확인 항목 | 어떻게 | 실패 시 |
|---|---|---|---|
| O-1 | **누가 결정하나** — 클라이언트(승격·LOCK 권한), 디자이너(판단기준 승격), 오너(제출본 결정)의 역할과 연락 경로 | 사람에게 묻고 `onboarding.md` 역할표에 적는다. 한 사람이 겸해도 역할별로 적는다 | 결정자 미정 → `BLOCKED`, 미해결 결정 이름 "결정자 미지정" |
| O-2 | **프로젝트 설정** — `docs/projects/<id>/project.json` 존재, PRD 경로·길이(≥200B), `domain_terms`, `interview.audiences`, `interview.skill` | `python scripts/harness/check_contracts.py <id>` ERROR 0 | 없으면 템플릿에서 만들고 사람이 값 확인 |
| O-3 | **모드와 시작 막** — plan-only/build/review/improve, 그리고 M/W/I/U 중 어디서 시작하나. 이미 만들어진 산출물(Figma 화면·HTML·문서)이 있으면 **막 상태표**로 정리하고 LOCK 유무를 적는다 | 기존 산출물은 "있음/LOCK 없음"으로 등록. 있다고 해서 LOCK된 것으로 치지 않는다 | — |
| O-4 | **대상 파일** — Figma URL을 사람이 주는가, 새로 만드는가. 새로 만들면 첫 보고에 URL 제시 + 가정 로그 "높음" | G-3 사전 확인 | URL 없고 생성 권한도 없음 → plan-only만 |
| O-5 | **도구 실측** — `/mcp` 상태, Figma MCP 5능력(읽기/속성/렌더/쓰기/변수), 인터뷰 스킬 MCP 연결(A/B/C 경로), 한도 잔량 | `docs/figma-mcp.md` 표 갱신, `docs/integrations/*` 경로 확인 | 인증 필요 → 사람에게 `/mcp` 요청, 멈춤 |
| O-6 | **입력 자산 인벤토리** — 기존 레퍼런스·브랜드 가이드·기존 화면·더미 데이터 규칙(실명 금지)·기준일 | `onboarding.md` 자산표. 있는 것은 `실측`, 없는 것은 "없음"으로 — 추측으로 채우지 않는다 | — |
| O-7 | **작업 약속** — 라운드 상한(기본 3), 컨펌 채널·응답 대기 시간, 검증 격리 수준(도구 제한 가능 여부), 커밋·푸시 브랜치 | 사람과 합의해 적는다 | — |
| O-8 | **온보딩 재진술** — 위 내용을 짧은 문장 7~8개로 재진술하고 사람이 "맞다/틀린 줄 번호"로 답한다(ooo restate 방식) | 승인 원문을 GATE `stage: onboarding`의 근거로 | 틀린 줄 수정 → 재진술 반복 |

- 온보딩은 **질문지가 아니라 재진술**로 끝낸다 — 사람이 처음부터 다 적게 하지 않고, 에이전트가 읽을 수 있는 것(레포·Figma·설정)을 먼저 읽고 정리한 뒤 틀린 것만 고치게 한다.
- 드라이버가 바뀌면(세션·사람) `onboarding.md`의 인수인계 표에 한 줄 추가하고 O-3·O-5만 다시 확인한다. 전체를 다시 돌리지 않는다.
- 온보딩에서 모은 값 중 판단기준·기준값은 **여기서 확정하지 않는다** — 원장(brief)의 몫이다. 온보딩은 "누가, 무엇으로, 어디서부터"만 잠근다.

## 디자인 프로세스 — 4막 + 단계별 확정 잠금

UI 디테일을 먼저 그리면 인터뷰가 색·폰트 얘기로 흘러 **기능이 맞는지**를 아무도 검증하지 못한다. 반대로 UX를 다 확정하고 나서 무드를 잡으면 무드가 UX를 다시 흔든다. 그래서 **무드 → 와이어프레임 → 기능 인터뷰 → UI 상세** 순서로 나누고, 막마다 클라이언트 확정을 **잠금(LOCK)**으로 기록한다. (디자이너 피드백 원문 2026-09-05: "디자인 무드부터 잡는다", "와이어프레임은 일단 html 레벨에서 먼저. 중간에 컨펌", "client가 이미 좋다고 했으면 UX 레벨에서 크게 변경하는 상황은 피하고 싶다 — divide and conquer로 단계적으로 확정", "곧이곧대로 믿지 말고 유사한 스타일로 2~3번 다시 찔러본다")

| 막 | 이름 | 매체 | 산출물 | 확정 잠금 | 사람 개입 |
|---|---|---|---|---|---|
| **M** | 디자인 무드 | 레퍼런스 이미지(HTML 갤러리 또는 URL) 1개씩 | `brief.md` 시각 언어 섹션 + 무드 보드(3~5개 채택 레퍼런스) | `LOCK-M` 무드 어휘·채택/기각 레퍼런스 | 반응 원문 + "왜" 되묻기 |
| **W** | 와이어프레임 (UX) | **① HTML 로우파이(클릭 가능)** → 중간 컨펌 → **② Figma `W Wireframes`** | HTML 파일 + Figma W 화면 + notes | `LOCK-W` 화면 목록·순서·CTA 목적지 | 컨펌 2회(HTML, Figma) |
| **I** | 기능 인터뷰 | W 화면 + 시나리오 과제 | `interview.md` | `LOCK-I` 요구 계약·해석 승격 결과 | **필수** |
| **U** | UI 상세 | Figma `03 Screens` 토큰·컴포넌트 | 하이파이 + A/C/V | `LOCK-U` 최종 승인 | 최종 판단 |

### 확정 잠금(LOCK) 규칙 — 확정된 것은 나중에 흔들지 않는다
- 막이 끝나면 `decisions.md`에 `LOCK-<막>` 블록을 append: 무엇을 확정했나(목록), 누가(역할), 언제, 근거 원문.
- **잠긴 항목은 뒤 막에서 변경 제안을 하지 않는다.** 뒤 막에서 잠긴 항목이 틀렸다는 증거가 나오면 "변경"이 아니라 **`UNLOCK 요청`**을 사람에게 낸다 — 이유·영향 범위·비용(재작업 막 수)을 적고, 사람이 승인해야 풀린다. 에이전트가 조용히 되돌리지 않는다.
- UNLOCK은 라운드 카운터를 증가시킨다(상한 3). 같은 항목을 두 번 UNLOCK하면 요구 해석 자체가 틀린 것 → 0단계 에스컬레이션.
- 잠금 전 컨펌은 **한 번에 하나의 막만** 묻는다. "무드도 괜찮고 화면도 괜찮죠?"처럼 두 막을 한 질문에 섞지 않는다.

### 되묻기 규칙 — 클라이언트 말을 곧이곧대로 믿지 않는다 (M·W·I 공통)
클라이언트의 첫 반응("따뜻해 보여요", "좋아요")은 라벨이다. 라벨을 기준으로 승격하지 않고 **같은 성질의 레퍼런스·변형 2~3개로 다시 찔러본다.**
1. 첫 반응 원문 기록 → "왜 좋으세요?" 한 번.
2. 답에서 나온 단어(예: "따뜻", "친근", "라운드")를 **같은 축의 유사 레퍼런스 2~3개**로 시험한다 — 라운드가 더 큰 것 / 라운드는 같고 색만 차가운 것 / 라운드 없고 따뜻한 색만인 것. 어느 것에서 반응이 꺾이는지가 진짜 기준이다.
3. 세 번 모두 같은 방향이면 후보 → 승격 질문. 갈리면 갈린 지점을 원문으로 기록하고 기준을 더 좁게 쓴다.
4. 되묻기 기록 열(`probe-1/2/3`)이 비어 있는 후보는 승격 질문을 하지 않는다.
- 인터뷰 진행 자체는 프로젝트 설정 `interview.skill`에 지정한 인터뷰 스킬로 한다. 기본 어댑터는 Ouroboros `ooo interview`(`docs/integrations/ooo-interview.md`) — 그 `references` 대비 질문이 0-2의 5축과 같고, `refine_answer`가 probe-1, 유사 변형 cue 추가가 probe-2/3, `restate` 승인이 LOCK 근거가 된다. ooo의 자동 기본값·`seed-ready`는 쓰지 않는다. 지정이 없으면 위 되묻기 규칙과 0-2 루프를 수동으로 쓴다. 어떤 스킬·경로를 썼는지 `interview.md` 머리에 적는다.

### M막 규칙
- 0단계 0-2 루프와 같은 진행이지만 **시각 언어(원장 섹션 4)만** 조준한다. 구조·기능 얘기가 나오면 원문만 기록하고 W막으로 넘긴다.
- 레퍼런스는 HTML 갤러리(스크래치 디렉터리 또는 Artifact)로 1개씩 보여 준다. 이미지 출처·URL·라이선스 메모를 함께 남긴다(`templates/reference-review.md`).
- 산출물: 채택 레퍼런스 3~5개 + 기각 레퍼런스와 기각 이유 원문 + 무드 어휘(예: "따뜻·친근·라운드, 딱딱한 폰트 아님") → `brief.md` 시각 언어. **토큰 값(HEX·폰트명)은 여기서 정하지 않는다** — 어휘와 레퍼런스만 잠근다. 값은 U막에서 어휘에 맞춰 고르고 실측한다.

### W막 규칙
- **① HTML 로우파이 먼저.** 프로젝트 `process.wireframe_html_dir`에 화면당 1개 HTML(회색 박스·실제 문구·CTA는 다음 화면으로 링크). 클라이언트가 클릭해 보고 **중간 컨펌**. 이 HTML은 검증 매체이며 산출물이 아니다 — 이 하네스의 "코드로 UI를 만들지 않는다" 규칙의 명시적 예외.
- 컨펌 원문을 받고 되묻기 규칙을 적용한 뒤 **② Figma `W Wireframes`**에 옮긴다. W 화면은 U 화면과 **1:1 대응**(같은 `S<nn>`). W가 흐름의 원장이다.
- W 컴포넌트(`WF/*`)는 회색 1~3단계만. `_system` 토큰 바인딩 금지 — 바인딩하면 클라이언트가 색을 평가하기 시작한다(M막에서 잠근 무드 어휘도 W에는 넣지 않는다).
- 각 W 화면 notes에 목적 / CTA 목적지 / 까다로운 경우 / 인터뷰 질문 1~3개.
- W막 종료 GATE(`stage: wireframe`)에 HTML 컨펌 원문·Figma 컨펌 원문·V-1/V-2/V-3 자체 점검이 있어야 `LOCK-W`.

### I막 규칙 — 표상이 아니라 체험
- 대상은 project.json `interview.audiences`별 최소 1명. 실제 사람이 없으면 **페르소나 시뮬레이션 Agent**(신규 컨텍스트, PRD §사용자 상황만 받음)로 대체하되 "시뮬레이션"이라고 명시 — 실제 인터뷰와 같은 급으로 승격 근거가 되지 않는다.
- W 화면을 순서대로 보여 주고 **시나리오 과제**를 준다. 라벨 질문 금지. 막힌 지점·되돌아간 지점·틀린 예상을 원문으로. 되묻기 규칙 적용.
- 기록 → 증류(`GAP-F` 기능 갭 / `GAP-X` 흐름 갭 / 해석 정정) → 승격은 사람.
- **LOCK-W와 충돌하는 갭**이 나오면 UNLOCK 요청으로 낸다. 조용히 W를 고치지 않는다.
- I막 종료 GATE(`stage: interview`) PASS + `LOCK-I` 후에만 U막.

### U막
기존 제작-L/S·A·C·V 그대로. 시작 시 `LOCK-W`의 화면 목록·CTA와 대조하고, 토큰 값은 `LOCK-M`의 무드 어휘에서 고른다(값 선정 소스=`가정(위임)`, 측정 소스=`실측`). U에서 UX 변경 제안 금지 — UNLOCK 요청만.

**라우터 추가 행**: `LOCK-M 없음 → M막` / `LOCK-W 없음 → W막(HTML → Figma)` / `interview.md 없음 또는 LOCK-I 없음 → I막` / `LOCK-I 있음 → U막(제작단계)`. `plan-only`는 M·W까지, `review`는 U 검증만.

## 게이트 — 라우터보다 먼저 통과시킨다

라우터가 파일 존재로 분기하므로, 무엇을 어디서 볼지 먼저 확정해야 한다. 넷 다 통과하지 못하면 다음으로 가지 않는다.

**G-1. 산출물 루트 확정.**
기본값 `<cwd>/design/<project-id>/`(project.json의 `artifact_root`). 이미 있으면 그것을 쓰고, 없으면 사람에게 확인하고 만든다.
★ **이 경로를 세션 내내 고정한다.** 중간에 바뀌면 이전 `decisions.md`를 못 찾아 라운드 1로 재시작하고, 그 순간 재시도 카운터와 반복실패 판정 근거가 함께 사라진다.

**G-2. 템플릿 복사.**
산출물 루트에 `brief.md`·`decisions.md`가 없으면 이 스킬 레포 루트의 `templates/`에서 복사한다(스킬 파일 기준 상위 경로다 — `.claude/skills/` 아래가 아니다). **이미 있으면 복사하지 않는다.**

**G-3. 대상 Figma 파일 확정.**
파일 URL·페이지·프레임을 사람에게 묻고 `brief.md`의 `target` 키에 기록한다. 이게 없으면 제작·A·C단계가 무엇을 대상으로 하는지 알 수 없다.
- 사용자가 URL을 주지 않아 에이전트가 새 파일을 만들었으면 **가정 로그에 "확인 필요: 높음"으로 남기고, 첫 보고에서 URL을 사용자에게 보여 준다.** 제작이 한참 진행된 뒤 사용자가 다른 파일을 지정하면 재현 비용이 두 배가 된다(실제 발생: 1차 제작본과 사용자 지정 파일이 갈라져 두 파일에 나뉘어 존재).
- **같은 파일에 쓰는 세션은 하나만.** 다른 에이전트·세션이 같은 파일에 쓰고 있다는 징후(내가 만들지 않은 노드가 생김, 컴포넌트가 이미 존재)가 보이면 쓰기를 멈추고 사람에게 어느 세션이 소유자인지 묻는다. 두 세션이 같은 스크립트를 병렬로 돌리면 컴포넌트가 중복 생성되고 하나는 크기 버그를 안은 채 남는다.
- target이 바뀌면 이전 파일의 node ID를 재사용하지 않는다. `brief.md`에 `backup:`으로 이전 파일을 남기고 어느 파일이 제출본인지 **미해결 결정의 이름**으로 적는다.

**G-4. Figma MCP 스모크 테스트.**
`docs/figma-mcp.md`의 실측 절차를 통과시킨다. **미통과면 여기서 멈춘다.** 인증은 `/mcp` 슬래시 커맨드로만 가능해 **에이전트가 수행할 수 없다** — 사람에게 요청한다. 0·B단계를 먼저 돌고 나서 인증 벽에 부딪히면 그 작업이 낭비된다.
- 실측 결과는 `docs/figma-mcp.md`의 표에 **읽기 / 노드 속성 / 렌더 / 쓰기 / 변수·스타일 조작** 다섯 능력으로 나눠 기록한다. 하나라도 없으면 해당 단계의 폴백을 함께 적는다.
- **429·한도 초과는 자동 재시도하지 않는다.** 원인·시각·재개 조건을 `decisions.md`에 적고 사람에게 보고한다. 검증 Agent가 한도로 중단되면 그 항목은 `BLOCKED`(판정 불가)다 — PASS도 FAIL도 아니다.

## 인수인계 GATE — 단계 사이에 반드시 남기는 블록

각 단계가 끝날 때 `decisions.md` 현재 라운드 끝에 아래 YAML 블록을 **append**한다(양식: `templates/contracts/gate.yaml`). 다음 단계는 이 블록의 `output_refs`가 실재하는지, `target_ref`가 `brief.md` target과 같은지 확인한 뒤에만 시작한다.

```yaml
stage: build-screens            # requirements | align | diverge | build-library | build-screens | verify-A | verify-C | verify-V
mode: build
project_id: <project-id>
run_id: <세션 시작 시 고정>
revision: 1.2                   # 라운드.하위라운드
producer: <세션/에이전트 식별>
target_ref: <brief.md target의 file_key + page>
input_refs: [<경로>, ...]
output_refs: [<경로 또는 node ID>, ...]
status: PASS                    # PASS | PARTIAL | FAIL | BLOCKED
blockers: []                    # 미해결 결정의 이름
next_stage: verify-A
```

- `PASS`라는 글자만으로 통과하지 않는다. `output_refs`가 없거나 target이 다르면 `BLOCKED`로 되돌린다.
- `PARTIAL`은 진행 보고다. 의존 단계를 여는 승인이 아니다.
- `BLOCKED` = 증거·권한·결정이 없어 판정 자체를 못 한 것. `FAIL` = 검사했는데 위반. 둘을 섞지 않는다 — 검증 Agent가 한도 초과로 죽은 것은 `BLOCKED`다.
- 제작 세션과 검증 세션의 `producer`가 같으면 검증 입력으로 받지 않는다(절대 규칙 4의 기계적 검사).

## 검증 Agent 배선 — A·C단계 공통

"별도 Agent로 띄운다"는 문장만으로는 격리가 되지 않는다. 네 가지를 배선으로 지킨다.

**① 컨텍스트를 상속하는 Agent를 쓰지 않는다.** `fork` 계열(부모 대화 이력을 물려받는 종류)은 금지다. 그 문장은 fork로도 문자상 충족되지만, 그 순간 격리가 조용히 무력화된다. 신규 컨텍스트 Agent만 쓴다.

**② 같은 세션에서 "이제 검증자 관점으로 보겠습니다"로 대체하지 않는다.** 이건 격리가 아니라 역할극이다.

**③ 검증 Agent에게 파일 탐색을 허용하지 않는다.** 프롬프트에 `decisions.md`를 넣지 않는 것만으로는 부족하다 — Read·Glob이 있으면 검증 Agent가 스스로 찾아 읽는다(산출물이 같은 폴더에 나란히 있어 한 번에 발견된다). **필요한 파일만 절대경로로 지정하고, 그 외 탐색을 하지 말라고 명시한다.**

**④ 검증 Agent는 수정하지 않는다.** 판정만 낸다. 고치는 것은 제작 주체의 일이다.

**⑤ 격리 강제 수준을 기록한다.** 프롬프트에 "탐색 금지"라고 쓴 것과 도구 자체를 막은 것은 다르다. 검증 보고 머리에 `격리: 프롬프트 지시만 / 도구 제한 적용 / 별도 작업 디렉터리` 중 하나를 적는다. 프롬프트 지시만인 상태를 "물리적 격리"라고 보고하지 않는다.

**⑥ 검증자의 "참고 관찰"은 버리지 않는다.** 판단기준 밖이라 판정하지 않은 관찰(예: 화면 간 더미 데이터 인물 불일치, 카운트와 카드 수 불일치)은 `decisions.md`에 원문으로 남기고, 제작 주체가 **데이터 정합 수정**으로 라우팅한다. 판정 기준으로 승격하는 것은 여전히 사람만 한다.

### 0-1. 원장과 수렴 판정 — 우연에 의한 수렴 금지

`brief.md` 맨 위의 「수렴 판정표」가 원장이다. 필수 섹션 9개(target / 화면 목적·사용자 / 화면 요소 목록 / 시각 언어 / 구조·워크플로 / 인터랙션 품질 / 거부할 가정 / A단계 기준값 / C단계 판단기준) 각각이 다음 넷 중 하나로 해소되어야 0단계가 끝난다.

| 해소 클래스 | 뜻 | 요건 |
|---|---|---|
| **사람** | 디자이너·클라이언트가 직접 말했다 | 반응 원문이 근거로 연결되어야 한다 |
| **실측** | 기존 Figma 라이브러리·파일에서 읽었다 | 증거 경로(변수·스타일 이름)를 남긴다. 무제한 탐색 금지 — 대상 파일 안에서만 |
| **가정** | 안전한 기본값으로 닫았다 | 근거 서술 필수. **사람이 명시적으로 생략·위임을 선택한 경우에만** — 에이전트가 스스로 기본값으로 닫는 것은 금지다. 전문가의 미답을 기본값으로 닫으면 안목 추출이 무효화된다 |
| **차단** | 사람 권한이 필요한데 아직 답이 없다 | 미해결 결정의 이름을 명시하고 **멈춘다** |

- **완료 = 차단·충돌·미기입이 0이고 나머지가 전부 사람/실측/가정.** "반응을 몇 개 받았는가"는 완료 조건이 아니다 — 열린 갭이 소진됐는가가 조건이다.
- **충돌 처리**: 같은 키에 값이 둘이면 소스 우선순위(사람 > 실측 > 가정)로 푼다. 같은 급끼리 충돌하면 지어내서 고르지 않고 충돌 상태로 표시해 사람에게 보여준다.
- 갭의 우선순위 = 판정표의 행 순서. 항상 첫 번째 열린 갭부터 조준한다.

### 0-R. 레퍼런스 조사·검수·추출 — 인터뷰 앞의 필수 절차

레퍼런스는 앱 이름이 아니라 **출처가 확인된 화면·상태·흐름** 단위로 다룬다. 인기·설치 수는 배경 정보이며 디자인 채택 근거가 아니다. 이 절차의 계약은 `templates/reference-review.md`다. 기존 0-2의 사람 인터뷰와 승격 권한은 그대로 유지한다.

**하네스 유지보수·레퍼런스 조사만 요청한 경우**: Figma 제작 세션을 시작하지 않는다. 조사 보고서와 절차·템플릿을 작성하며 G-3/G-4, B 후보 생성, A/C 제작 검증은 실행하지 않는다. 프로젝트 디자인의 승인·완료로 보고하지 않는다. 실제 디자인 세션에서는 모드에 해당하는 게이트를 그대로 적용한다.

1. **조사 질문 고정**: 열린 갭과 사용자가 수행할 과업을 적는다. 같은 과업의 화면끼리 비교한다. 다른 과업의 레퍼런스는 비교 순위에 섞지 않고 보조 자료로 표시한다.
2. **소싱·동일성 확인**: 공식 사이트·앱스토어에서 제품명, 개발사, 패키지/앱 ID, URL, 열람일, 확인 가능한 버전·플랫폼을 기록한다. 블로그는 발견 경로 또는 보조 관찰로 표시한다. 접근 실패·동명이인·오래된 버전은 사실대로 남긴다.
3. **증거 확보**: 원본 전체 화면과 추출 영역을 연결한다. 공식 소개문, 스토어 홍보 화면, 직접 실행 화면, 직접 실행 흐름을 구별한다. 이미지가 없으면 시각 품질은 미검증, 클릭하지 않았으면 인터랙션은 미검증이다. 스크린샷으로 토큰·폰트·간격·컴포넌트 구조를 실측했다고 주장하지 않는다.
4. **독립 증거 검수**: 수집자와 다른 신규 컨텍스트 검수자가 출처·화면·주장의 일치를 확인한다. 「검증 Agent 배선」의 탐색 제한·수정 금지·격리 수준 기록을 적용한다. 지정된 증거와 조사 질문만 주고 수집자의 추천·사람 선호·decisions.md는 주지 않는다. 출력은 주장별 `SUPPORTED / CONTRADICTED / UNVERIFIED`와 근거 위치다. 검수자를 사용할 수 없으면 `미실시`로 남기며 스스로 검수 완료를 선언하지 않는다.
5. **사람에게 한 개씩 제시**: 0-2의 원문 반응·5축 질문을 실행한다. 에이전트는 채택/보류/제외를 **추천**할 수 있지만, 최종 선택은 사람이 한다. 제품 전체 채택과 개별 요소 채택을 혼동하지 않는다. 이유와 적용 범위를 원문으로 남긴다.
6. **요소 추출**: 채택한 범위에서 관찰 → 작동 원리 가설 → 우리 과업에 적용할 방식 → 가져오지 않을 것 → 필요한 상태 → 검증 방법을 적는다. 산출물은 B 후보가 아닌 패턴·기준 후보다. 신규 판단기준은 0-2에서 사람이 별도로 승격해야 한다.
7. **추적 연결**: `REF → 증거 → 사람 반응 → 선택 → PATTERN → CRITERION → 화면/컴포넌트 → A/C/흐름 검증`의 ID를 기록한다. 제외 항목도 보존하고 재검토 조건을 남긴다. 변경은 이력 추가 방식으로 기록한다.

**두 종류의 상태를 분리한다.** 증거 검수 통과는 디자인 채택이 아니다. 사람의 취향상 채택도 미확인 기능을 사실로 만들지 않는다. 증거 부족 항목을 제외로 자동 변환하지 말고 보류 사유를 남긴다. 자동 총점·가중치·채택 커트라인은 만들지 않는다.

**0-R 인수인계 조건**: 다음 단계가 사용하는 항목마다 증거 범위, 독립 검수 결과, 사람의 선택과 이유, 적용 범위, 패턴 ID가 있어야 한다. 정성 기준은 별도 승격 기록까지 필요하다. 부족하면 해당 의존 항목만 `BLOCKED`로 기록한다. 관계없는 조사·문서화는 계속할 수 있다. 미답·검수 미실시를 승인으로 간주하지 않는다. 참조가 없는 사람 직접 요구는 그 원문을 별도 근거로 사용할 수 있다.

**이후 단계 연결**: B에는 승인된 추출 패턴과 확정 기준만 전달한다. 제작 기록에는 적용된 패턴 ID와 실제 노드 ID를 매핑한다. A는 실제 노드 속성을 검사하고, C는 확정 기준과 제작 렌더만 받는다. C에 경쟁 앱 추천 사유를 넘기지 않는다. 실제 흐름의 유효성은 클릭·상태 전환 증거로 별도 확인한다.

### 0-2. 레퍼런스 인터뷰 루프 — 5축 대비 질문과 승격

1. **열린 갭 확인** — 판정표에서 첫 번째 미해소 섹션을 본다.
2. **그 갭을 줄일 레퍼런스 1개**를 0-R의 증거·검수 기록과 함께 제시한다. 한 번에 하나씩 — 여러 개를 한꺼번에 주면 상대가 비교 모드로 들어가 개별 반응이 흐려진다. 증거 범위와 미검증 사항을 함께 보여 준다.
3. 자유서술 반응("좋다/싫다 + 왜")을 받고 **원문 그대로** 기록한다. 요약 금지 — "산만하다"와 "정보가 많아 부담된다"는 다른 기준을 가리킨다.
3-b. **되묻기**(「디자인 프로세스」의 되묻기 규칙): 반응에서 나온 단어를 같은 축의 유사 레퍼런스 2~3개로 다시 시험한다. 되묻기 기록이 없는 후보는 6의 승격 질문으로 가지 않는다.
4. **5축 대비 질문**으로 심화한다 — "이 레퍼런스에서 우리가 **무엇을 복사하고 무엇을 피해야** 하나요?"를 다섯 축으로 나눠 묻는다: ① 표면 룩앤랭귀지 ② 워크플로·구조 ③ 인터랙션 품질 ④ 원하는 결과 ⑤ 거부할 가정. 라벨을 묻는 게 아니라 눈앞의 구체물에 대한 대비를 묻는 것이므로 표상 금지 원칙과 충돌하지 않는다. 다섯 축의 답이 원장 필수 섹션 2·4·5·6·7에 그대로 꽂힌다.
5. **증류**: 반응에서 판단기준 후보를 뽑아 「판단기준 원장」에 **후보 상태로** 기입한다. 후보는 태생이 확인 대기다.
6. **확인·승격**: 후보를 디자이너에게 보여 승격/기각을 받는다. **승격된 것만 판단기준(확정)이 된다.** 기각돼도 반응 원문은 보존한다. 증류는 에이전트가 하되 승격 권한은 사람에게만 있다 — 이것이 "에이전트가 판단기준을 채우면 오염"의 기계적 구현이다.
7. 판정표를 갱신하고 1로 돌아간다. 수렴하면 종료.

### 0-3. 스톨 감지 — 개수가 아니라 갭을 조준한다

다음 신호가 보이면 루프가 헛돌고 있는 것이다.
- 디자이너의 반응이 같은 뜻의 generic 답 반복("글쎄요, 그냥 좋아요")
- 인터뷰어의 질문이 광범위 질문으로 흐름("또 뭐 있나요?", "더 보여드릴까요?")
- 새 레퍼런스를 보여줘도 열린 갭이 줄지 않음

대응: 다음 레퍼런스를 무작위로 고르지 말고 **최우선 열린 갭을 정면으로 줄이는 레퍼런스**를 고른다(예: 인터랙션 품질이 비었으면 인터랙션이 대비되는 레퍼런스). 두 번 연속 갭이 줄지 않으면 그 갭의 이름을 명시하고 사람에게 직접 묻는다.

### 소스 어휘를 더 쪼갠다 — "PRD 원문"과 "PRD에서 도출한 해석"은 다른 소스다

원장의 소스 열에 `사람`이라고만 쓰면 PRD가 실제로 요구한 것과 에이전트가 PRD를 읽고 만들어낸 디자인 해석이 섞인다(실제 사례: PRD가 "두 사용자 집단을 따로 관리한다"고만 했는데 "두 집단을 항상 **색으로** 구분"이 `사람` 소스로 확정 처리됨 — `docs/harness-lessons.md` L13). 그래서 소스는 다섯 가지다.

| 소스 | 뜻 | 확정 가능? |
|---|---|---|
| `사람-원문` | PRD·디자이너 발화의 원문 그대로 | 예 |
| `사람-해석` | 원문에서 에이전트가 도출한 디자인 결정 | **아니오** — 후보. 사람이 승격해야 확정 |
| `실측` | Figma 파일·라이브러리에서 읽은 값 | 예 (증거 경로 필수) |
| `가정(위임)` | 사람이 명시적으로 생략·위임한 항목의 기본값 | 예(가정 상태) |
| `차단` | 사람 권한 필요, 미답 | 아니오 |

에이전트가 만든 토큰을 Figma에 넣고 다시 읽었다고 `실측`으로 바꾸지 않는다 — 그 값의 **선정 소스**는 `가정(위임)`이고 **측정 소스**만 `실측`이다. `brief.md` 토큰 표에 두 열을 따로 둔다.

### 기준값 공급원 분리 — 증류로 만들 수 없는 것이 있다

- **기존 디자인 시스템이 있으면 증류하지 않는다.** "우리 서비스"처럼 기존 파일·라이브러리가 있는 경우, 팔레트·타이포·네이밍은 **Figma의 변수·스타일·컴포넌트 라이브러리를 실측해** 채운다(소스=실측, 증거 경로 필수).
- **5축 증류는 정성 기준에만 쓴다**(밀도 선호, 무드, 회피할 클리셰 등).
- **정량 임계값**(그리드 단위, 재사용률 하한)은 **실측 또는 사람 입력**이다. 자유서술에서 임계값을 만들면 그게 곧 추측이고 절대규칙 1 위반이다.

### 탈출구 — 사람이 생략을 선택할 때

"그냥 만들어줘"라고 하면 교착하지 않는다. **사람의 명시적 선택으로** 미해소 섹션들을 가정("요구사항 정렬 생략 — 판단기준 미수집")으로 닫고 B단계로 간다. 그 결과 A·C단계 대부분이 SKIP이 되고, 검증이 거의 없었다는 사실이 원장과 최종 보고에 남는다. 에이전트가 생략을 먼저 제안할 수는 있으나 선택은 사람이 한다.

**산출물**: `brief.md` (원장)

## B단계 — 발산·수렴

어떻게 만들지에 정답이 하나가 아닐 때.

**스킵 경로 — 축 분기가 불필요한 경우**: 사람이 이미 명확한 스펙을 줬거나 정답이 하나라면, `decisions.md` 라운드 1에 **"축 분기 불필요 — 사유: …"**를 적고 선택 완료로 간주해 제작단계로 간다. 이 경로가 없으면 라우터가 B단계를 벗어날 방법이 없어 순환한다(후보를 만들려면 B를 실행해야 하고, B를 벗어나려면 후보가 있어야 한다).

- 축은 2~4개. **독립성 검사**: 한 축의 값을 바꿔도 다른 축이 따라 바뀌지 않아야 한다. 따라 바뀌면 한 축이다 — 합친다.

### B-1.5 운영 메모 — 대표 시안 N개 + 외부 평가 하네스 (2026-09-05 사용자 요청, 기준 대기)

사용자가 "대표 시안 3개씩 빠르게 만들고 평가·검수 하네스로 좋은 방향을 선택"하기를 원한다. B-2/B-3의 배선은 그대로 쓰되 다음을 적용한다.

## 제작단계 — 선택된 후보를 Figma에 만든다

**주체**: 메인 세션 또는 전용 Agent 1개. B-2의 후보 생성 Agent들이 만들지 않는다.

**입력**: `brief.md`(토큰·`target`) + `decisions.md`의 선택된 축 조합 + 아래 화면 요소 목록

**화면 요소 목록** — `brief.md` 원장의 「화면 요소 목록」에서 읽는다(0단계 필수 섹션 3번). 비어 있으면 — 0단계를 생략·축약한 경로 — 여기서 사람에게 확인해 원장에 채우고 진행한다. 미확정 요소는 가정 로그에 명시한다.

**네이밍**: `brief.md`의 `naming.convention`을 제작 시점에 지킨다. A-5가 나중에 이걸 검사하므로, 지키지 않으면 A단계에서 반드시 FAIL한다.

**제작 순서 — 라이브러리(L)와 화면(S)을 나눈다**
1. **제작-L**: 변수·텍스트 스타일 → 아이콘 → 원자 컴포넌트 → 복합 컴포넌트. 끝나면 컴포넌트 세트 이름·ID·배리언트 목록을 `decisions.md` 제작 기록에 적고, **독립 읽기(`get_metadata` 또는 읽기 전용 스크립트)로 실재를 확인**한 뒤 S로 간다. 자기 제작 보고("만들었다")를 실재 확인으로 치지 않는다.
2. **제작-S**: 승인된 화면을 L의 인스턴스로 조립한다. 화면마다 `use_figma` 1회. 컴포넌트 ID가 없는 화면 조립은 시작하지 않는다.
3. 화면을 만들 때 **같은 구조가 두 번 이상 반복되면 그 자리에서 컴포넌트로 승격**한다(섹션 헤더, 리스트 행, 타일). 나중에 승격하면 인스턴스 치환 과정에서 텍스트를 잃기 쉽다(실제 발생: 원본 프레임을 지운 뒤 텍스트를 읽어 크래시).

**Figma Plugin API 실전 함정 — 제작 스크립트에 반드시 반영**
- `FRAME`에는 `description`이 없다(COMPONENT만). 화면 설명은 프레임 아래 `"<화면명> · notes"` 텍스트 노드로 남긴다.
- `resize()`는 auto-layout의 hug를 FIXED로 되돌린다. 고정 폭 컴포넌트는 `resize(w, 10)` 뒤 **반대 축을 다시 AUTO로** 설정한다. 이걸 빠뜨리면 높이 10px 컴포넌트가 생긴다.
- `combineAsVariants(nodes, parent)`는 nodes와 parent가 **같은 페이지**에 있어야 한다. 실패하면 그 호출 전체가 롤백되니 컴포넌트 생성과 화면 치환을 한 호출에 섞지 않는다.
- 인스턴스로 치환할 때는 **원본을 지우기 전에 텍스트·속성을 변수에 복사**한다.
- 화면 프레임이 고정 높이(390×844)면 `content`가 잘린다. 화면마다 `content.children` 높이 합 + 패딩 + gap을 계산해 프레임 높이와 비교하는 검사를 스크립트 끝에 넣고, 넘치면 항목을 줄이거나 gap을 줄인다.
- 색은 항상 `setBoundVariableForPaint`로 변수에 바인딩한다. 예외색(브랜드 컬러)은 `brief.md` exceptions에 먼저 적고 쓴다.
- 겹침 아바타 같은 음수 gap도 그리드 배수(-8)로 맞춘다. -10, -6은 A-3에서 걸린다.
- 소프트 배경 위 12~13px 라벨은 대비율 4.5:1을 거의 항상 놓친다. 토큰을 정할 때 `status/*`·`side/*`의 진한 색은 **미리 대비율을 계산**해 정한다(실제: 8개 토큰을 제작 후 다시 어둡게 조정).

**출력**
1. `target`에 지정된 위치의 프레임
2. **제작 전·후 노드 스냅샷** → `<산출물루트>/.cache/nodes-before.json`, `nodes-after.json`
   ★ A-4(재사용률)는 이 diff 없이는 계산할 수 없다. 제작 전 스냅샷을 반드시 남긴다.
3. 제작-L 종료·제작-S 종료 각각에 인수인계 GATE 블록

**스냅샷 계약 — 20KB 출력 제한 아래에서**
`use_figma`의 반환은 약 20KB에서 잘린다. 화면 11개 트리를 그대로 덤프하면 반드시 잘리고, 잘린 JSON은 A단계가 파싱하지 못한다. 그래서 스냅샷은 두 층으로 남긴다.
- **사실 파일(facts)**: 노드를 1회 순회하며 A-0~A-6 각 항목의 **위반 목록·카운트·인벤토리**를 계산해 저장한다(위반 0건이면 빈 배열). 계산 방법(대비율 공식, 배경 추정 방식, 분모 정의)을 파일 안에 적는다. A 검증 Agent의 기본 입력이다.
- **원본 트리**: 화면 2~3개 단위로 나눠 여러 호출로 덤프해 `.cache/tree-<범위>.json`으로 저장한다. 사실 파일을 못 믿을 때 검증자가 재검산하는 용도다. 시간이 없어 못 남겼으면 `brief.md` 검증 방식 기록에 "트리 재검산 불가"를 적는다.
- A-0은 인스턴스 내부까지 전 범위, A-1~A-6은 이번 제작 노드만(인스턴스 내부 제외)으로 **수집 범위를 파일에 명시**한다.
- 좌표 반올림·HEX 축약은 허용하되, 대비율 계산은 반올림 전 값으로 한다.

## A단계 — 구조적 사실 검증

Figma 노드 속성만으로 판정한다. 스크린샷 불필요.

**실행**: 별도 Agent(위 「검증 Agent 배선」 준수). 만든 주체는 자기 결과를 통과시키는 쪽으로 판정이 기운다.

**입력 전달**: 노드 트리를 **1회만** 조회해 `<산출물루트>/.cache/nodes-after.json`에 저장하고, Agent에는 **경로만** 준다. 프롬프트에 인라인으로 넣으면 큰 화면에서 즉시 터진다. 6항목 전부를 이 스냅샷 하나로 판정한다(항목마다 조회하면 6배가 된다).

**출력**: 항목별 `PASS` / `FAIL` / `SKIP` / `N/A`.
- `FAIL`이면 **위반 노드 경로와 실제 값을 전부 나열한다.** 개수만으로는 고칠 수 없다.
- 기준값이 비어 있으면 `SKIP(기준값 없음)`. **추측해서 판정하지 않는다.**
- 해당 개념이 이 화면에 없으면 `N/A`.

**기록**: 판정 원문을 `decisions.md`의 「검증 로그 — 하위 라운드」에 **그대로** 적는다. **요약하지 않는다** — C-라우팅의 국소/방향 구분이 이 서술에 전적으로 의존한다.

**검사 스코프 (A-1~A-6 공통)**: 이번에 만든 노드만 본다. **라이브러리 컴포넌트 인스턴스의 내부는 제외한다** — 그건 이 화면의 결함이 아니다. A-0은 예외로 전 범위를 본다.

### A-0. 고정 하한선 — `brief.md`와 무관하게 항상 판정한다. SKIP 불가

프로젝트가 무엇이든 지켜야 하는 객관적 품질 하한선이다. 사람이 기준값을 채우지 않아도 판정한다.
★ **이 항목이 없으면 기준값이 비었을 때 A단계의 검증력이 정확히 0이 된다.**

- [ ] **텍스트 대비율** — 본문 4.5:1, 큰 텍스트 3:1 미만이면 FAIL (WCAG AA). 노드 경로와 실측 대비율을 낸다. 비활성 컨트롤(disabled 배리언트) 안의 라벨은 WCAG 1.4.3 면제 대상이므로 `inactiveControl=true`로 따로 표기하고 FAIL로 세지 않는다 — 단 그 사실을 보고에 적는다. 배경이 반투명·그라데이션이라 확정 계산이 안 되면 "계산 불가"로 적고 렌더로 넘긴다. 채운 척하지 않는다.
- [ ] **누락 리소스** — 깨진 이미지, 로드 실패 폰트, 빈 이미지 fill이 있으면 FAIL.
- [ ] **자동 생성 기본명** — `Frame 427`·`Rectangle 12`·`Group 3` 같은 이름이 남아 있으면 FAIL. 프로젝트 무관 규칙이므로 `naming.convention`이 비어 있어도 판정한다(A-5와 분리한 이유다).
- [ ] **프레임 밖으로 넘친 노드** — 대상 프레임 경계를 벗어나 잘리는 노드가 있으면 FAIL. 단, `brief.md` 화면 요소 목록에 "가로 스크롤" 또는 "오버레이"로 선언된 컨테이너의 자식은 제외한다 — 선언 없이 넘치면 FAIL이다(실제: 상태 탭 칩 5개 중 1개가 342px 밖으로 나가 있었고, 선언이 없었으므로 결함으로 처리해 2줄 wrap으로 수정).

### A-4. 컴포넌트 재사용률
- **조회**: 제작단계가 남긴 **`nodes-before.json` ↔ `nodes-after.json` diff.** Figma 노드에는 "새로 만들었다"는 속성이 없으므로 diff 없이는 계산 불가다. 스냅샷이 없으면 `SKIP(스냅샷 없음)`.
- **산식(REUSE-A, 기본)**: 분자 = 이번 제작 노드 중 컴포넌트 인스턴스 수. 분모 = 이번 제작 노드 중 프레임 + 텍스트 + 인스턴스(인스턴스 내부 제외). **아이콘 벡터와 리프 도형은 제외한다** — 세면 분모가 폭발해 어떤 화면도 하한을 넘지 못한다.
- ★ 이 산식은 **레이아웃 래퍼 프레임(content, row, col)과 화면 고유 본문 텍스트를 분모에 넣는다.** 그래서 컴포넌트를 성실히 써도 40~55%에 머물기 쉽다(실측: 11화면에서 41%→컴포넌트 4종 추가 승격 후 45%). 사람이 하한을 정할 때 **어느 산식인지 함께 확인**한다. 다른 산식("반복 패턴 중 인스턴스 비율" 등)을 쓰려면 `REUSE-B`처럼 다른 ID를 붙이고 하한도 따로 받는다. 산식을 바꾸고 같은 숫자를 그대로 적용하지 않는다.
- **함께 보고**: 컴포넌트별 인스턴스 수, 남은 반복 비컴포넌트 프레임 목록(이름 기준 2회 이상), 최대 트리 깊이. 깊이의 하한·상한을 에이전트가 만들지 않는다.
- **기준**: `thresholds.component_reuse_min` + `thresholds.component_reuse_formula`
- **판정**: 하한 미달이면 FAIL. **새로 만든 노드 목록을 함께 낸다** — 그중 기존 컴포넌트로 대체 가능한 것이 실제 결함이다. 2회 연속 FAIL이면 하한이 산식과 맞지 않을 가능성을 사람에게 묻는다(A-라우팅 4).

### A-라우팅 (FAIL 시)

A단계 FAIL은 전부 **기계적으로 고칠 수 있는 것**이다(그래서 A단계다). 미적 판단이 아니므로 B로 돌아가지 않는다.

1. **제작 주체가** FAIL 항목을 수정한다. 검증 Agent는 고치지 않는다.
2. 수정 후 **A단계 재검** — 새 Agent를 다시 띄운다. 재검 Agent가 한도·429로 중단되면 `BLOCKED`로 기록하고 사람에게 재개 조건을 보고한다. 제작 주체의 자체 계산으로 대체하지 않는다.
3. 재검 횟수를 **하위 라운드 카운트**(아래)에 기록한다.
4. 같은 항목이 2회 연속 FAIL이면 기준값이 현실과 안 맞을 가능성 — 사람에게 확인한다. A-4는 특히 산식(REUSE-A)과 하한이 같은 전제인지 묻는다.
5. **수정 영향 범위**: 토큰 값이나 공통 컴포넌트를 고쳤으면 그 컴포넌트를 쓰는 **모든 화면**을 재검 대상에 넣는다. 화면 국소 수정이면 그 화면의 A + 렌더 C + 관련 V-3만 재검한다. 무관한 화면의 PASS는 유지한다.

## C단계 — 미적·게슈탈트 판단

A단계 통과 후, **반드시 스크린샷을 렌더해서** 판단한다. 개별 수치가 다 맞아도 전체가 어색할 수 있고, 그게 이 단계가 따로 있는 이유다.

**스크린샷 전달 배선** — Agent 프롬프트는 텍스트만 담으므로 이미지를 직접 넣을 수 없다.
→ 스크린샷을 `<산출물루트>/renders/r<라운드>.png`로 **저장하고, Agent에는 절대경로만 준다**(Agent가 Read로 읽는다).
→ 렌더 툴이 없으면 사람에게 수동 export를 요청한다. **C단계는 자동 실행이 원리적으로 보장되지 않는 유일한 단계다** — 그래도 스크린샷 없이는 성립하지 않으므로 이 경로는 반드시 확보한다.

### 검증자 격리 — 이 단계의 핵심 장치

「검증 Agent 배선」 ①~④를 전부 적용한다. 그 위에 입력을 제한한다.

| 주는 것 | 주지 않는 것 |
|---|---|
| 스크린샷 절대경로 | `decisions.md` — 어떤 후보를 왜 골랐는지 |
| `brief.md` 「판단기준 원장」의 **확정 상태 행만** (후보 제외) | 제작 과정·설계 의도·대화 이력 |
| 아래 체크 6항목 | 파일 탐색 권한 (스스로 찾아 읽는다) |
| A단계 판정 결과 **요약만** — 어느 항목이 PASS/SKIP인지 | A단계가 본 노드 트리·기준값 원본 |

왜: 제작 의도를 아는 검증자는 탈락 항목에서 **"의도가 이랬으니 괜찮다"로 자기변호**한다. 검증자의 무지가 검증력이다. 실제 사용자도 의도를 모르고 화면을 보므로, 검증 조건이 실사용 조건과 같아진다.

A단계 결과 요약만 주는 이유: C-3은 "수치는 A-3이 봤다"를, C-6은 "존재 여부는 A-6이 봤다"를 전제한다. A-6이 SKIP된 줄 모르면 검증자는 빈 상태가 있는지도 모른 채 C-6을 판정하거나 A-6과 중복 탈락시킨다. 항목별 PASS/SKIP만 주면 **설계 의도는 섞이지 않으므로 격리는 유지된다.**

### 판정 규칙

각 항목을 `PASS` / `FAIL + 무엇이 어떻게 보이는지 + 스크린샷 상 위치` / `SKIP(판단기준 미기재)`로 답한다.

- **판단기준이 `brief.md`에 없는 항목은 판정하지 않고 SKIP한다.** 기준 없이 PASS/FAIL을 내면 그게 곧 추측이다.
- "개선 여지가 있다" 같은 중립 표현을 쓰지 않는다 — 판정이 아니라 회피다.
- **전 항목 SKIP은 통과가 아니라 판정 불가.** 정지하고 사람에게 기준을 요청한다 — 요청 사유에 기준이 없는 항목의 이름(C-n)을 나열한다(절대 규칙 5).

**「판단기준 원장」 ↔ 아래 6항목 매핑**: 원장의 C단계 기준 행에 `C-1`~`C-6` 태그를 붙인다. 태그가 없으면 어느 항목에 걸리는지 알 수 없고, "여기 없는 기준으로 탈락시킬 수 없다"는 규칙과 결합하면 그 항목은 영구히 PASS가 된다.

### 사람 판정과 오버라이드 재유입 — 우로보로스 고리

C 검증 Agent의 판정은 제안이다. 최종 판정은 사람이 내린다(절대 규칙 2). **사람이 Agent 판정을 뒤집는 사건(오버라이드)은 버리는 게 아니라 다음 라운드의 판단기준 원석이다.**

1. **기록**: `decisions.md`의 「오버라이드 로그」에 남긴다 — 항목 / Agent 판정 / 사람 판정 / 사람이 말한 이유 **원문**.
2. **증류**: 그 이유에서 "판정을 가른 기준"을 뽑아 `brief.md` 「판단기준 원장」에 **후보**로 기입한다 — 0-2의 확인 경로와 동일하게 태생이 확인 대기다.
3. **확인·승격**: 디자이너가 승격하면 다음 C 재검과 다음 라운드부터 검증 Agent에게 그 기준이 전달된다 — 승격된 기준은 원장의 확정 행이 되므로 기존 배선 그대로 흘러간다.
4. ★ **완화 방향 자동 증류 금지.** "사람이 PASS로 뒤집었으니 이 항목은 앞으로 덜 엄격하게 보자"를 에이전트가 스스로 쓰지 않는다 — 통과가 목적이 되는 순간 검증이 무너진다. 완화든 강화든 승격은 사람만 한다.

이 고리가 있어야 라운드가 반복될수록 검증 Agent의 판정이 그 디자이너의 안목에 수렴한다 — **평가의 출력이 차세대 기준의 입력이 된다.**

## V단계 — 실재·흐름 검증 (C 통과 후, 사람 최종 판단 전)

A는 노드 속성, C는 보이는 품질을 본다. 둘 다 통과해도 **요구사항이 화면에 실제로 있는지, 화면이 이어지는지**는 아무도 확인하지 않았다. V가 그 구멍을 막는다.

**실행**: 별도 신규 컨텍스트 Agent. 입력은 ① 요구 계약(PRD 원문 위치 → REQ → 화면/상태 매핑, `templates/contracts/requirements.json` 양식) ② 사실 파일의 화면 인벤토리·노드 ID ③ 최신 렌더. `decisions.md`·제작 의도는 주지 않는다.

**판정 항목**
- [ ] **V-1 요구 커버리지** — PRD의 기능 요구 각각이 어느 화면 어느 노드에 있는가. 없으면 FAIL + REQ ID.
- [ ] **V-2 까다로운 경우 커버리지** — PRD가 "화면 어딘가에서 다뤄야 한다"고 한 경우 각각의 실재. `docs/…/screen-map` 커버리지 표의 각 셀이 실제 노드를 가리키는지 확인한다. 표에 있고 화면에 없으면 FAIL.
- [ ] **V-3 흐름 연결** — 핵심 CTA마다 (source node, 목적지 화면) 대조. 좌→우로 놓여 있다는 사실과 연결은 다르다. Figma 프로토타입 연결이 있으면 "연결됨", CTA 문구로만 표현됐으면 "표현됨"으로 기록한다. 목적지 화면이 없으면 FAIL.
- [ ] **V-4 상태 커버리지** — 요구 계약이 정한 상태(예: 도메인 enum 4종)가 각각 최소 1개 화면에 실제 인스턴스로 있는가. empty/loading/error를 기계적으로 모든 화면에 요구하지 않는다 — 요구 계약에 적힌 것만 본다.
- [ ] **V-5 데이터 정합** — 같은 엔티티(인물·모임·날짜)가 화면 간에 모순 없이 표시되는가. 더미 데이터 문서(fixtures)와 대조한다. C 검증자의 참고 관찰이 여기로 온다.
- [ ] **V-6 리소스 실재** — 화면이 참조하는 컴포넌트·변수·스타일이 현재 파일에 실제로 있는가(사실 파일의 `instanceByComponent` vs 컴포넌트 페이지 인벤토리).

**출력**: 항목별 PASS/FAIL/SKIP + 종합. FAIL은 REQ ID·화면·노드 경로를 낸다. 수정 책임: V-1/2/4는 제작-S, V-3은 제작-S(+프로토타입), V-5는 fixtures 문서 또는 제작-S, V-6은 제작-L.

## C-라우팅 (FAIL 시)

C단계는 합격/불합격이 아니라 **원인 진단**까지 낸다. `decisions.md`의 지난 라운드 탈락 항목과 이번을 대조한 뒤, 아래를 **표에 적힌 순서대로** 검사한다.

| 검사 순서 | 판정 | 조건 | 행동 |
|---|---|---|---|
| **1번째** | **반복 실패** | 후보를 바꿨는데도 직전 라운드와 **같은 항목**으로 탈락 | **0단계로 에스컬레이션.** 요구사항 해석 자체가 틀렸다는 신호다. |
| **2번째** | **방향 오류** | 표면 속성 하나를 고쳐서는 해결 불가한 구조적 문제 | **B단계로 회귀.** `decisions.md`에 새 라운드를 연다. |
| **3번째** | **국소 결함** | 표면 속성 하나의 문제 (예: 카드 간격만 불균일) | 그 속성만 고쳐 **C단계 재검.** B로 돌아가지 않는다. **하위 라운드 카운트를 증가시킨다.** |

★ 이 순서를 지켜야 한다. **반복 실패를 국소 결함으로 오진하면 같은 실패를 무한히 반복한다.** (원본 스펙의 번호는 국소=1·방향=2·반복=3이지만, **검사는 그 역순**이다. 번호 순서로 검사하지 마라.)

★ **탈락 항목이 여럿이고 판정이 엇갈리면, 가장 먼저 걸리는 판정 하나로 라운드 전체를 처리한다**(반복 실패 > 방향 오류 > 국소 결함). 항목별로 다른 행동을 동시에 할 수 없다.

### 국소 결함 vs 방향 오류 — 기본 판별 절차

"국소 조정으로 고쳐지는가"는 **고쳐 보기 전에는 알 수 없는 사후 판정**이다. 그래서 추측하지 않고 실제로 한 번 고쳐 본다.

1. 탈락 사유가 **특정 노드·속성 하나**로 지목되는가? 지목되지 않고 화면 전반에 걸쳐 서술되면 곧바로 **방향 오류**다.
2. 지목되면 그 속성만 바꿔 **1회 재렌더**한다(하위 라운드 `N.k` 증가).
3. 해결되면 **국소 결함**으로 확정. 해결되지 않으면 **방향 오류**다 — 그 후보 자체가 이 기준을 만족할 수 없다는 뜻이다.
4. 하위 라운드 상한(`N.3`)에 닿으면 2번을 더 반복하지 않고 **방향 오류로 승격**한다. 국소 수정을 세 번 해서 안 되면 국소 문제가 아니다.

## 안전한 재개 — 끊긴 뒤 다시 시작할 때

- 재개 전에 `decisions.md` 제작 기록의 노드 ID 목록과 현재 파일을 **1회 읽기로 대조**한다. 이름만 같은 노드를 내 것으로 채택하지 않는다. 응답이 끊겨 생성 여부가 불명확하면 실재 확인 → 없으면 재생성, 있으면 제자리 수정.
- 삭제·전체 재생성을 재개의 기본값으로 두지 않는다. 컴포넌트를 바꿔 끼우면 의존 인스턴스의 오버라이드가 날아간다.
- `improve` 모드는 이전 run의 라운드 번호를 이어 쓴다. 상한(3)은 run이 바뀌어도 초기화되지 않는다.

## 재시도 상한 — 두 층위

`decisions.md`가 카운터를 겸한다. 별도 저장소를 만들지 않는다.

| 층위 | 무엇을 세는가 | 기록 위치 | 기본 상한 |
|---|---|---|---|
| **라운드** `N` | B단계 재발산 횟수 | `decisions.md` 라운드 헤더 | 3 |
| **하위 라운드** `N.k` | 같은 라운드 안의 국소 수정·A재검 횟수 | 해당 라운드의 재검 로그 | 3 |

★ **하위 카운트가 없으면 국소 결함 루프와 A-라우팅은 무한 반복 가능하다.** 둘 다 B단계를 거치지 않아 라운드가 늘지 않기 때문이다. 반드시 `N.k`를 증가시킨다.

**상한 도달 판정**: 라운드 3이 **C단계에서 탈락한 시점**에 멈춘다 — "라운드 3을 시작할 때"가 아니다(그러면 실질 상한이 2가 된다). 하위 라운드도 같다: `N.3`이 실패한 시점.

상한에 닿으면 사람에게 에스컬레이션하고 **멈춘다. 에이전트가 상한을 스스로 늘리지 않는다.** 보고 사유는 "상한 도달"이 아니라 **미해결 결정의 이름**이다(절대 규칙 5) — 어떤 항목이 어느 라운드에서 계속 탈락했고 어떤 기준이 미확정인지.
