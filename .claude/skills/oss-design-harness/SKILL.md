# oss-design-harness — 판단기준 추출 하네스

**순서가 아니라 함수다.** 사람이 0→B→A→C 순서로 일하는 이유의 상당수는 사람의 기억력·주의력 한계를 우회하는 워크어라운드이지, 결과를 좋게 만드는 원인이 아니다. 각 단계는 "지금 이 판단이 불확실한가"를 스스로 체크해서 진입 여부를 정한다. 배경: [docs/concept.md](../../../docs/concept.md).

## 진입 조건 (각 단계를 언제 실행하는가)

| 단계 | 진입 조건 | 스킵 조건 |
|---|---|---|
| 0. 요구사항 정렬 | 무엇을 만들지(IA, 핵심 화면, 톤) 자체가 불확실 | PRD/브리프에 이미 명시됨, 또는 사람이 방향을 지정함 |
| 0-a. 레퍼런스 리서치 | 0단계에 진입했고, 이 도메인·과업의 **실제 화면을 아직 보지 않음** | 사람이 레퍼런스를 이미 줌 |
| B. 발산·수렴 | 어떻게 만들지에 정답이 하나가 아님 (무드/밀도/구조 등) | 0단계에서 이미 톤·구조가 확정됨, 또는 국소 수정 작업 |
| 제작 | 0/B 산출물(또는 사람의 명시적 지정)이 있음 | — (항상 필요) |
| A/C 검증 | 화면을 새로 만들었거나 수정함 | 순수 조회·설명 요청 |

**클라이언트가 없다는 것은 0-a의 스킵 사유가 아니다.** 레퍼런스 리서치의 목적은 둘인데, 클라이언트 부재로 사라지는 건 하나뿐이다 — 사람에게 보여줄 **자극물**로서의 목적만 소멸하고, 에이전트 자신의 **시각 입력**(실제 화면을 봐야 톤·밀도 판단이 선다)으로서의 목적은 그대로 남는다. 스킵하면 실물을 한 장도 안 본 채 텍스트 추론만으로 톤과 레이아웃을 정하게 된다.

## 층 분리 — 어디에 무엇을 쓰는가

이 스킬의 `references/`는 **방법**(어떻게 판단하는가)만 담는다. **값**(이 프로젝트에서 얼마인가)은 전부 프로젝트 폴더에 쓴다. 방법론 파일에 프로젝트 답을 쓰면 다음 프로젝트가 그 답을 그대로 베껴 하네스가 오염된다.

| 프로젝트 파일 | 담는 것 | 생성 시점 |
|---|---|---|
| `projects/<슬러그>/brief.md` | 레퍼런스+반응 원문, 역추출한 판단기준, 가정 로그, 디자인 토큰 | 0단계 |
| `projects/<슬러그>/decisions.md` | 독립 축, 축별 후보·비교근거·선택, 남은 트레이드오프 | B단계 |
| `projects/<슬러그>/criteria.md` | **기능 커버리지 목록**(요구사항·유저스토리·흐름) + A/C단계 합격선(그리드 단위, 허용 컬러, 재사용률 하한, 밀도 상한 등) | 제작 전 |
| `projects/<슬러그>/build-plan.md` | 프레임 규격, 화면 목록, 제작 순서, 스코프 밖 항목 | 제작 전 |
| `projects/<슬러그>/verify-log.md` | A/C단계 검증 이력, **화면별 재시도 횟수**, 진단 분류, 기준을 고친 기록 | 첫 검증 시 |

`brief.md`/`decisions.md`는 `templates/`에서 복사해 시작한다. `criteria.md`는 `brief.md`의 토큰과 `decisions.md`의 축 선택에서 유도해 **제작 전에 미리** 적는다 — 검증 시점에 기준을 정하면 이미 만든 것에 맞춰 기준이 휘어진다.

## 0단계 — 요구사항 정렬

레퍼런스/시나리오는 표상(라벨)이 아니라 체험으로 제시한다. "모던한 게 좋으세요?" 금지. 방법론: [references/stage-0-alignment.md](references/stage-0-alignment.md).

**보여줄 레퍼런스가 아직 없으면 먼저 찾는다** — 검색어 생성부터 조합 판단까지: [references/reference-research.md](references/reference-research.md). 사람이 레퍼런스를 직접 주면 이 단계는 건너뛰고 반응 역추출로 바로 간다.

산출물: `brief.md` (위 층 분리 표 참고).

**실제 클라이언트가 없는 세션(솔로 구현, 데모, 하네스톤 연습 등)에서는** 침묵 대신 근거 있는 가정으로 채우고 `brief.md`의 가정 로그에 그렇게 명시한다. 가정을 사실인 것처럼 감추지 않는다.

## B단계 — 발산·수렴

축을 먼저 분리한 뒤에만 후보를 만든다. 축을 안 나누고 화면 전체를 통째로 비교하면 무엇 때문에 선택했는지 뒤섞인다(confound). 방법론: [references/stage-b-diverge.md](references/stage-b-diverge.md).

산출물: `decisions.md` (위 층 분리 표 참고).

## 제작 — Figma로 옮기기

`brief.md`/`decisions.md`에서 확정된 토큰·구조를 실제 노드로 만든다. 분해 순서·화면 목록은 `build-plan.md`에 먼저 적는다. Figma 호출 규칙: [references/figma-playbook.md](references/figma-playbook.md).

- 화면은 한 번에 하나씩, 섹션 단위로 증분 제작한다 (거대한 단일 `use_figma` 호출 금지).
- 반복되는 요소(버튼, 카드, 상태 배지 등)는 로컬 컴포넌트로 한 번 만들고 인스턴스로 배치한다.
- 색상/타이포/스페이싱은 `brief.md`의 토큰 값을 로컬 변수/텍스트 스타일로 등록해 재사용한다. 하드코딩 반복 금지.
- 제작 시작 전에 `criteria.md`가 있는지 확인한다. 없으면 먼저 쓴다 — A/C단계가 판정할 기준이 없으면 검증이 무의미해진다.
- `criteria.md`의 기능 커버리지 목록은 **요구사항 문서에서 직접** 항목화한다(디자인 결정에서 유도하지 않는다). 유저스토리가 여러 역할을 준다면 역할별로 따로 적는다 — 한 역할이 통째로 빠지는 사고가 흔하다.

## 검증 — A/C단계로 넘기기

제작 직후에는 항상 `design-verify` 스킬을 호출해 A(구조적 사실)와 C(미적 판단)를 검증한다. 판단 **방법**은 그 스킬의 references, 판정 **기준값**은 `projects/<슬러그>/criteria.md`.

### C단계 실패 시 라우팅

**진단 기준과 분류는 `design-verify` 스킬이 정본이다** — 여기에 다시 쓰지 않는다(두 곳에 쓰면 어긋난다). 이 스킬은 진단 결과를 받아 **어디로 되돌아갈지**만 실행한다.

| 진단 | 이 스킬이 하는 일 |
|---|---|
| 국소결함 | 그 속성만 고치고 C 재검. B로 돌아가지 않는다 |
| 방향오류 | B단계로 회귀 — 다른 후보 선택 또는 재발산 |
| 결정충돌 | 0/B의 결정이 서로 모순 → 해당 결정을 사람과 재논의. 제작으로 되돌아가지 않는다 |
| 반복실패 | 0단계로 에스컬레이션 — 요구사항 해석 자체가 틀렸다는 신호 |

**재시도 상한: 같은 화면에 대해 C단계 3회.** 횟수는 `projects/<슬러그>/verify-log.md`에서 센다 — **그 파일이 없으면 상한이 집행되지 않으므로, 첫 검증 전에 템플릿에서 복사해 만든다.** 3회를 넘기면 자동으로 계속하지 말고 사람에게 에스컬레이션 — 무엇을 3번 시도했고 왜 계속 실패했는지 그 로그를 요약해 보고한다. 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.
