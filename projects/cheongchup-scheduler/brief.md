# Brief — 청첩장모임 스케줄러

## 보여준 레퍼런스

실제 대상 클라이언트가 없어 스크린샷 제시는 생략했다. 대신 PRD(§3 "사용자들의 상황")의 문장을 반응 원문으로 취급했다 — PRD 작성자가 이미 구체적 상황 묘사로 암묵적 판단기준을 남겨두었기 때문 (`stage-0-alignment.md` §1 참고).

- PRD 원문: "청첩장을 줄 사람은 평균 40~60명, 많으면 100명을 넘기는 경우도 있습니다."
- PRD 원문: "결혼식 3개월 전부터 매주 주말마다 모임이 2~3건씩 잡히는 시기가 옵니다."
- PRD 원문: "한 모임에는 보통 3~6명이 함께 나오지만, 직장 상사처럼 1:1로 따로 만나야 하는 관계도 섞여 있습니다."
- PRD 원문: "날짜 후보를 보내도 며칠씩 답이 없는 사람이 꼭 있어, 언제까지 기다릴지 정해야 하는 순간이 옵니다."
- PRD 원문: "신랑 쪽 지인 풀과 신부 쪽 지인 풀이 따로 관리되다가도, 상견례 자리처럼 양가가 같이 나가야 하는 모임이 섞여 있습니다."
- PRD 원문: "결혼식이 2주 앞으로 다가온 시점에 갑자기 잡히는 급한 모임도 있습니다."

## 역추출한 암묵적 판단기준

- "메신저 방이 수십 개로 늘어나면 예비부부 스스로도 놓치기 시작한다" → **핵심 문제는 캘린더의 날짜 축이 아니라 "진행 상태 추적 실패"다.** 홈 화면의 1차 프레임은 상태별 리스트여야 한다.
- "한 사람이 여러 무리에 걸쳐 있는 경우가 많다" → 그룹 소속은 다중 선택이 기본값. 단일 라디오형 소속 UI는 이 도메인에서 틀린 설계다.
- "직장 상사처럼 1:1로 따로 만나야 하는 관계도 섞여 있다" → 모임 인원수 하한이 없어야 한다(1명짜리 모임도 정상 케이스).
- "여러 커플로부터 동시에 청첩장모임 요청을 받고 있어, 한 번에 파악하고 싶다"(초대받은 지인 관점) → 초대받은 사람 전용 화면(요청 모아보기)이 필요하다는 신호지만, 이번 스코프에서는 **예비부부(호스트) 화면만 우선 제작**하기로 가정(아래 가정 로그 참고).
- "회신 마감 기한을 둘 수 있어야 한다" + "언제까지 기다릴지 정해야 하는 순간" → 마감기한은 설정 화면 안에 숨은 값이 아니라 리스트/카드에 바로 노출되는 1급 정보.
- "양가가 같이 나가야 하는 모임이 섞여 있다" → 모임에 "소유자" 개념(신랑측/신부측/공용)이 필요하고 화면에서 배지 등으로 구분돼야 한다.

## 명시적 가정 로그

- **범위**: 이번 제작은 예비부부(호스트) 시점 화면만 다룬다. "초대받은 지인 전용 응답 화면"은 PRD 유저스토리 2번에 명시돼 있으나, 시간/스코프상 이번 실행에서는 제외한다 — 모임 상세 화면 안에 "지인이 보게 될 회신 화면 미리보기" 정도로만 축소 반영한다.
- **인증/로그인**: 예비신랑·예비신부 두 사람이 계정을 공유하는지 별도 계정으로 연동하는지 PRD에 명시 없음 → **하나의 앱을 두 사람이 함께 로그인해 쓰는 공유 워크스페이스**로 가정(개인용 캘린더 앱과 구분되는 PRD §5 조건 반영).
- **알림/리마인드**: PRD에 회신 마감 기능은 있으나 푸시 알림 스펙은 없음 → 이번 화면 제작에서는 "마감 임박" 상태를 배지로만 표현하고, 실제 알림 발송 플로우는 화면에 넣지 않는다.
- **다크모드**: PRD에 언급 없음 → 라이트 모드만 제작.
- **디바이스**: PRD에 명시 없음 → 모바일 앱(iOS 기준 390×844)으로 가정. 청첩장모임 조율은 이동 중 카톡 답장하듯 쓰는 상황(PRD §3)이 많다고 판단.
