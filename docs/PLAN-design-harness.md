# PLAN — 두 도메인에서 재사용 가능한 Figma 디자인 하네스

작성일: 2026-09-05 · 상태: 구현 전 제안

## 1. 목표와 범위

현재 청첩장모임 스케줄러를 완성하는 데 필요한 하네스를 먼저 보강하고, 이후 사주 풀이 앱은 **PRD와 프로젝트 설정을 교체해 같은 절차로 설계**할 수 있게 한다. 공통화의 대상은 요구사항 추적·제작 계약·검증·재개 절차다. 청첩장 앱의 화면 구성이나 색상을 사주 앱의 기본값으로 사용하지 않는다.

최종 디자인 산출물은 계속 Figma 파일이다. 이 PLAN의 스크립트는 계약 검사·증거 수집·실행 보호를 위한 보조 도구이며, HTML/React UI 제작으로 범위를 바꾸지 않는다. 사주 계산 엔진과 실제 서비스 백엔드 구현은 범위 밖이다.

이번 작업은 PLAN 작성이다. 아래 경로와 계약은 제안이며, 현재 실행 중인 하네스 규칙이나 Figma 파일을 변경한 것이 아니다. 문서 계획에는 Figma 제작 게이트를 실행하지 않는다. 실제 제작을 시작할 때는 승인된 절차의 게이트를 적용한다.

### 보존할 원칙

- `oss-design-harness/SKILL.md`가 절차의 단일 원본이다. 다른 스킬과 CLI 설정은 얇은 진입점으로 둔다.
- 판단기준 승격, 축별 후보 선택, 최종 디자인 승인은 사람이 한다. 기존에 명시적으로 승인·위임한 범위는 재질문하지 않는다.
- 원문 반응과 가정의 출처를 보존한다. 에이전트가 만든 값을 Figma에서 다시 읽었다는 이유로 사람 승인으로 바꾸지 않는다.
- 제작자와 검증자는 신규 컨텍스트로 분리한다. Codex worker는 선택된 후보를 제작하며, B 후보 생성은 기존 Claude 배선을 유지한다.
- Figma 쓰기는 단일 worker가 담당한다. 기존 라운드·하위 라운드 상한과 429 자동 재시도 금지를 유지한다.

## 2. 근거와 현재 진단

## 3. 목표 구조 — 공통 절차 / 프로젝트 값 / 실행 증거

```text
.claude/skills/oss-design-harness/SKILL.md  # 모드·단계·라우팅의 유일 원본
.claude/skills/wedding-scheduler-figma/    # invitation-scheduler 설정을 고르는 래퍼
templates/brief.md                       # 사람 반응·판단기준·승인 원장
templates/decisions.md                   # append 전용 라운드·인수인계 GATE
templates/contracts/                    # requirements, screens, components, 검증 패킷
schemas/                                # 계약 JSON Schema
scripts/harness/                        # 계약 검사·패킷 생성·스냅샷 정규화
docs/projects/<project-id>/
  project.json                          # PRD·원장·산출물의 경로 및 도메인 설정
  domain.md                             # 개념·상태·콘텐츠 규칙·가정
  fixtures.json                         # 고정 기준일을 포함한 합성 데이터
design/<project-id>/
  brief.md                              # target·승인의 권위 있는 원장
  decisions.md                          # 실행 전이·라운드 기록의 권위 있는 원장
  _system/brief.md                       # 이 프로젝트의 디자인 시스템
  contracts/                            # 요구사항·화면/상태·컴포넌트 계약
  runs/<run-id>/<revision-id>/
    manifest.json                       # 입력·증거 식별자; 별도 상태 원장 아님
    node-map.json                       # 논리 ID ↔ file/page/node ID
    evidence-index.json                 # 증거 경로·해시·수집 시각·완전성
    reports/                            # 독립 A/C/V 판정 원문
    .cache/                             # before/after·검증 입력 패킷
    renders/                            # revision별 렌더
docs/examples/saju/prd.md                # 확장 리허설용 PRD; 제품 확정본과 구분
docs/harness-lessons.md                  # 재현된 실패→범용 규칙→회귀 사례
```

`project.json`에는 target을 복제하지 않고 `brief_path`, `system_brief_path`, `prd_path`, `artifact_root`를 둔다. 실행 manifest의 target은 원장에서 추출한 잠금 사본이며 원장 revision/hash와 일치해야 한다. 루트는 run 시작 시 고정한다.

현재 앱은 `docs/prd.md`, `docs/screen-map.md`, `design/invitation-scheduler/`, `design/_system/brief.md`를 그대로 가리키는 호환 설정으로 시작한다. 활성 실행 중 경로 이동은 하지 않는다. `_system` 이동은 현재 run이 끝난 뒤 참조를 함께 바꾸거나, 기존 경로를 현재 앱 전용으로 계속 유지한다. 사주 앱은 처음부터 별도 경로를 사용한다.

### 단일 원본 규칙

- `brief.md`: 요구 해석·판단기준·승인·target의 원장. 확정과 후보를 분리한다.
- `decisions.md`: 기존처럼 전이와 재시도 카운터의 원장. 별도 `state.json`은 만들지 않는다.
- 계약 JSON: 대응 원장의 기계 판독용 산출물. `source_ref`, `source_hash`, `schema_version`으로 오래된 사본을 감지한다. 파생 파일을 수정해 원장을 우회하지 못하게 한다.
- 보고서는 독립 판정 원문이다. decisions에는 원문을 append하고 보고서 해시를 연결한다. 판정 수정은 기존 기록 삭제 대신 정정 기록을 추가한다.
- `.cache/`와 `renders/`는 계속 커밋하지 않는다. 저장소를 새로 받은 검증자가 증거 파일에 접근할 수 없으면 ‘재검증 불가’를 명시하고 재수집한다. 해시만으로 렌더를 봤다고 처리하지 않는다.

## 4. 공통 계약과 실행 흐름

### 4.1 식별자와 계보

ID는 프로젝트 범위에서 유일하게 관리한다: `REQ-*` 요구, `ASM-*` 가정, `CRIT-*` 기준, `SCR-*` 화면, `STATE-*` 상태, `CMP-*` 컴포넌트, `DEC-*` 선택, `GAP-*` 결함.

필수 계보는 `PRD 원문 위치 → REQ → 화면/상태/전이 → Figma node ID → 검증 증거`다. 요구사항에 없는 화면을 제안할 수 있지만 `ASM`이나 선택 근거를 연결한다. 화면 개수를 공통 상수로 고정하지 않는다.

각 판단기준에는 `source_kind`, `source_ref`, `status`, `approved_by`, `approval_ref`, `scope`를 둔다. PRD 원문과 에이전트 해석이 다르면 같은 ‘사람’ 소스로 묶지 않는다. 토큰에도 `selection_source`와 `measurement_source`를 따로 둔다.

### 4.2 인수인계 GATE

각 단계는 대표 산출물 하나와 증거 참조를 내고, decisions의 해당 라운드 끝에 구조화된 `GATE` 블록을 append한다.

```yaml
schema_version: 1
project_id: invitation-scheduler
run_id: "<고정 실행 ID>"
revision_id: "<현재 수정 ID>"
stage: build-screens
producer_session_id: "<제작 세션 ID>"
input_refs: []          # 경로 + 해시 + schema version
output_refs: []         # 경로 + 해시
target_ref: "<brief target과 revision>"
status: PARTIAL         # PASS | PARTIAL | FAIL | BLOCKED
blockers: []            # GAP ID, 미해결 결정 이름, owner_stage
next_stage: null
```

다음 단계는 필수 ID·해시·산출물 실재·대상 일치를 검사한다. `PASS`라는 글자만으로 통과하지 않으며, 본문의 긍정적 표현을 근거로 FAIL을 뒤집지도 않는다. `PARTIAL`은 진행 상황이고 필수 의존 단계를 여는 승인이 아니다. `BLOCKED`는 증거·권한·결정 부재, `FAIL`은 검사한 결과의 위반이다.

항목 판정 `PASS/FAIL/SKIP/N/A`는 유지한다. 필수 증거가 없어 판정할 수 없는 경우 게이트를 `BLOCKED`로 한다. 특히 A-0은 SKIP이나 자동 PASS로 바꾸지 않는다. 전부 N/A인 경우를 포함해 집계표를 명시하고, 미검증 항목을 PASS로 세지 않는다.

### 4.3 단계와 소유권

| 단계 | 주체 | 주요 산출물 | 다음 단계 진입 조건 |
|---|---|---|---|
| 모드 선택·G | master | 실행 manifest | plan-only / build / review / improve 구분. build는 target·도구 능력 확인 |
| 요구 계약 | master/cso | requirements 계약 | PRD 요구 전량 추적, 미확정 해석 표시 |
| 0 요구 정렬 | 사람과 직접 대화하는 master/cso | brief | 기존 수렴 규칙 충족, 승인·위임 근거 연결 |
| B 발산·선택 | Claude 후보·비평 배선 + 사람 | decisions 선택 기록 | 사람 선택 또는 기존 규칙에 부합하는 명확한 스펙·위임 근거 |
| 제작-L 라이브러리 | worker | components 계약 + 실제 ID | 토큰·스타일·원자/복합 컴포넌트 실재와 독립 구조 검사 |
| 제작-S 화면 조립 | worker | node-map + 화면 증거 | 승인된 화면·상태를 실제 인스턴스로 조립 |
| A 구조 검증 | 독립 reviewer | A 보고서 | 현재 A 규칙 + 증거 완전성·바인딩 검사 |
| C 미적 검증 | 신규 컨텍스트 reviewer | C 보고서 | 현재 revision 렌더와 승격된 기준만 사용 |
| V 실재·흐름 검증 | 독립 reviewer | V 보고서 | 요구·상태·연결·리소스 실재, 최신 증거 일치 |
| 최종 판단 | 사람 | 승인/보류 기록 | A/C/V의 검증 범위와 미해결 결정을 보고 판단 |

라이브러리 게이트의 실재 확인은 자기 제작 보고를 신뢰하지 않고 독립 읽기 증거로 확인한다. 작은 작업에서는 에이전트 수를 늘리지 않고 기존 reviewer를 신규 컨텍스트로 호출한다.

`plan-only`는 문서만 작성하며 target이 없어도 계획을 낼 수 있다. build 전환 시 G-3/G-4를 통과해야 한다. `improve`는 기존 run과 GAP 목록을 입력으로 받고 원래 라운드 카운터를 이어 쓴다. 새 run ID로 반복 실패 상한을 초기화하지 않는다.

## 5. 검증과 실행 보호의 보강

### 5.1 역할별 접근 범위

| 역할 | 허용 | 차단 |
|---|---|---|
| 요구 해석·후보 생성 | 지정 입력 읽기, 자기 계약 파일 쓰기 | Figma 쓰기; 후보는 Figma 조회도 금지 |
| worker | 승인된 target 읽기·쓰기, 지정 산출물 갱신 | 대상 밖 변경, 기준 자체 승격, 자기 결과 최종 판정 |
| A reviewer | A 패킷과 노드 증거 읽기 | 디자인 수정, decisions·제작 대화 접근 |
| C reviewer | 렌더·확정 기준·A 요약 읽기 | 노드 트리·전체 brief·제작 의도 접근 |
| V reviewer | 요구 계약·node-map·현재 실재 증거 읽기 | 제작 의도 기반 평가, 디자인 수정 |

도구 허용 목록, 파일 접근 제한, hooks 적용 여부를 Claude/Codex 각각 시험한다. 프롬프트에 ‘탐색 금지’만 쓴 상태는 물리적 격리로 기록하지 않는다. 강제 기능이 부족하면 지정 파일만 담은 별도 작업 디렉터리와 읽기 전용 도구 구성을 사용하고, 그마저 안 되면 격리 미달을 보고한다. 임의 스크립트 실행 도구에는 도구 이름 필터만으로 충분하지 않으므로 실제 target 검증 경로를 포함한다.

### 5.2 스냅샷 계약

수집기는 각 revision에서 before/after와 수집 범위를 기록한다. A의 각 항목은 같은 수집 결과를 재사용한다. 최종 V의 독립 조회는 별도 검증 단계의 1회 수집으로 정의해 무제한 재조회와 구분한다.

- 공통: file/page/root ID, 수집 시각, 입력 revision, 누락·잘림 여부, 좌표계, 수집기 버전.
- A-0: 인스턴스 내부를 포함한 대상 범위, 원래 정밀도의 위치·크기·변환, clipping/scroll/visibility, 색·투명도·배경 관계, 텍스트 run별 속성, 리소스 진단 정보.
- A-1~6: 변경 노드 집합, 변수 ID와 바인딩, 텍스트 스타일 ID, layout 속성, main component ID, variant 속성·필수 상태. 인스턴스 내부 제외는 수집 후 검사 필터로 적용한다.
- 복합 배경 등 대비를 확정 계산할 수 없는 경우 필요한 렌더·별도 측정 증거를 연결한다. 지원하지 않는 정보를 채운 척하지 않는다.
- 스크롤 영역이나 의도된 오버레이는 명시된 구조 계약과 비교한다. 단순히 프레임 밖 좌표라는 이유만으로 결함으로 확정하지 않는다.

현재 A-4의 0.70은 청첩장 프로젝트에 기록된 승인값으로 유지하되, 승인 근거와 기존 분모 정의를 함께 확인한다. 분모는 공통 스킬의 프레임·텍스트·인스턴스 범위를 기준으로 명문화하고, ‘재사용 대상 중 인스턴스 비율’을 보조 지표로 쓸 경우 다른 지표 ID를 부여한다. 산식 변경 후 같은 70%를 몰래 적용하지 않는다. 재사용률과 트리 깊이는 함께 보고하며 깊이의 새 하한·상한을 임의로 만들지 않는다.

### 5.3 실제 흐름 V

화면이 좌→우로 놓였다는 사실과 프로토타입 연결을 구분한다. 각 핵심 CTA의 source node, action, destination node를 요구 전이와 대조하고 현재 파일에서 목적지 존재를 확인한다. UI mock으로만 표현한 동작은 ‘표현됨’, 실제 Figma 연결은 ‘연결됨’으로 기록한다.

empty/loading/error/partial/complete 같은 상태는 모든 컴포넌트에 기계적으로 붙이지 않는다. 요구 계약에서 해당 상태의 적용 여부와 근거를 정한다. C는 보이는 완성도를, V는 필요한 상태·진입·복귀 경로의 존재를 확인한다.

### 5.4 안전한 재개와 수정 범위

`node-map`에 논리 ID, file/page/node ID, 소유 run, component 연결을 기록한다. 재개 시 ID와 소유권을 검증해 호환 노드는 제자리 수정한다. 이름만 같은 타인 노드를 채택하지 않는다. 응답이 끊겨 생성 여부가 불명확하면 먼저 실재를 대조하고 재생성한다. target이 바뀌면 기존 node ID를 재사용하지 않고 별도 이전 계약을 만든다.

| 실패 | 수정 책임 | 다시 검증할 범위 |
|---|---|---|
| target·입력 해시 불일치 | master / 원장 소유 단계 | 인수인계부터; Figma 쓰기 전 차단 |
| 요구 누락·승인 근거 부족 | 요구 계약 / 0 | 영향받는 화면·컴포넌트 및 하위 A/C/V |
| 공통 컴포넌트 결함 | 제작-L | 해당 컴포넌트와 이를 쓰는 모든 화면 |
| 화면 국소 결함 | 제작-S | 변경 노드 관련 A + 해당 렌더 C + 관련 연결 V |
| 기준 오해·검증기 오탐 | 검증 계약·검증기 | 수정한 규칙의 모든 영향 대상; 디자인은 자동 수정하지 않음 |
| C 반복 실패·방향 오류 | 기존 C 라우터 | 기존 우선순위(반복→방향→국소)와 상한 유지 |
| 429 / 인증 만료 | 도구 실행 담당→master | 자동 루프 중단, 재개 조건 기록; 인증은 사람 처리 |

스냅샷은 복원 가능한 백업과 동일하지 않다. 라이브러리 교체·보관 이동 등 구조 변경은 오버라이드와 의존 인스턴스를 대조할 복구 방안을 먼저 준비한다. 삭제·전체 재생성을 재개의 기본값으로 두지 않는다.

## 6. 청첩장과 사주를 분리하는 방법

사주 앱의 상세 PRD는 아직 제공되지 않았다. 아래 사주 흐름은 **하네스 확장 리허설용 후보**이며 제품 요구 확정이나 판단기준 승격이 아니다.

| 항목 | 청첩장: 현재 PRD·원장 | 사주: 검증용 후보 | 공통 하네스 책임 |
|---|---|---|---|
| 사용자·관계 | 두 예비부부와 초대받은 지인 | 본인 풀이 사용자; 타인 프로필·궁합은 미정 | 사용자·권한·주체를 입력 계약으로 읽기 |
| 핵심 흐름 | 지인→편성→후보·회신→확정→전체 일정 | 출생정보 입력→확인→풀이 요청→결과 읽기 | 흐름·상태·복귀 경로 추적 |
| 도메인 상태 | waiting/ready/confirmed/done | 입력 미완성/요청 중/결과 준비/실패 등 후보 | 상태 enum을 프로젝트에서 공급 |
| 까다로운 경우 | 중복 소속, 늦은 회신, 겹침, 공동 모임 | 출생시각 모름, 입력 수정, 요청 실패, 긴 풀이 | 케이스→화면·상태→검증 증거 매핑 |
| 입력 정책 | 이름·그룹·연락처 | 양력/음력·윤달·출생지 등 수집 여부 미정 | 미정 입력과 차단되는 결정을 이름으로 표시 |
| 콘텐츠 | 회신 안내·확정 공유 문구 | 풀이 표현 수준, 용어 설명, 단정적 표현 허용 범위 미정 | 도메인 콘텐츠 정책·승인 근거를 별도 계약으로 전달 |
| 디자인 시스템 | 현재 아이보리·측별 색·모임 배지 | 브랜드·무드·밀도 전부 미정 | 토큰 선정 절차만 재사용; 값은 독립 |
| 데이터 | 고정 기준일·모임·회신 fixture | 합성 출생정보·명시적 예시 풀이 | 실제 개인정보 없는 재현 가능한 fixture |

사주 fixture의 최소 제안은 입력→확인→요청→결과 읽기다. 결제·궁합·오늘의 운세·저장·공유는 자동 추가하지 않는다. 시간 모름을 허용할지, 입력을 바꾸면 기존 결과를 어떻게 표시할지는 도메인 결정으로 남긴다. 실제 풀이의 계산 정확도와 Figma 결과 화면의 디자인 검증은 별도 책임이다.

청첩장 fixture도 검증한다. 예를 들어 `screen-map.md`의 ‘같은 날’과 ‘시간 겹침’은 다른 상태로 정의할 필요가 있고, 고정 오늘 날짜와 `급함 D-12` 사례는 시나리오 기준일을 분리해야 한다. 도메인 사례의 모순을 공통 UI 규칙으로 승격하지 않는다.

## 7. 구현 순서와 완료 조건

- [ ] 현재 파일 상태와 활성 run·루트를 기록한다. 다른 에이전트의 작업 파일을 일괄 정리하지 않는다.
- [ ] target·429·A-4·승인 상태의 불일치를 원장 근거에 맞춰 정리한다.
- [ ] 전용 스킬의 target 상수를 제거하고 원장 참조로 바꾼다.
- [ ] `scripts/harness/check-contracts` 초판과 실패 fixture를 추가한다. 실제 확장자는 레포 실행 환경에 맞춰 결정한다.

완료 조건: 서로 다른 file key, 오래된 기준값, 승인 근거 누락을 넣은 입력을 검사기가 잡는다. 문서 정리를 실제 Figma 품질 통과로 보고하지 않는다.

### P1 — 프로젝트 설정과 구조화된 인수인계 도입

의존성: P0.

- [ ] 현재 앱의 호환 `project.json`을 만들고 공통 스킬에서 프로젝트 값을 직접 읽지 않게 한다.

- [ ] brief·decisions에서 패킷을 생성하고 ID·해시·승격 근거·단계 입력을 검사한다.
- [ ] plan-only/build/review/improve의 진입·차단 조건을 공통 스킬에 명시한다.
- [ ] 코어·템플릿의 고유 도메인 값 검사를 추가한다. 프로젝트 산출물·fixture·출처 예시는 허용 범위로 구분한다.

완료 조건: 청첩장 설정을 사주 fixture 설정으로 바꿔도 코어 수정 없이 요구 계약을 생성한다. PRD가 빈 파일이면 이름만 보고 정상 입력으로 처리하지 않는다. 인수인계 입력이 바뀌면 기존 PASS는 stale로 거부한다.

### P2 — 제작-L/S와 검증 증거 강화

의존성: P1. 이 단계의 실제 Figma 작업은 확정된 대상과 build 게이트가 필요하다.

- [ ] A/C 패킷을 생성하고 리뷰어에 전체 brief 대신 필요한 추출본만 전달한다.

- [ ] 역할별 도구·파일 접근 제한을 런타임별로 시험하고 강제 수준을 기록한다.

완료 조건: 인스턴스 내부 결함·누락 before·잘린 스냅샷·오래된 렌더·끊긴 CTA를 각각 감지한다. 라이브러리 수정 시 이를 사용하는 화면의 재검 목록이 생성된다. worker 세션과 reviewer 세션이 같으면 검증 입력을 거부한다.

### P3 — 재개 및 두 도메인 회귀검증

의존성: P2. 사주 라이브 제작 전에는 그 프로젝트의 PRD·target·기준 확정이 추가로 필요하다.

- [ ] 사주 fixture PRD에 가정·비목표·열린 결정을 명시하고 의미 있는 상태 사례를 넣는다.
- [ ] 같은 논리 작업을 재개했을 때 node ID 대조 후 수정하며 중복 프레임을 만들지 않는지 검증한다.
- [ ] 중간 실패·target 변경·429·증거 부재를 주입해 재개 경로와 상한을 확인한다.
- [ ] 청첩장과 사주에서 동일 코어 revision으로 계약 리허설을 수행한다.
- [ ] 두 프로젝트가 준비되면 독립 A/C/V를 포함한 Figma 실전 리허설을 각각 수행한다.

완료 조건: ‘두 도메인 문서 리허설 통과’와 ‘두 도메인 실제 Figma 검증 통과’를 따로 보고한다. 사주 target·기준이 없으면 전자를 완료하고 후자는 대기로 남긴다. 최종 디자인 승인자는 사람이다.

## 8. 회귀검증 매트릭스와 측정

| 검사 사례 | 기대 결과 | 실행 층 |

| 공통 규칙에 groom/bride·사주 전용 enum 유입 | 도메인 누출 탐지 | 로컬 정적 검사 |
| 미승격 후보 또는 근거 없는 해석을 확정 기준으로 전달 | 검증 패킷 생성 거부 | 로컬 계약 |
| before 누락 / after 잘림 / 다른 revision 렌더 | 해당 필수 검증 BLOCKED | 증거 fixture |
| 컴포넌트 ID 없이 화면 조립 진입 | 제작-S 진입 거부 | 단계 계약 |
| 인스턴스 내부 A-0 결함 | 누락 없는 결함 탐지 | 노드 fixture + 실전 |
| 화면 존재하지만 CTA 목적지 없음 | V FAIL, source node 보고 | 연결 fixture + 실전 |
| 같은 run 재개·응답 유실 | 중복 생성 없음, 실재 대조 | 제어된 Figma 리허설 |
| 공통 컴포넌트 수정 | 영향 화면 전체 재검, 무관 화면 유지 | 의존 그래프 + 실전 |
| 429 | 자동 재시도 0, 원인·재개 조건 기록 | 도구 실패 fixture |
| C 기준 전부 미기재 | 판정 불가, 항목 이름 보고 | 라우터 fixture |
| 사주로 프로젝트 전환 | 청첩장 화면명·토큰·상태·개인 데이터 유입 없음 | 두 PRD 리허설 |

측정 항목은 요구·상태·전이 커버리지, 변수/스타일 바인딩률, 재사용률과 산식, 트리 깊이, 반복 실패 수, MCP 호출 수, 재개 중 중복 노드 수, 검증 SKIP 비율, 사람 오버라이드다. 동일 PRD·fixture·기준 revision·가능한 한 동일 실행 환경에서 전후를 비교한다. 모델·도구·기준이 달라지면 비교 조건에 명시한다.

새로운 미적 임계값을 PLAN에서 확정하지 않는다. 커버리지·무단 쓰기·증거 완전성과 같은 계약 조건은 자동 검사하고, 밀도·색온도·재사용률 임계값은 승인된 프로젝트 기준으로 판정한다.

## 9. 실행 전에 남겨둘 결정

아래는 이 PLAN 작성을 막는 질문이 아니라 해당 구현·제작 단계에 진입할 때 해결할 결정 목록이다.

| 결정 이름 | 필요한 시점 | 처리 |
|---|---|---|
| 사주 제품 범위 | 사주 PRD 확정 전 | 핵심 풀이 범위와 궁합·결제·저장 포함 여부를 사람에게 확인 |
| 사주 입력·콘텐츠 정책 | 요구 정렬 완료 전 | 출생시각 모름·달력 입력·풀이 표현 규칙을 확정 |
| 사주 target 및 시각 기준 | 사주 build 전 | 해당 프로젝트 원장에서 별도 확정 |
| 기존 승인 기록의 근거 대조 | P0 | 이미 승인된 항목은 유지하고 근거 없는 해석만 후보로 정정 |
| 실행 환경의 권한 강제 수준 | P2 | CLI·MCP 실측 후 강제 가능 범위와 잔여 제한 기록 |
| 활성 run 경로 이전 시점 | 현재 앱 run 종료 후 | 진행 중에는 호환 경로 유지; 이전 시 참조와 해시 함께 갱신 |

첫 구현 단위는 **P0의 target·정책·기준 불일치 정리와 검사기**로 한다. 이어서 P1의 프로젝트 설정을 도입하면 현재 청첩장 제작을 보존하면서 사주 확장의 기반을 마련할 수 있다.
