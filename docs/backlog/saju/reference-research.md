# 사주 풀이 앱 레퍼런스 조사와 디자인 하네스 적용

조사일: 2026-09-05. 범위: 점신·포스텔러·헬로우봇·사주명 공식 소개 및 스토어 공개 이미지. 실제 앱 설치·로그인·결제·화면 전환은 수행하지 않았다. 아래 추천과 구성안은 분석자의 제안이며 사용자의 디자인 채택·기준 승격이 아니다. 기존 청첩장 프로젝트의 PRD·Figma target·토큰은 이번 조사 대상이 아니다.

## 1. 이번 조사에서 결정해야 하는 것

“어느 앱이 가장 예쁜가”를 고르면 화면 전체를 모방하기 쉽다. 먼저 사용자의 과업을 정하고, 그 과업에 도움이 되는 요소를 골라야 한다. 조사 질문은 다음과 같다.

- 처음 온 사용자가 자기 정보를 입력하고 첫 풀이까지 도달하는 구조는 무엇인가?
- 전문 용어가 많은 결과를 요약·근거·상세로 어떻게 나눌 것인가?
- 매일 돌아오는 사용자에게 무엇을 먼저 보여줄 것인가?
- 정해진 리포트와 대화형 후속 질문을 어떻게 연결할 것인가?
- 결과 저장·다시 보기·공유에서 무엇을 유지하고 무엇을 감출 것인가?

네 앱은 서비스 범위가 다르므로 앱 전체의 우열을 매기지 않는다. 정보 입력 화면, 결과 읽기 화면, 콘텐츠 탐색 화면, 대화 화면은 각각 같은 과업끼리 추가 비교해야 한다.

## 4. 앱별 상세 분석 — 기능 사실과 디자인 제안을 분리

### 점신: 여러 운세를 한곳에서 읽는 구조

**공식 소개로 확인**: 일일·시간대별 운세 보고서, 생활 추천, 인맥 저장과 궁합, 전문가 전화 상담, 타로, 광고 관련 행운패스와 보상 기능을 제공한다. 상담사는 400명 이상으로 소개한다. [점신 공식 소개](https://play.google.com/store/apps/details?hl=ko&id=handasoft.mobile.divination)

**직접 관찰**: J-01의 기기 내부는 장식 이미지 아래에 여러 항목을 동일한 원형 수치와 라벨로 배치하고 설명을 이어간다. 항목을 훑어볼 수 있는 시각 구조다. 다만 이 장면은 신년운세 일부이며 오늘의 홈이라고 부를 수 없다.

**추출 제안 P-J-01**: 긴 풀이 앞에 항목별 요약을 둔다. 숫자·색만 제시하지 말고 해당 항목의 뜻과 짧은 해설을 붙이는 방식으로 변형한다. 동일한 형태의 반복은 Figma 컴포넌트로 표현할 수 있다.

**채택 추천 범위**: 요약에서 상세로 넘어가는 정보 계층. **보류 추천**: 원형 점수의 표현 방식과 상담 마켓 전체. 사주 풀이 앱의 핵심이 자기 이해라면 상담사 검색·예약까지 첫 버전에 넣을 이유가 아직 없다.

**검수할 질문**: 사람에게 항목만 보여줘도 무엇을 뜻하는지 설명할 수 있는가? 점수가 무엇의 확률인지 오해하지 않는가? 상담을 포함한다면 연결 전 비용·이용 가능 상태·연결 실패 후 경로를 설계했는가? 이는 제안할 검증 시나리오이며 점신에서 해당 문제가 발생한다는 결론은 아니다.

### 포스텔러: 콘텐츠를 발견하는 구조와 캐릭터의 역할

**공식 소개로 확인**: 장르·주제별 무료/유료 풀이, 일일 점수, 장기 상세 풀이, 운세 캘린더를 제공한다. [포스텔러 공식 소개](https://play.google.com/store/apps/details?hl=ko&id=com.un7qi3.forceteller)

**직접 관찰**: F-02 기기 내부에는 장르 탭, 검색 아이콘, 캠페인 배너, 텍스트 중심 인기 목록이 구분되어 있다. 작은 캐릭터는 목록 제목 부근을 보조한다. F-01과 F-02 바깥의 수묵·트로피 장식은 앱 전체 스타일의 증거가 아니다. ‘MZ에게 인기이니 파스텔 캐릭터를 쓰면 된다’는 결론은 이 자료에서 나오지 않는다.

**추출 제안 P-F-01**: 콘텐츠 분류와 원하는 질문으로 진입하는 경로를 구분한다. 우리 앱에서는 ‘어떤 역학 장르인가’와 ‘무엇이 궁금한가’를 혼동하지 않는 탐색 구조를 검토한다. **P-F-02**: 캐릭터를 설명 시작·빈 상태의 안내에 배치하되 긴 본문 읽기를 방해하지 않도록 한다.

**채택 추천 범위**: 분류·검색·질문형 제목의 역할 분담. **보류 추천**: 캐릭터의 구체 외형, 전체 무드, 캘린더 기능. 캐릭터 선호와 미래 날짜를 비교할 필요는 사람에게 확인해야 한다.

**검수할 질문**: ‘올해 이직’ 같은 목적을 가진 사람이 장르를 몰라도 진입할 수 있는가? 탐색 중 유료 콘텐츠임을 언제 알게 되는가? 캐릭터가 사라져도 과업을 이해할 수 있는가? 검색 실패·빈 카테고리·이미 구매한 콘텐츠 상태가 있는가?

### 헬로우봇: 짧은 대화와 결과 카드의 결합

**공식 소개로 확인**: 사주·타로 등 여러 콘텐츠와 AI 챗봇 상담을 소개한다. 이것만으로 모든 콘텐츠가 자유로운 생성형 대화라는 사실은 확인되지 않는다. [헬로우봇 공식 소개](https://play.google.com/store/apps/details?hl=ko&id=com.thingsflow.hellobot)

**직접 관찰**: H-02는 캐릭터 이름과 아바타 아래에 결과 카드를 놓고, 설명을 여러 말풍선으로 나눈다. H-01에는 주제마다 매우 다른 색과 표지 표현이 보인다. 한 화면 안의 통일된 디자인 시스템이라고 해석하지 않는다.

**추출 제안 P-H-01**: 요약 결과 카드 뒤에 짧은 설명과 다음 질문을 이어갈 수 있는 흐름을 검토한다. 대화를 모두 다시 읽지 않아도 결과를 찾을 수 있도록 리포트·보관함 연결을 함께 설계한다.

**채택 추천 범위**: 대화 중 핵심 결과를 별도 카드로 보존하는 패턴. **제외 추천 범위**: 근거를 설명하지 않는 예측 확률이나 특정 날짜를 그대로 우리 앱의 확정적 약속으로 옮기는 문구. 이는 표현에 대한 분석자의 추천이며 사용자 확정 기준은 아니다.

**검수할 질문**: 응답을 기다리는 동안 무엇이 진행되는지 보이는가? 대화 중 입력한 출생 정보를 수정할 수 있는가? 중단 후 돌아와 결과를 찾을 수 있는가? 추천 질문과 자유 입력이 각각 어디까지 지원되는지 구분되는가?

### 사주명: 입력에서 분석·보관·공유까지의 범위

**공식 소개로 확인**: 생년월일시 입력, 사주팔자·오행·용신 등을 다루는 AI 풀이, 관심 분야·월 선택, 궁합, 상대 정보 저장, 풀이 기록, 이미지 공유를 제공한다. 로그인은 선택이며 리워드 광고 시청으로 풀이 1회를 제공한다고 명시한다. [사주명 공식 소개](https://play.google.com/store/apps/details?hl=ko&id=com.playreturns.sajuyeon)

**직접 관찰**: S-01은 밝은 카드에 오늘의 한 줄, 분야별 문단, 마지막 조언을 나눈다. 포스터의 짙은 붉은 배경과 금색 선은 확인했지만 앱 전체가 같은 배색이라는 근거는 없다. 이번 이미지에는 만세력 표나 오행 차트가 없으므로 그 디자인의 우수성을 판정할 수 없다.

**추출 제안 P-S-01**: 짧은 요약 → 관심 분야별 설명 → 오늘 적용할 행동 순서로 결과를 구성한다. **추가 조사 P-S-02**: 명식·오행은 공식 설명으로 기능 존재만 확인했으므로 실제 결과 화면을 확보한 뒤 시각화 방식을 판단한다.

**채택 추천 범위**: 요약·주제별 풀이·실생활 조언의 구분. **보류 추천**: 오행 차트 스타일, 용신 표시, 광고 흐름. 입력 정보 재사용·저장·공유는 요구사항 후보로 올리되 실제 사용 흐름을 확인한다.

**검수할 질문**: 출생 시간을 모르는 사람이 진행할 수 있는가? 광고 완료 후 분석이 실패했을 때 이용권과 입력을 보존하는가? 기록이 없는 상태에서 첫 풀이로 이동하는가? 공유 전에 생년월일시·실명을 숨길 수 있는가?

| F-01 | UI 근거로 제외 제안 | 캠페인 무드 비교에는 사용 가능 | 앱 화면과 홍보 포스터를 구별 |
| F-02 | 부분 채택 제안 | 탐색 경로·텍스트 목록·보조 캐릭터 | 탐색 과업 테스트·캐릭터 선호 |
| H-01 | 보조 자료 | 콘텐츠 표지의 표현 범위 | 실제 목록 UI 확보 |
| H-02 | 부분 채택 제안 | 결과 카드와 짧은 후속 대화 | 실제 입력·오류·복귀 흐름 |
| S-01 | 부분 채택 제안 | 한 줄 요약·분야별 설명·행동 조언 | 실제 앱 결과 화면 확보 |

어떤 항목도 아직 사람이 adopt로 선택하지 않았다. 따라서 아래 앱 구성과 검증 항목은 프로젝트에 자동 적용하지 않는다.

## 6. 사주 앱 전체 구성 — 요구사항 논의를 위한 기능 지도

다음은 경쟁 앱의 실제 IA를 합친 결과가 아니라, 위 조사에서 도출한 **우리 앱의 과업 분해 제안**이다. 구현 범위와 내비게이션 개수는 아직 결정하지 않는다.

| 영역 | 사용자 목적 | 세부 기능 후보 | 필수로 논의할 상태 | 참고 패턴 |
|---|---|---|---|---|
| 첫 방문·정보 입력 | 나에게 맞는 풀이 준비 | 생년월일, 달력 구분, 시간·시간 모름, 입력 검토·수정 | 날짜 오류, 시간 미상, 중단·복귀 | S4 기능 설명; 입력 UI 미확보 |
| 오늘 | 짧게 오늘의 흐름 확인 | 대상 프로필·날짜, 한 줄 요약, 주제별 설명, 상세로 이동 | 프로필 없음, 날짜 변경, 불러오기 실패 | P-J-01 / P-S-01 |
| 내 풀이 | 나를 이해할 설명 읽기 | 요약, 분야별 풀이, 명식·오행 설명, 용어 도움말, 후속 질문 | 분석 대기·실패, 수정 후 재분석, 긴 문장 | P-S-01; P-S-02 추가 조사 |
| 탐색 | 궁금한 주제로 진입 | 주제별 분류, 질문형 제목, 검색, 무료·유료 구분 | 검색 결과 없음, 미구매·구매 완료 | P-F-01 |
| 대화 | 내 상황을 더 물어보기 | 질문 제안, 입력, 결과 카드, 다시 보기 연결 | 응답 대기, 실패·재시도, 세션 복귀 | P-H-01 |
| 궁합 | 두 사람의 관계 비교 | 대상 선택·추가, 입력 확인, 관계별 해석 | 상대 정보 없음, 같은 대상 선택, 삭제 | S1/S4 기능 설명; 흐름 미확보 |
| 보관함 | 예전 결과 다시 읽기 | 날짜·대상·분야 목록, 상세 진입, 삭제 | 기록 없음, 긴 제목, 데이터 복구 | S4 기능 설명; UI 미확보 |

**우선 논의 제안**: 첫 방문 → 입력 확인 → 풀이 요약 → 상세 → 저장·재열람의 한 흐름부터 검증한다. 이후 ‘매일 확인’, ‘대화’, ‘궁합’ 중 제품 목적에 맞는 경로를 추가한다. 상담 마켓·포인트 경제·날짜 캘린더는 운영 복잡도와 목적이 별도이므로 자동 포함하지 않는다.

## 7. 디자인 프로세스에 넣는 방법

### 조사부터 제작까지

1. 과업과 열린 질문을 기록한다. ‘친근함’만 적지 말고 ‘한자를 모르는 사람이 풀이의 뜻을 설명할 수 있는가’처럼 장면을 정의한다.
2. 같은 과업의 화면을 수집한다. 소개 글만 확보했다면 기능 근거로 제한한다. 신규 디자인을 생성해서 레퍼런스 증거로 삼지 않는다.
3. 별도 검수자가 출처·화면·주장 일치를 검수한다. 수집자의 추천을 주지 않아 관찰을 유도하지 않는다.
4. 사람에게 화면을 하나씩 보여주고 반응을 받는다. 다음 화면을 보여주기 전 그 화면의 채택 범위·보류 이유를 남긴다.
5. 원문 반응에서 추출 패턴과 기준 후보를 만든다. 앱 전체를 고르는 행위와 특정 정보 계층을 고르는 행위를 분리한다.
6. 사람이 기준을 승격하면 B단계의 독립 비교 축과 baseline으로 연결한다. 무드·밀도·정보 공개 방식이 서로 영향을 주면 축을 재분리한다.
7. 선택된 조합으로 라이브러리·화면을 만든다. 패턴마다 적용 노드 ID를 남긴다.
8. A는 노드 속성, C는 승인된 기준과 렌더, 흐름 검증은 상태 전환을 확인한다. 결과에서 새 취향이 발견되면 원문을 다음 기준 후보로 되돌린다.

### 검증 기준 후보 — 아직 확정 아님

| 후보 | 평가할 장면 | 판단에 필요한 증거 | 연결 |
|---|---|---|---|
| CR-01 요약과 설명의 위계 | 결과를 처음 여는 장면 | 사람이 무엇부터 읽는지·각 구역 역할을 설명하는지 | C-2 / J-01, S-01 |
| CR-02 읽기 밀도 | 가장 긴 실제 풀이 | 본문·장식·다음 행동이 경합하는 위치 | C-4 / F-02, S-01 |
| CR-03 캐릭터 역할 | 처음 설명·빈 상태·긴 결과 | 안내를 돕는지, 설명을 가리는지에 대한 사람 반응 | C-5 / F-02, H-02 |
| CR-04 복구의 완성도 | 시간 미상·분석 실패·대화 복귀 | 수정·재시도 후 입력과 결과가 유지되는 흐름 | C-6 + 흐름 검증 |
| CR-05 표현의 이해 | 점수·예측 날짜·오행 해설 | 사용자가 수치를 어떻게 해석하는지 | 콘텐츠 이해 검증; 기존 C에 억지로 끼우지 않음 |

통과 점수·허용 밀도·폰트 크기·그리드·색상은 이번 조사로 정하지 않는다. 참조 이미지의 픽셀은 원본 Figma 토큰이 아니다. 도메인별 기준은 별도 사주 프로젝트 원장에 넣고 공통 하네스에는 절차만 둔다.

## 8. 이번 반영과 남은 결정

- 공통 SKILL에 0-R 절차와 조사 전용 작업 범위를 추가했다.
- `templates/reference-review.md`에 증거·독립 검수·추천·사람 결정·추출·변경 이력 계약을 추가했다.
- brief 템플릿에 REF/PATTERN 연결, decisions 템플릿에 제작 노드 추적을 추가했다.
- 공식 공개 이미지 6개를 읽고 분석했다. 직접 실행 흐름과 Figma 제작 검증은 미실시다.
- 별도 신규 컨텍스트 검수자가 이미지 6개의 관찰 주장을 확인했다. [독립 검수 원문](saju-reference-evidence-review.md). 증거 일치 확인이며 디자인 채택 판정은 아니다.
- `git diff --check`는 통과했다. 기존 계약 검사기는 오류 0건, 사주 프로젝트 원장 3개 미생성 경고를 보고했다. 이는 이번 조사 보고서를 사주 프로젝트의 승인된 원장으로 간주하지 않았기 때문이다. 공개 이미지가 Git 제외 대상인 것도 확인했다.
- 사람의 REF별 채택·보류·제외, 새 기준 승격, 앱 기능 범위는 미결정이다. 이번 조사 완료가 디자인 승인 완료를 뜻하지 않는다.

최종 확인 시 저장소의 `scripts/harness/check_contracts.py`, `templates/contracts/gate.yaml`, V단계 본문이 존재한다. 기존 검사기는 프로젝트 경로·도메인 분리·GATE 등을 검사한다. 이번 0-R 추가는 문서 기반 절차·기록 계약이며 REF의 사람 선택이나 이미지 증거를 자동 판정하는 엔진을 구현한 것은 아니다.
